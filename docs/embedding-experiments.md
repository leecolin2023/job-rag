# 怎样验证 Embedding 与 Rerank 是否真的改善 RAG 检索？

> 本文以 Job-RAG 的 Qwen3.7 离线实验为实例，讲清检索实验的设计、运行过程、评价指标及解释边界。实验产物独立存放，不会自动替换线上 PostgreSQL 索引或服务。

## 一、先区分两个不同的问题：找得到，还是排得好？

假设用户想找“负责企业知识库全链路的工程岗位”。检索系统首先要从数百条岗位中**把有关岗位纳入候选**，然后才需要**把真正最匹配的放到前面**。

- **Embedding 召回**：把问题和岗位文本编码成向量，通过相似度生成候选。它改变“哪些岗位进入候选及初始排名”。
- **Rerank 重排**：拿到一组**已经召回的**岗位，根据问题重新判断顺序。它可能提升前排质量，却不能找回根本没有进入候选集的岗位。
- **BM25**：依据词项出现频率、文档长度等计算词法相关性。技术名词明确的查询常有很强表现；它和向量方法提供的是不同检索信号。

因此本项目把实验分为两轮：**第一轮在同一查询和硬条件下比较召回/分块方案；第二轮冻结同一批候选，只比较重排**。如果第二轮偷偷增加查询改写或召回来源，效果变化就无法归因给 Rerank。

## 二、为什么不能只把“模型切换前后”拿来比较？

检索结果除了受模型影响，还受**原文怎么组织、文档块大小、查询表达、硬条件、岗位聚合规则**影响。换掉模型同时改变分块时，即使排名提高，也不知道是哪种变化带来的。

第一轮固定 Embedding 模型、1024 维、查询和硬条件；不使用 Rerank、改写或 Hybrid，把文档表示作为主要变量。

| Arm | 文档表示 | 能回答的对照问题 |
|---|---|---|
| A_legacy_1100 | 历史 1100 字符正文切分、重复完整头部 | 原有基线 |
| B_fixed_compact_1100 | 与 A 相同正文边界，头部更紧凑 | 删掉重复结构化元数据有没有影响 |
| C_section_compact_1100 | 章节/条目/条件边界，紧凑岗位与章节上下文 | 结构化组织的**综合**效果 |
| D_section_typed_1100 | C 的相同边界，加条件性质提示 | 提示词本身有无效果 |
| E_section_typed_600 | D 的小预算方案 | 更小的块是否更利于召回 |
| BM25_reference | 岗位标题+完整描述的词法检索 | 不付费向量的参考，不混为 dense 单因素组 |

C 相对 B 不只变化了标题；A 的旧预算只限制正文，渲染后总长度可能超过 1100。因此不能宣称“所有方案完全等 Token、只比较分块算法”。

准备快照 `runtime/experiments/prepared-20261025-v5` 覆盖 **592 条非空岗位描述**。A/B/C/D/E 块数分别为 **790 / 790 / 2443 / 2443 / 2657**。块数只是处理结果，不是检索质量分数；规则变化后要重新生成快照。

## 三、向量如何转成岗位级排名？

先按硬条件决定 eligible 岗位；对它们的全部向量块计算**归一化余弦相似度**；同一岗位如果有多个块，取最高得分作为岗位代表分数，再输出 Top-M（默认 50）。

```text
问题 → Embedding 向量
  → 与全部符合硬条件的文档块计算相似度
  → 同一岗位取最高命中块
  → 按岗位排序 → Top-50候选
```

为什么不先截取 Top-50 chunk 再去重？因为一份长 JD 可以让多个相似块同时进榜，从而挤掉其他本应进入候选的岗位。

**max 聚合也有代价**：拥有更多块的岗位，可能有更多机会出现局部高相似分数。因此 C/D 增加块数后的变化不能直接解释成“模型理解增强”。实验需同时查看具体命中块与不同预算的表现。

## 四、怎样判断 Recall、nDCG 和 Precision？

如果每条问题只人工标注了 1 条已知相关岗位，那么系统找回这条岗位，只能说明**种子命中**。语料里可能还有 10 条同样相关的岗位，未标注不等于负例。

本轮有 **30 条查询、15 个主题组**；每组两种表述，组内不跨 dev/test，划分为 dev 14 条、test 16 条，涵盖 RAG、知识图谱、Harness、Web3、营销 Agent、多模态、推理、运维、实习和产品。

指标及其意义：

- `seed_recall@5/10/20`：已知正例中有多少出现在前 K；**不是全集真实 Recall**。单种子情况下也对应种子 HitRate。
- `seed_ndcg@5`：已知正例排得越靠前权重越高；未标注相关岗位会使解释受限。
- `precision_lower_bound@K`、`judged_fraction@K`：区分“至少有多少已标相关”和“实际审过多少”；不能宣传成正式准确率。
- `pooled_*`：对多系统候选池统一人工审过之后的受限指标。
- 无前缀 `recall@K`/`precision@K`：只有把所有 eligible 岗位穷尽判断并包含负例，才具备相应标注覆盖条件。

Dev 用于选择方案，Test 留作最终检验，不能反复根据 Test 调参。置信区间按**主题组**做配对 cluster bootstrap（2000 次、固定种子），而不是把 30 种相近写法都当作独立用户。15 组仍只是 pilot 规模。

## 五、第二轮为什么必须先冻结候选、再人工审阅？

`pool --depth 50` 把所有系统 Top-50 和种子正例合并，按 job_id 排列并隐藏原系统名/排名，避免标注者受先入印象影响。每个 query/job 打分：

| 字段 | 含义 |
|---|---|
| `grade` | 0 不相关、1 部分相关、2 相关、3 直接匹配 |
| `evidence` | 正例须引用岗位原文，并检查没有违反硬条件 |
| `reason` | 尤其解释“优先非必备”、否定条件、非 AI Agent 等误判 |
| `reviewed=true` | 本查询的**候选池**已审完，非全部语料穷尽 |
| `judgment_scope=pooled` | 默认标注范围，不得擅改成 exhaustive |

可以用 `rescore` 根据新人工标签重新评分，无须重复生成 Embedding；修订保存为新目录，不覆盖原结果。

固定第一轮某个通过 dev 选择的 dense arm 与同一候选集合，第二轮分别比较：`none`（原排名）、`bm25`（池内词法排序）、`section_rule`（透明章节/条件权重）、`qwen_default`、`qwen_recruitment_instruction`。最后两者用同一专用模型，仅改变招聘判断指令。全部方法使用同一候选岗位及父文档表示。

父文档优先包含任职要求、职责和加分项，通常每岗不超过 **1800 UTF-8 字节**；候选很多时统一缩减预算，并标记截断。这个数不是 Token。Rerank 必须返回完整候选索引排列；失败、重复、缺索引则停止，不能悄悄回退后继续宣布模型胜利。

第二轮主要看 **nDCG@5、Precision@5、MRR**，同时报告候选 Recall 上限。Rerank 不改变候选覆盖率是机制决定的，**不是失败证据**。模型输出分数也不能未经校准就当作跨请求的概率或阈值。

## 六、真实调用如何做到可复查并控制费用？

阿里百炼北京业务空间使用官方说明中的两种服务：

| 功能 | 模型 | 原生接口路径 |
|---|---|---|
| Embedding | `qwen3.7-text-embedding-flash`，1024 维、每批最多 20 条 | `/api/v1/services/embeddings/text-embedding/text-embedding` |
| Rerank | `qwen3.7-text-rerank` | `/api/v1/services/rerank/text-rerank/text-rerank` |

Embedding 文档请求设置 `parameters.text_type=document`，查询设置 `query`，不另加 instruct；Rerank 一次提交同一候选集合，以免把不同请求的相对分数误作同一尺度。文档列示 Embedding 单条上限 128,000 Tokens，但当前分块远小于它。

API Key **不是 API Host**：Host 由业务空间决定，不能从凭据反推。项目的隔离配置 `.env.experiments` 使用用户自己的北京空间 Host，凭据在本地终端隐藏输入：

```bash
python3 scripts/setup_bailian_env.py \
  --host https://llm-q9ba44cu7o2ffpnb.cn-beijing.maas.aliyuncs.com --set-key

job-rag-experiment --max-requests 2 probe --execute
```

配置文件权限 0600；不在 CLI 参数、Git 或聊天中放 Key。官方模型说明只证明接口存在，**当前账户是否授权必须靠探针请求验证**。官方接口资料：[文本向量](https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api)、[文本排序](https://help.aliyun.com/zh/model-studio/text-rerank-api)。

为让对照可复现：

1. `prepare` 不调用 API，冻结 CSV、查询、正例、分块/偏移、实现及策略哈希。
2. 缓存键包括 Host、模型、维度、query/document 类型及精确文本；同一文本复用向量，但不能跨模型签名混用。
3. 候选排名保存 hash；第二轮改候选就必须重新冻结 manifest。
4. 只有显式 `--execute` 才发送请求；`--max-requests` 限 HTTP 次数（重试也计入）。
5. `--max-cost-cny` 按公开价和 usage 加软件保护，当前首轮设 **0.50 元/500 请求**；它不是云端账单硬限额。失败请求即使无 usage 也可能计费，429/部分 5xx 有限重试，401/403/404 不无意义重试。
6. 日志存 request_id、模型、内容哈希、HTTP 状态、时延及 usage，不存凭据/正文；缓存耗时不等于模型网络时延。模型别名可能滚动更新，运行时间和缓存可帮助追溯，但不能证明后端权重严格固定。

结果存 `runtime/experiments/`，包含准备快照、SQLite 缓存、请求 JSONL、排名、`summary.json`、`report.md`、`metrics.csv`，均被 Git 忽略。

## 七、这轮已经做到了哪一步？

截至 2026-10-25：解析、快照、API 适配和实验基准已完成；**76 项测试通过**；隔离 PostgreSQL 迁移与 pgvector 测试通过（数据库测试向量不是 Qwen 输出）。正文覆盖审计未发现非空白内容丢失，**95 条岗位无法可靠判断章节，保留 unknown**。

真实 Embedding 探针返回了 1024 维向量，Rerank 小探针通过；百炼响应的 `index` 字段和部分文档示例 `text_index` 不同，适配器已兼容并校验。首轮真实召回已执行：**348 次成功响应报告 1,531,082 输入 Token**，按公开价格估算约 **0.1914 元**；全量 Rerank **尚未执行**。费用可用 `python scripts/summarize_experiment_usage.py --journal <manifest中的request_journal>` 复核，不等同于实际账单。

从原理到实践，实验要回答的不是“用了更先进模型没有”，而是：**在固定问题、数据与条件的前提下，究竟哪种表示或排序方法改变了结果，是否真的改变了用户能找到的相关岗位。** 具体排名见 [第一轮结果](recall-pilot-2026-10-25.md)。
