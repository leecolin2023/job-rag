# 如何观察一次 Agent 岗位检索：会话、服务日志与数据状态

当用户说“Agent 没找到那个岗位”时，问题可能发生在三个不同位置：模型没有提出合适的查询、检索服务没有返回候选，或者岗位资料本身已经变化。如果只看最终回答，很难知道原因。因此需要区分**会话行为、服务请求和业务数据状态**。

## 一、三种记录各自回答什么问题？

| 记录 | 观察对象 | 能回答的问题 | 不能证明什么 |
|---|---|---|---|
| OpenCode harness 会话 | 用户输入、模型可见回复、工具调用参数与结果 | 模型实际怎样改写查询、选择证据、生成回答 | 无法还原供应商私有推理过程 |
| API/MCP/网关/nginx 日志 | 请求状态、服务运行、访问异常 | 请求是否到达、HTTP 为什么失败、容器有无故障 | 不是完整工具输入/输出审计 |
| 数据库业务历史 | `revisions`、`status_events`、`index_tasks` | 某岗位何时改变、是否被核验、索引是否失败 | 不直接反映模型为什么选择它 |

这些记录对应三条不同的事实链。**调用方的模型会话保存在调用方环境**，远端 Job-RAG 服务不会自动收集其它机器上的 OpenCode 会话。当前也没有跨服务 trace ID 或全量请求/响应审计，不能把局部日志拼成一条已经完整验证的端到端追踪。

## 二、沿真实调用顺序排查一个例子

假设问题是“昨天可以查到某个 RAG 岗位，今天找不到”。

第一步看**会话**：两次查询的城市、薪资、技能硬条件是否相同？Agent 有没有把“加分项 Python”误当成“必须 Python”？实际调用了哪个 MCP 工具、带了什么参数？

第二步看**服务**：MCP 请求有无成功到达，是否返回 401、429 或 5xx，调用有没有超时？HTTP 200 只能说明请求成功处理，不能保证候选相关。

第三步看**数据**：岗位是否被标记为 `closed`、描述是否已更新、索引任务是否失败或签名不兼容？如果岗位因明确硬条件被排除，再怎么改写语义查询也不会找回来。

第四步才判断**排序质量**：在候选集合和状态一致的前提下，比较原文证据、各路排名与 Agent 的最后选择。由此区分“没进候选”“进了候选但靠后”“模型读到了但判断不当”。

这个顺序是排障示例，并不假定所有失败都有同一种原因。

## 三、如何导出 OpenCode 可观察轨迹？

在**保存该会话的调用方机器**上执行：

```bash
python3 scripts/export_test_trace.py ses_你的会话ID
```

脚本通过 OpenCode V2 API 读取会话，**不直接修改 OpenCode 活动数据库**。默认仅导出首轮到第一个 `idle` 事件，避免后续其他对话干扰对一次查询的分析。

```text
runtime/analysis/<session_id>/
├── timeline.md    # 按时间阅读
├── trace.json     # 结构化轨迹
└── tools.jsonl     # 逐次工具调用
```

导出保留可观察的输入、输出、工具参数、返回结果、状态和已有时间信息；排除私有推理、供应商原始载荷及明显的密钥字段，并对 Bearer 字符串做基础脱敏。Code Mode 工具有时显示为 `execute`，其 `input.code` 和返回结果仍能说明实际 MCP 调用。

**这不是完整思维链，也不是通用秘密扫描器。** 导出目录被 Git 忽略、使用受限权限，且脚本拒绝覆盖已有目录；分享前仍需检查岗位内容、个人信息与密钥。查看 OpenCode 本地数据路径可运行：

```bash
opencode debug paths db
opencode debug paths log
```

不要直接修改正在使用的数据库。

## 四、服务端日志怎么看？

```bash
sudo docker compose --env-file .env.docker \
  -f docker-compose.yml -f docker-compose.public.yml logs --tail 100 api mcp gateway
```

日志主要用于确认容器状态、请求错误与网关行为，而非重建完整的 Agent 决策。它们不应记录 Authorization 令牌、完整私人简历或供应商请求正文。

未来若增加更完整的可观测性，合理的思路是为一次请求建立一致的关联 ID，让调用方工具轨迹、MCP/API 请求与索引版本能够对齐，同时规定保留期限、脱敏和访问控制。**这是后续设计方向，不是当前已实现功能。**

最终要记住：**可观测性不是“日志越多越好”，而是能把某个结果追溯到足以解释它的查询、服务与数据状态，并清楚知道哪一段证据尚未记录。**
