# Job-RAG 当前能力：从岗位原文到可追溯的检索服务

> 状态快照：2026-10-25；线上服务版本 **0.1.0**。本文解释已建成的系统怎样运行、每项能力解决什么问题，以及哪些成果仍停留在离线实验。它不是实时运行监控。

## 一、Job-RAG 实际要解决什么问题？

原始招聘表格可以记录“岗位名称、公司、薪资、岗位描述”，但用户实际会问：“广州有哪些侧重企业 RAG 和 Agent 工程、薪资下限达到 20K 的岗位？”

这不是一个简单的关键词查找：薪资和城市必须满足**硬条件**，岗位职责与用户目标之间的相似程度属于**相关性排序**，最后还要知道**原文依据和招聘状态**。因此，项目把一条招聘信息拆成几种不同责任的数据，而不是把整张 CSV 直接交给大模型回答。

| 层次 | 保存或执行的内容 | 为什么需要 |
|---|---|---|
| 原始来源 | `data/jobs.csv`，593 个唯一岗位 ID、592 条有描述 | 任何判断都能回查原文；没有描述的 1 条不能凭空补齐 |
| 事实与生命周期 | SQLAlchemy 数据模型、岗位版本、状态事件、首次/最近观察和核验时间 | 区分“岗位文字更新”与“岗位确实在招” |
| 检索索引 | BM25、分块、可选 Embedding、版本签名和失败重试 | 根据问题找出候选，同时防止新旧文本或模型索引混用 |
| 条件过滤 | 城市、薪资、经验等结构化字段 | 防止“语义很相关但不符合必要条件”的岗位混入 |
| 应用入口 | FastAPI、网页、CLI、只读 MCP | 同一份数据可由浏览器、脚本或 Agent 查询 |
| 调用方理解 | DeepSeek/OpenCode harness 进行查询改写和证据比较 | 理解复杂表述，但不能把模型解释当成岗位事实 |

当前本地可使用 SQLite，Docker 服务化使用 PostgreSQL + pgvector。**存在 pgvector 数据库不等于已经运行向量检索**：线上尚未接入真实 Embedding；已有真实 Qwen Embedding 数据来自独立实验，不应与线上状态混为一谈。

## 二、一条用户查询怎样得到候选岗位？

以“找广州、月薪下限 20K、负责知识库全流程建设的工程岗位”为例：

1. **确定硬条件。** 城市和可比较的月薪下限先从结构化事实字段过滤。缺少薪资或为不同计薪单位的记录不能被推断为达标。
2. **检索候选。** 当前线上以 BM25 及多查询词法召回为主。BM25 利用词项匹配与文档统计排序；它能很好识别明确技术词，但不能保证理解每种语义改写。
3. **汇总同一岗位。** 一个岗位可能有多个命中分块，返回结果按岗位 ID 聚合，避免一份长 JD 的多个段落占满列表。多查询结果可以通过 RRF 融合：它使用各路排名而非强行比较不同来源的原始分数。
4. **核对证据和状态。** 候选显示可追溯的描述片段；最终推荐前通过 `get_job` 读取完整原文、最新版本及状态。
5. **可选模型解释。** OpenCode 的 DeepSeek harness 可提出同义查询、检查证据并形成说明；它是调用检索工具的模型，**不是生成向量的 Embedding 模型**。网页本身不会因接入 MCP 而自动具备 Agent 理解能力。

岗位状态初始全部为 `unknown`。导入时的“已获得描述”只表示资料收集成功，**不是正在招聘的证明**；系统目前没有爬虫或自动核验职位有效性的机制。

## 三、为什么需要版本、索引任务和模型签名？

如果企业修改了 JD，却继续使用旧向量，就可能出现“展示的是新版岗位、命中理由却来自旧版内容”的矛盾。项目因此区分**来源事实的版本**与**面向检索的派生索引**：

- 原始行没有变化时，主要更新观察时间；内容变化保留历史版本。
- 岗位描述改变时，重建该岗位的分块；索引准备好之前不把旧内容当作新内容展示。
- 只有采集日期或薪资等不影响向量文本的字段变化时，在签名相同的条件下可以复用向量。
- 索引任务失败保留状态供 `worker` 重试；不得把失败后的半成品索引标记为完成。
- 解析规则、分块预算或 Embedding 模型发生变化时，索引签名隔离旧结果；新代码及数据迁移并非自动完成。

目前写入与索引按**单写入者**设计。没有常驻分布式队列、蓝绿索引切换管理器和完整自动迁移设施。这是一个可运行的原型服务，不是多租户生产知识平台。

## 四、部署链路与信任边界

```text
其他机器的 OpenCode / harness
  → 公网 HTTPS :443 /mcp（宿主机 nginx）
  → 127.0.0.1:8443（Docker 网关，Bearer 鉴权、限流）
  → MCP → API → PostgreSQL + pgvector

本机网页 / API：127.0.0.1:8008
本机 MCP：127.0.0.1:8009/mcp
```

公网 MCP 地址为 `https://106.55.35.201/mcp`，**必须携带经安全渠道发放的令牌**；没有开放导入、管理、SQL 或模型密钥读取。数据库和核心服务不直接映射到公网。调用方维护自己的模型账户、额度与会话，本服务器不共享 OpenCode Go 凭据。

这套隔离的目的，是让远端 Agent **能够查岗位，却不能因为查询需求而取得写库权限**。不过共享只读令牌无法辨别每个具体用户；没有完整的用户级配额与请求审计，不适合直接承载多租户敏感数据。

## 五、哪些能力已经验证？验证又不能证明什么？

| 验证对象 | 已有结果 | 不应扩大成的结论 |
|---|---|---|
| 自动化功能 | `pytest -q`：36 项通过，覆盖导入、更新、下架、检索、降级与鉴权 | 不是全部业务场景的质量保证 |
| 数据库 | `scripts/check_postgres.py` 在隔离库验证 pgvector 写入/距离、版本替换、关闭过滤 | 测试向量不是实际 Qwen Embedding |
| MCP | `scripts/check_mcp.py` 验证握手、工具目录、统计、候选与详情 | 不是多客户端压测 |
| harness | 已用 `opencode-go/deepseek-v4.1-flash` 完成统计→查询改写→候选召回→详情复核 | 不代表模型生成的判断都正确 |
| 公网入口 | 错误或缺失令牌返回 401、正确令牌可访问；TLS 信任检查通过；原站点仍返回 200 | 不是安全渗透测试或证书生命周期监控 |

离线实验已经真实调用 Embedding 并获得可复查排名，但**线上仍使用 0.1.0 容器，未迁移和切换**。第一轮结果与结论边界分别见 [召回实验](recall-pilot-2026-10-25.md)、[逐项案例](recall-case-audit-2026-10-25.md)。

## 六、目前最重要的能力边界

**检索效果**：缺少穷尽标注的相关性基准；关键词、章节分块、语义向量、Rerank 应按固定对照实验判断，不因启用了模型就假设效果更好。

**业务真实性**：岗位未自动验证有效性；重复/近重复招聘信息、条件冲突与人工状态维护仍是数据质量问题。

**工程运维**：缺少自动备份、完整迁移工具、证书到期告警、分布式索引调度与跨服务统一追踪；新服务器不能照搬当前 nginx、IP 和证书路径。

**交付范围**：仓库保留源代码、593 条源 CSV、配置模板、测试与部署定义；不提交实值 `.env*`、访问令牌、证书私钥、业务数据库及备份、运行日志、OpenCode 会话导出或用户全局配置。

理解这套系统的关键，是把四件事分开：**岗位原文是什么、哪些岗位符合硬条件、检索系统把谁排前面、最终推荐有没有证据支持。** 它们有关联，但任何一项都不能替其他项做保证。
