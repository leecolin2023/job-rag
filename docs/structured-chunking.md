# 为什么 RAG 要结构化分块？从招聘 JD 到可追溯检索证据

## 一、分块改变的不是原始事实，而是模型看见事实的方式

一份招聘 JD 往往同时包含“岗位职责”“任职要求”“加分项”“福利”。例如，“熟悉 Python”出现在**任职要求**中，和出现在**加分项**中，文字相近，但对求职者的意义完全不同。

传统固定长度切分按字符数划开文本，可能把标题与要求拆散、把两个条件接在同一块中。检索模型看到局部句子时便失去了上下文。结构化分块希望做到：**检索时仍能知道一段文字属于哪个章节、处于什么条件语境，并能回到原始字符位置核对。**

不过，结构化并不必然提高召回：块变小后，原本跨几个条目才完整的业务场景也可能被拆散；增加条件提示还可能改变向量相似度。是否更好需要实验而不是靠设计直觉裁定。

## 二、分块流程具体如何运行？

`job_rag/chunking/core.py` 负责构造 `Document(text, details)`，公共入口由 `job_rag/chunking/__init__.py` 导出；需要文本列表时读取各 `Document` 的 `text`。原固定分块由 `chunking/legacy.py` 的 `legacy_documents()` 提供，用于历史方案对照，不再由标准化模块提供分块入口。目录职责见[分块目录说明](../job_rag/chunking/README.md)。

1. **识别章节。** 支持职责、任职要求、加分项、福利、公司介绍与 `unknown`，兼容编号、Markdown 和异常换行标题，例如 `【岗位\n职责】`；不在普通句子内部随意找标题。
2. **保留条目。** 优先保持一条要求及其续行的整体性，不把 `Python或Java` 这样的条件机械拆开。
3. **识别条件性质。** 标签为 `required`（必备）、`preferred`（优先）、`not_required`（非必备）、`mixed`（混合）、`unspecified`（未说明）。当一个条目同时有要求与例外时，保守标记 `mixed`，不假装已经完成逻辑推理。
4. **控制分块边界。** 不跨岗位、章节和条件标签混合块；过长时优先按句子拆，最后才硬切，并记录 `continuation_id`、`hard_split` 与来源位置。
5. **建立溯源元数据。** 记录正文及标题偏移、原文、章节、标签识别方式、解析/分块版本和预算单位。

原文偏移以 Python Unicode 码点计数，即 `source_offset_unit=unicode_codepoints`；它不是 UTF-8 字节下标，也不能直接当作 JavaScript UTF-16 下标。

这些标签是**规则解析结果**，不是经过人工确认的招聘条件。“未知”比凭猜测标成“必备”更可靠。真实复杂条件仍要结合原文判断。

## 三、为什么向量文本和事实字段要分开？

新方案的 Embedding 文本侧重**岗位标题、章节、条件提示（可选）和原文**；公司、薪资、城市、学历继续保存在事实库和返回结果。

原因有两个。第一，城市和薪资属于确定性硬筛选，不能通过“向量比较看起来像”来保证准确。第二，薪资等内容字段更新时，只要向量正文及模型签名未变，就能复用已有 Embedding，同时事实库记录新版本；采集时间等采集元数据更新则只原位刷新，不产生新版本。

这正是“事实层负责准确过滤、向量层负责相似召回”的职责分离，而不是认为向量可以替代数据库条件。

## 四、1100 字符为什么不等于 1100 Token？

文本预算约束的是分块占用的空间，但不同计数口径不可以混用：

| `CHUNK_BUDGET_UNIT` | 实际含义 |
|---|---|
| `chars` | Unicode 字符数；结构化分块把上下文头部也计入预算 |
| `utf8_bytes` | UTF-8 编码字节数，是保守代理量，非模型 Token |
| `tokens` | 使用指定本地 tokenizer JSON；需实验依赖与 `TOKENIZER_PATH` |

同一汉字可能占多个 UTF-8 字节，模型 Token 数又受具体 tokenizer 影响。项目**没有假设旧 Qwen tokenizer 等同于托管 Qwen3.7 tokenizer**；实验默认使用字符预算，真实模型调用量依据百炼返回的 usage。

缩小分块可能提高定位精度，却也增加块数、降低单块上下文完整度；扩大分块的利弊反过来。具体的取舍见 [实验协议](embedding-experiments.md) 和 [首轮结果](recall-pilot-2026-10-25.md)。

## 五、检索结果如何把“命中”变成“可核对”？

新返回结构的 `evidence_details` 包含命中片段的章节、条件性质、原文位置；`qualification_context` 还提供任职要求和加分项上下文，总预算为 **3600 字符**。发生截断时会标记 `truncated`；完整岗位仍通过详情接口获得，Chat 生成端也能使用这些上下文。

**注意一个重要区别**：现有 `skills` 参数只保证技能词出现在标题/描述里，**不保证该技能是岗位必备条件**。虽然分块保存了 `preferred` 等标签，系统尚未把复杂条件解析成可靠的布尔筛选器。这说明“能够标注条件”和“能够严格执行条件”不是同一能力。

## 六、改变分块策略为什么还需要迁移和重建索引？

新 `chunks` 表增加可空 `details JSON` 字段，并记录迁移版本 `002_chunk_structure`。已有库不会在启动时被悄悄改表；缺列会要求显式迁移。

```bash
# 停止并发写入，先备份数据库
job-rag migrate
job-rag reindex
```

索引签名包含解析版本、分块版本、策略、预算单位、预算大小及本地 tokenizer 文件哈希。因此更改规则后旧向量不参与新方案检索，避免**模型/文本版本不对应**。

截至本文件快照，**线上容器尚未升级**，实验使用独立数据库，不会直接改线上数据。实际发布应先备份、保留旧镜像与配置；在恢复副本上验证迁移和 MCP；构建候选索引后核对数量、状态及人工样例，再决定切换时间。

当前没有在线蓝绿切换管理器。直接在单库重建索引可能使旧签名岗位暂时不可检索，正式变更要采用候选库或维护窗口。

结构化分块的完整判断不是“能切得更细”，而是：**它是否在保留充分语境的同时，使每个命中片段可以被正确解释、定位和复核。**
