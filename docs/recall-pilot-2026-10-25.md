# Embedding 召回实验告诉了我们什么？一轮真实 RAG 对照的解读

> 2026-10-25 的真实运行记录。本文既保留全部主要结果，也解释为什么它们不能被简化为“Embedding 输给 BM25”。

## 一、实验究竟比较什么？

把“能找到工作岗位”拆成两件事：**是否把相关岗位带进前 K 位**，以及**它们是否真的符合整段求职意图**。前者可以从排名直接观察；后者需要人工判断岗位原文。若只标注了一个已知好岗位，那么“没找到这个指定 ID”并不等于“没找到任何合适岗位”。

本轮使用百炼北京业务空间真实 `qwen3.7-text-embedding-flash`（1024维），不是测试向量；592 条有描述的岗位、30 条查询，按 15 个主题组拆成 dev 14 条/test 16 条。五个 Embedding 分块 arm 在同一问题和硬条件上执行；不使用 Rerank、查询改写或 Hybrid。先对所有 eligible 块做精确余弦计算，再按岗位取最高分并留 Top-50。

运行结果存于 `runtime/experiments/recall-20261025-v1/`，源快照为 `prepared-20261025-v5`。

**本节数字全部是 `seed` 指标：每个问题只有一个来源可核验的种子正例，未知候选不代表负例。** 因此 seed Recall@K 在这里也等于指定岗位 HitRate@K，不能解释成总体 Recall 或 Precision。

## 二、先看完整结果，再解释它们

五种文档方案：A = 原固定分块；B = 紧凑固定分块；C = 章节紧凑分块；D = C 加条件性质文本提示；E = D 的小预算版本。BM25 用完整标题和描述做词法参考，因此也存在输入表示差异，不是 Embedding 与 BM25 的纯算法对照。

### 这些数字背后至少有四层含义

**第一，BM25 对本轮种子岗位表现很强，但这不是“词法理解强于语义理解”的证据。** 查询是根据岗位原文构造的，往往包含明确技术词，天然有利于词项匹配；BM25 检索全文、向量方案检索分块，输入条件也不完全一致。

**第二，C 在 Test 把正例排得更前，不等于已经证明结构化分块普遍更好。** C 相对 A 的 test seed nDCG@5 约 +0.1399，按 8 个主题组做 bootstrap 的 95% 区间为 [0, 0.28125]，包含 0；而 Dev 没出现一致改善。样本小、任务相近，不支持稳定显著提升或直接上线。

**第三，分块更多不必然更准确。** D 添加条件提示没有提高本轮向量排名；E 更小的预算也没让主要 seed 指标变好。条件标签仍值得作为**可追溯元数据**保留，但不能预先认定“把条件词写进向量就更聪明”。

**第四，不应根据 Test 反过来选择赢家。** 如果必须固定一个 dense 基线继续做第二轮，Dev 上 A 是保守起点，同时保留 BM25 参照；真正切换还需要完整候选审阅。

## 三、看五个真实例子，为什么同一个平均数可能掩盖不同机制

| 查询 | 原固定向量 A | 章节向量 C | BM25 | 更合理的解读 |
|---|---:|---:|---:|---|
| `harness-01` | 26 | 1 | 2 | 章节上下文把“Agent infrastructure、上下文压缩、记忆”对应的指定岗位排前 |
| `marketing-02` | 1 | 11 | 2 | 结构化分块反而可能打散销售机器人失败会话与人工接管的完整工作情景 |
| `rag-01` | 15 | 49 | 6 | 虽未命中指定种子，但 C 与 BM25 的 Top-1 都是高度贴合的“知识库开发工程师（RAG方向）” |
| `data-product-02` | 1 | 1 | 2 | BM25 Top-1 是与种子职责非常接近的另一岗位，未标注会制造假输赢 |
| `mmrag-01` | 10 | 9 | 1 | 对跨文本/图片/音视频 RAG 的明确需求，BM25 将指定多模态岗位排前；C Top-1 偏视觉商品识别 |

这些是**指定种子岗位的名次**，不是各算法生成内容的可信度分数。例如 `rag-01` 的已标种子是“AI解决方案专家（RAG方向）”，C 排 49；但真正 Top-1 的“知识库开发工程师（RAG方向）”明确覆盖“知识接入→解析→索引→检索→服务全链路”。仅因为这份岗位没在正例表中，就宣称“C 没找回有关岗位”，会误判真实用户体验。

同理，`data-product-02` 两份岗位都写有“具备一定的代码能力”为加分项，其规范化文本相似度约 **99.01%**。这种近重复不表示两个岗位 ID 必须业务合并，却要求标注者把两个都审一遍。

详见[五案原文及全部30条排名](recall-case-audit-2026-10-25.md)。另外，Dev 的 A 未在 Top-10 找到 `rag-01`、`harness-01`；C 未找到 `rag-01`、`marketing-02`，说明改善与退化会相互抵消。

## 四、为什么接下来不是立刻接上 Rerank？

Rerank 可以重新排序已召回的 Top-50，但它**无法弥补候选集里缺失的真正相关岗位**。如果先让模型重排、却不审阅新上来的结果，就会把“未标注”误当“不相关”，产生错误的 Precision@5。

目前已有不需模型费用的候选审阅文件：

- `runtime/experiments/review-20261025-v1.json`：Top-50 并集，2470 项 query/job 判断。
- `runtime/experiments/review-priority-top5-20261025-v1.json`：优先池，301 项判断。

应先复核以上退化问题及 Top-5 候选的原文，补全正例、近重复、否定条件与必备/优先判断；然后以固定候选比较重排方法。Rerank 小探针**已经成功**，但全量第二轮**尚未运行**，没有任何全量重排提升结果。

## 五、费用数字又说明了什么？

本轮共 **351 次 HTTP 尝试**：348 次 200，3 次 429 并经过有限重试。成功响应报告输入 **1,531,082 Token**；按公开价 **0.125 元/百万 Token**，对应估算 **0.19138525 元**。3 次无 usage 的失败请求被软件保护做了保守预留，manifest 中累计保护估算为 **0.2048395 元**，低于设置的 0.50 元。另有两个 Embedding 和一个 Rerank 小探针，所有真实请求中已报告 usage 的公开价格估算约 **0.191416 元**。

这不是账户实际扣款金额：免费额度、折扣、429 是否计费以平台账单为准。向量缓存已保存，不必为复看报告反复付费。排名、块 ID、bootstrap 和 CSV 见运行目录；日志只存哈希与 usage 元数据，不公开 Key。

## 六、如何复核而不污染原实验？

```bash
python scripts/explain_recall_cases.py
```

脚本从已保存结果导出全部 30 个问题、种子岗位、六种方案排名、Top-5 的岗位原文及章节向量命中块，写入 `runtime/analysis/recall-case-audit-20261025/{cases.md,rankings.csv,cases.json}`。不重新调用模型，不修改原标签或排名。BM25 分数与余弦相似度不是同一量纲，比较名次与证据而非比较原始分值。

这次最重要的学习结论是：**检索系统的好坏不是模型名字决定的。问题怎么构造、岗位怎样分块、如何标注相关性，会同时影响指标和对结果的解释。** 当前结果可以指导下一次实验，却还不能裁决真实用户查询上的最终赢家。
