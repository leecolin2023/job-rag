# 为什么种子岗位的排名不能代表真实检索质量？30 条 RAG 查询的逐项学习

> 本文依据 2026-10-25 **已保存**的真实 Embedding 实验结果重新解释排名，没有重新调用模型、回填正例或修改原始数据。原始结果 SHA256：`3f43e403024d9eafbedf52fcaa97c07de7025d6a8ea66e85b3deda6aae1308a6`。

## 一、先理解排名实验到底测到了什么

系统面对一条查询，例如“找负责企业知识接入、索引、检索和答案生成全链路的岗位”，会为所有符合硬条件的岗位计算排名。实验事先指定某个岗位 ID 为**种子正例**；表中的“第几名”，只表示这个指定 ID 在结果中的位置，并不表示其他候选不相关。

本轮共有 **592 条非空岗位描述、30 条查询**，查询由助手依据岗位原文构造，不是独立用户盲测。真实模型为 `qwen3.7-text-embedding-flash`，维度 1024；查询与种子来源见 [benchmark.v1.json](../experiments/benchmark.v1.json)，总体设计见 [实验协议](embedding-experiments.md)。

这里使用四种代表方法：

| 代号 | 做法 | 同样需要注意的条件 |
|---|---|---|
| A | 历史固定长度分块 Embedding | 文档头部和正文切法与新方案不同 |
| C | 章节紧凑分块 Embedding | 一个岗位更多小块，取最相似块代表岗位 |
| D | C 的同样边界再加条件文本提示 | 提示也会改变输入向量 |
| BM25 | 标题 + **完整岗位描述**的词法检索 | 与分块向量不是严格相同文本表示 |

以上排名越小，说明指定种子越靠前；**不是相关性概率**。BM25 原始分数与余弦相似度不是同一单位，不能直接比较分值。

## 二、先读总体统计：BM25 的优势究竟是什么？

| 方法 | 种子 Top-1 命中 | 种子 Top-5 命中 | 种子 Top-10 命中 |
|---|---:|---:|---:|
| A 原固定分块向量 | 18/30 | 26/30 | 28/30 |
| C 章节紧凑向量 | 22/30 | 26/30 | 28/30 |
| D 章节+条件提示向量 | 20/30 | 26/30 | 28/30 |
| BM25 | 24/30 | 29/30 | 30/30 |

这意味着在**这 30 个指定种子 ID**上，BM25 的前排出现次数更多；它不能证明 BM25 对**真实用户意图**的相关性更好。

还有两个解释边界：

- 问题大多依据岗位内容构造，带有明显技术关键词，词法方法容易得分；它不是用户不知道岗位措辞时的独立盲测。
- 向量方法检索分块并对同岗 max 聚合，BM25 检索整份 JD，因此差异可能同时来自**算法、文档表示和聚合规则**。

C 相对 BM25 是 **2 条更靠前、21 条相同、7 条更靠后**。这个比较也只针对指定种子的名次，不能自动变成对全部岗位相关性的裁决。

## 三、五个例子把差异背后的机制讲清楚

### 例 1：`harness-01`——章节上下文可能帮助模型看见正确语义

查询：“想做智能体基础设施，研究上下文压缩、记忆和多智能体通信而不是单纯调接口”。

种子岗位 **agent工程师**（`ae80798c88a78bd70nx53tS_FVpY`）原文包括 `agent infrastructure harness`、上下文压缩、Agent 通信、记忆及检索接入。

| 方法 | 指定种子排名 | 前三名（从左到右） |
|---|---:|---|
| A | 26 | — |
| C | **1** | agent工程师；智算/训练/推理/AI/开放/智能体/agent；AI-智能体开发工程师 |
| BM25 | 2 | AI全栈工程师-广州；agent工程师；大模型开发工程师 |

C 将原方案排第 26 的种子提升到第 1。合理的**机制假设**是分块保留了更集中的基础设施语境，使这个岗位与“上下文压缩、记忆”问题更相近；但是单例无法区分是具体哪种文本特征促成了变化，也不能宣称结构化分块普遍更优。

### 例 2：`mmrag-01`——语义相近不一定满足完整的跨模态任务

查询：“让智能体能查文本图片音视频知识，研发跨模态检索与视觉问答的算法岗”。

种子 **AI Agent算法工程师（多模态大模型）**（`f3fd56cf149da00d0nZ609-0GVFT`）原文明确要求多模态 RAG，打通文本、图像、音视频的知识召回与生成。

A 排 **10**、C 排 **9**、BM25 排 **1**。C 的前三名是“中级算法工程师”“多模态与具身智能算法实习生（南沙）”“大模型算法研究员/专家”；其中 Top-1 命中内容偏向快消零售商品检测、SKU 识别和视觉算法。BM25 的前三名是该种子、“多模态大模型工程师（视觉-语言多模态）”“大模型算法研究员/专家”。

这个例子说明：**泛化为“多模态视觉”有时会偏离“跨模态知识检索”这一核心需求**。BM25 把指定种子排第一；其他岗位到底是否合格仍要核对完整职责。

### 例 3：`marketing-02`——切得更细也会丢失完整业务情景

查询：“希望做销售机器人失败会话分析、提示词回归测试和人工接管流程”。

种子 **agent开发工程师-集团公司 15-35k领导面谈**（`b67546a596085f430nx62ti0FFRR`），原文涉及工具漏参、动作调用错误、超阶段回复，以及销售跟进、评测和异常转人工。

A 排 **1**、C 排 **11**、BM25 排 **2**。C Top-1 是“AI Agent 产品运营（社交拟人方向）”，命中 Badcase、人设脚本、Prompt 调优；BM25 Top-1 是有配送客服 AI 中台、工具调用与人工转接场景的“Agent 开发工程师（AI 智能体方向）”。

为什么值得注意？如果“失败分析、业务工具、人工接管”原本分散在几个条目，分块后取单个最高分，就可能失去它们构成**同一个工程任务**的关系。这是可检验的解释，不是已经证实的唯一根因；下一步应回看命中块与跨条目内容。

### 例 4：`rag-01`——种子掉到第49名，系统却仍可能找到真正相关的岗位

查询：“找负责企业知识接入、检索策略和回答生成全流程建设的工程岗位”。

唯一种子是 **AI解决方案专家（RAG方向）**（`e9181ab8456b19230nR_2NS_FVtY`）：A 排 **15**、C 排 **49**、BM25 排 **6**。

但 **C 和 BM25 的 Top-1 是同一条**：**知识库开发工程师（RAG方向）**（`1565396211cbed010nNy39W_GFJS`）。岗位原文写有“企业级知识库平台的架构设计与核心开发，覆盖知识接入→解析→索引→检索→服务全链路”，并涉及混合检索、Rerank、查询改写、引用溯源与可信回答。

这正是单正例评测的核心陷阱：**指标只看指定种子，用户却关心是否找到了合适岗位。** 两个系统共同找到了高度贴合的问题答案，但这条未被标注为正例。原排名应保持不变，需要改变的是人工判断的覆盖范围。

### 例 5：`data-product-02`——不同岗位 ID 可以都与问题相关

查询：“做标注平台迭代与提效指标体系的产品岗位，代码能力是加分而非硬性门槛”。

种子 **B端ai产品经理（PE、agent提效）-双休**（`2c3d80d403aa42fa0nx53dW1F1dS`）：A/C 均排 **1**、BM25 排 **2**。BM25 Top-1 是另一条 **B端 AI产品经理/运营**（`1f80b879aecd46360nN60tu0FFNU`）。

两条都把“具备一定的代码能力，熟悉 Python、JavaScript、SQL 等”写作**加分项**。经过 NFKC 与去空白的字符序列比较，描述约 **99.01%** 相似。这只是文本相似比例，既不等于模型分数，也不证明两个招聘 ID 可以业务去重。

它说明：如果用户接受这两条，A/C“第一”和 BM25“第二”其实不一定存在用户可感知的品质差距。实验要让标注理解**条件的强制性**，而不能用未标注的近重复岗位制造胜负。

## 五、怎样从这些结果继续得到可靠认识？

**第一步，区分硬条件与语义相关性。** 例如 `embodied-01` 硬筛选后只有 **3 条 eligible** 岗位，`platform-01` 只有 **15 条**。此类问题即使 Top-10 找到正例，也不能独立证明复杂语义能力。

**第二步，把“未标注”保持为未知。** 对多个系统前排候选进行盲化人工审阅，补充多个正例、近重复、否定条件与必备/优先条件证据。不要为了指标好看改写已有标签或排名。

**第三步，用相同文档表示做更清楚的对照。** 本轮 BM25 全文 vs Embedding 分块混杂了算法与文档处理，未来若要判断算法本身效果，应让对照共享可比较的输入表示。

**第四步，引入独立于岗位原文撰写的用户问法。** 现有 30 问题更像技术能力清单式的种子测试集，不能代替自然求职者写出的含糊或跨领域表达。

**第五步，在人工审阅完成后再进行固定候选的 Rerank。** 它解决前排排序，不负责补回没进候选池的岗位。Test 不能拿来循环挑方案。

拥有服务器快照时，可以不调用模型、不新增费用地核查 Top-5 原文和匹配块：

```bash
python scripts/explain_recall_cases.py
```

原始运行日志、凭据和缓存不公开。与统计报告有关的精确事实仍以 [第一轮汇总](recall-pilot-2026-10-25.md) 和原实验快照为依据。

**最后的概念区别**：指定正例的排名，是可观察的检索输出；候选是否满足用户需求，是需要证据与标注的判断。两者不能互相代替。
