# 公司与岗位工作内容分析（写入 jobs.csv.analysis）

投递前只回答两个问题：

1. **这家公司在做什么生意？** 它向谁提供什么产品或服务？AI 在业务中扮演什么角色？
2. **我进去之后具体做什么项目？** 为哪条业务线、接什么系统、交付什么东西？

这是“理解岗位”的分析，不是“人岗匹配评分”。

## 输入

- 必填：`job_id`
- 读取：`data/jobs.csv` 中该行的 `title/company/location/description/url/keywords/status`
- 读取：`data/company/company_info.csv` 中 `职位ID == job_id` 的公司介绍和业务信息；同一职位可能重复，先按 `职位ID` 去重、合并，取最长介绍
- 读取：`apply-flow/resume_skills_projects.md` 作为技术语境参考，帮助你理解岗位术语和可能的工作方式

## 核心要求：落到“具体项目”，不是复述 JD

“岗位具体做什么”必须回答到项目这一层。只写“负责 Agent 架构设计、RAG 体系建设、工具调用开发”属于 JD 复述，**不合格**。

每条项目按这个句式写：

```text
给 <哪条业务线/哪个产品/哪类客户> 做 <什么系统或能力>，<输入是什么、接什么系统>，交付 <什么东西>
```

- 写 **2–3 条**项目假设，覆盖 JD 里最重要的职责，不要罗列全部要求
- 项目必须挂到公司真实的业务线、产品名或客户类型上（如“保利云和+”“房小宝”“Amazon 广告后台”“轨交规章制度库”）
- 技术词（RAG、Agent、MCP、Milvus）只能作为**实现手段**出现在项目里，不能单独成句
- 每条的确定性要标出来：JD 明写的直接写；由公司业务推断的写“推测”；无法判断的写“待确认”

推断依据的优先级：

1. JD 明写的业务场景、系统、客户
2. 公司业务线、产品、客户类型（`company_info.csv`）
3. 同类企业的常规做法 —— 仅在前两者不足时使用，且必须标“推测”

### 公司信息缺失时

- 明确写“`company_info.csv` 无该公司介绍，业务无法确认”
- 项目只能按 JD 里出现的场景推断，并标注“按 JD 推断”
- 匿名岗位（“某大型互联网公司”等）不得给出具体产品名，只写到业务类型

### 反面例子

- ❌ “负责 Agent 系统架构、任务规划、工具调用、RAG 建设、性能调优。”（JD 复述，看不出做什么）
- ❌ “为公司提供企业级 AI 解决方案。”（没有业务线和交付物）
- ❌ “搭建智能客服系统。”（没有说明服务哪条业务、接什么数据）

### 正面例子（保利和润）

```text
公司在做什么：保利和润是央企保利发展控股旗下的房地产营销平台，做新房代理（保利和润）、新房分销（房小宝）和存量房租售（保利爱家），代运营“保利云和+”线上房产平台，覆盖 100 多座城市、700 多个在代项目；AI 主要用于营销转化和销售效率。岗位具体做什么：JD 明确要做多智能体协作、RAG 知识智能体和营销决策引擎，结合业务推测落地三类项目：①给“保利云和+”做购房咨询智能体，接入楼盘、户型、价格与政策知识库，承接初步答疑和推荐；②给房小宝分销与电销团队做线索分层和话术推荐，把用户画像、购买意向评分接到销售 SOP；③营销内容生产与审核，批量生成项目推广文案并做合规校验。交付物大概率是智能体服务、决策引擎 API 与评测集；先做哪条业务线待确认。
```

## 分析重点

### 1. 公司在做什么

- 主营业务、核心产品/内容平台、服务对象，尽量写到具体产品名或业务线；
- AI 在这家公司业务中的位置：主营产品、降本增效工具，还是尚未成为核心；
- 只用公司介绍和业务描述，不用工商信息、注册资本、融资历史、公司规模替代业务分析。

### 2. 岗位具体做什么

- 服务于哪条业务线、哪类客户或内部流程；
- 2–3 条具体项目（按上面的句式）；
- 技术重心：从职责、硬性要求、加分项判断哪部分是核心，哪部分只是附带；
- 交付成果：模型能力、内容生成能力、推理服务、业务系统、内部工具等；
- 无法确认的写“推测/待确认”，不要编造客户名、项目名、数字。

## 输出

在聊天里直接给出每条岗位的 `analysis` 全文，不要做摘要表、不要压缩成短要点（除非用户明确要求摘要）。

写入 `jobs.csv.analysis` 的结论使用两段式，建议 300–450 字，最多 500 字：

```text
公司在做什么：<主营业务、具体产品/业务线、服务对象、AI 的作用>。
岗位具体做什么：<2–3 条具体项目，每条写清业务线→系统→交付物；未确认的标推测/待确认>。
```

### 不要写进结论

- 工商信息、注册资本、融资历史、公司规模等常规信息；
- 技能匹配评分、硬门槛汇总、投递建议、面试准备；
- 只有技术标签、看不出公司业务和具体产出的短句；
- JD 职责的逐条复述。

## 自检清单（每条写完后过一遍）

- [ ] 第二段是否有 2–3 条“业务线/产品 → 系统/能力 → 交付物”的具体项目
- [ ] 项目是否挂在公司真实业务或 JD 明确场景上，而不是通用套话
- [ ] 技术名词是否只作为实现手段出现
- [ ] 推断部分是否标了“推测/待确认”
- [ ] 公司介绍缺失/匿名岗位是否已注明
- [ ] 重复发布的同公司同标题岗位是否在结论里互相注明
- [ ] 状态为“职位已关闭”的是否已注明
- [ ] 是否有 JD 复述、套话、编造的客户名或数字

## 写回 jobs.csv

不要手工编辑 CSV（description 含换行/引号）。此脚本只更新指定岗位的 `analysis`；采集 CSV 合并不得覆盖它。使用：

```bash
python3 apply-flow/set_analysis.py --job-id <job_id> --analysis '<结论>'
```

写入后读回该行确认 `analysis` 已更新，并把结论原文完整告诉用户。

## 确认后沟通投递

分析只负责写入结论，**不点击、不发送**。

等用户明确确认可以投递后，才运行：

```bash
node apply-flow/apply_job.mjs --job-id <job_id> --confirm
```

要求：

- 一次只处理一个 `job_id`
- 必须显式 `--confirm`
- 不批量、不循环、不跳过人工确认
- 脚本会检查 `analysis` 非空；按钮为“继续沟通”时不会重复点击
- 点击后记录聊天页内容和发送结果
- 发送成功，或按钮为“继续沟通”（已有沟通记录）时，`apply_job.mjs` 会把 `jobs.csv` 中该岗位的 `status` 自动改为 `已投递`，无需手动改状态
