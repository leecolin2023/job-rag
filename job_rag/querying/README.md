# 确定性查询：什么时候不应该使用向量检索？

如果用户问“广州有多少份 JD 在文字上提到 vLLM”，问题的关键是**完整、可复查的计数**，而不是找出最相关的前 20 条。如果使用有 Top-K 截断的向量或 BM25 结果来算总数，就会把“找到了多少”误写成“全库一共有多少”。因此 `querying/` 专门提供确定性的字段过滤、字面扫描、完整岗位读取和状态统计，不依赖模型或检索排名。

## 一、先理解公共硬条件

`filters.py` 定义 `StructuredFilters` 和 `matches()`，供查询层与[检索层](../retrieval/README.md)共用。条件包括城市、地区、薪资范围/计薪周期、求职者经验、学历、实习类型、字面必含技能和招聘状态。

例如一个岗位薪资为 `10-25K`，用户要求“月薪下限至少 20K”：按 `lower_bound` 规则不符合；若用户要求“薪资区间覆盖 20K”，按 `overlap` 则可能符合。工资未知或计薪周期不匹配时不能猜成符合。`skills=["vLLM"]` 只要求字面出现，不意味着 vLLM 是**必备任职要求**。

## 二、全库字面查询的执行过程

`catalog.py::catalog_query()` 从数据库有序读取岗位，先按字段和招聘状态筛选，再对指定 `title`/`description` 做词法匹配。多个词支持 AND/OR、大小写选项及两种匹配模式：`substring` 检查原样子串；`token` 要求词前后不紧邻 Unicode 字母/数字/下划线，但**不是中文分词或语义同义词扩展**。

~~~json
{
  "terms": ["vLLM"],
  "fields": ["title", "description"],
  "match_mode": "token",
  "filters": {"city": "广州"},
  "count_only": true
}
~~~

`matched_jobs` 是**当前语料和指定词法条件下的完整匹配数**；`eligible_jobs` 是词法筛选前的候选范围。空 `terms` 可枚举符合结构条件的全部岗位。字面命中数不等于具备这项能力的岗位数，也不能直接代表整个招聘市场。

## 三、为什么分页必须绑定快照？

如果先读取前 100 条岗位，过程中又导入新版本，继续按 offset 翻页可能出现遗漏或重复。`catalog.py` 通过 `corpus_id` 为当前语料生成指纹，再将语料和查询条件合成 `snapshot_id`。后续页必须传回相同条件、snapshot_id 与 next_offset；任何内容、状态或条件变化触发冲突，由 API 返回 HTTP 409，要求重新枚举。

这是一种**数据变化即中止的乐观校验**，并没有保存一个永久可查询的历史快照。`batch_jobs()` 每次最多读取 20 份完整 JD，可带 `corpus_id` 和岗位版本，避免全文读取和前面统计基于两批不同数据。

## 四、岗位详情和统计从哪里来？

`jobs.py` 提供 `job_detail()` 与 `knowledge_base_stats()`，前者关联全文、版本和状态历史，后者统计岗位数、城市、状态和索引任务。公共输出在 `storage/serialization.py` 统一组织，查询模块不再为了使用输出格式而依赖检索模块。

## 五、当前还做不到什么？

如果问题变成“广州多少岗位**真正要求**生产部署经验”，字面计数不足以判断“要求”还是“优先”“公司介绍”。当前工具能全量枚举和按批拿原文，但尚无内建的可恢复逐岗位语义判定、判定持久化与程序汇总引擎。Agent 必须明确处理范围、未处理量和证据，不能拿 Top-K 或字面数代替语义总体。
