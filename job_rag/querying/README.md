# 怎样从 JD 知识库得到可核对的查询结果？——结构化过滤、全库计数与语义判断

用户可能连续提出三种问题：

> “给我推荐几个负责 vLLM 部署的岗位。”
>
> “广州的 JD 中，有多少岗位**提到了** vLLM？”
>
> “广州到底有多少岗位**要求候选人具备生产环境模型部署能力**？”

三者都在使用招聘数据，却不能用同一个“搜索 Top-20”的结果来回答。第一题要发现并排序**值得进一步阅读的候选**；第二题要在明确范围内**逐条判定字面是否出现**；第三题不仅要遍历完整范围，还得读 JD、判断招聘语义，再按岗位去重汇总。

这就是本模块和[候选检索 Retrieval](../retrieval/README.md)的分工：Retrieval 尽量找到相关岗位，允许排名、近似和截断；Querying 更关注**确定性条件、完整枚举、原文读取和可复核的数据口径**。但“精确”始终相对于一个**已经明确定义的规则**，不代表代码天然理解了全部招聘含义。

## 一、为什么不能直接用检索结果回答“总共有多少”？

假设一个知识库有 600 个岗位。使用 BM25 或向量检索找“vLLM 部署”，结果列表展示前 20 条。即使前 20 条都真的相关，也无法证明第 21～600 条里不存在其他相关岗位。

这里涉及两种不同目标：

| 查询目标 | 典型做法 | 结果的意义 |
|---|---|---|
| **找到一些相关候选** | 相关性排序、Top-K、进一步读证据 | 优先阅读的名单；可能遗漏 |
| **统计满足某个规则的全部岗位** | 明确范围、逐条应用同一个规则、按岗位计数 | 对该规则和范围的完整计数 |
| **统计满足某个语义要求的全部岗位** | 完整枚举、逐份阅读 JD、统一语义判定、处理不确定性并汇总 | 在判定覆盖充分时的语义统计 |

第二、第三种目标都要求先知道**全集是什么**，不能由 Top-K 反推。更容易被忽略的是：即使扫描了全部岗位，也可能只完成第二种。比如检查“是否出现 vLLM”很精确，却不能自动回答“vLLM 是否必备”。

所以在系统设计上，应该先选择**操作的对象与判定规则**，再选择检索或完整遍历，而不是先调用一个搜索工具，再根据返回条数临时解释为总量。

## 二、精确查询首先要确定什么？不是 SQL，而是统计口径

一般的数据查询至少要明确三个问题：**查询范围是什么、满足条件是什么意思、按什么对象计数**。

以“广州、月薪 20K 以上的 vLLM 岗位有多少”为例：

**范围**要明确：是已收集的全部岗位，还是只统计已确认在招的？历史关闭岗位是否包含？采集时间是否允许较早？Job-RAG 默认包含 `active`（已确认在招）及 `unknown`（未核验），排除已关闭和疑似失效。`unknown` 不能写成“正在招聘”；若用户要求“确定在招”，应使用 `active_only=true`，但这又可能漏掉尚未核实的真实在招岗位。

**条件**要明确：“20K 以上”是**岗位公布的月薪下限至少 20K**，还是**岗位薪资区间覆盖 20K**？同一个 `10–25K` 职位，在第一种口径下不合格，在第二种口径下合格。薪资还必须区分月、天、小时；“面议”或无法解析的数字，不能因为可能满足就直接加入确定性结果。

**计数对象**也要明确：用户问的是*岗位数*，不是“vLLM 在 JD 中出现了多少次”，也不是 Chunk 数。当前记录按 `source:job_id` 区分；同一家公司发布的两条不同 ID、或者文字极相似的两个岗位，在没有额外业务去重规则时仍分别计数。

这三个问题中的任意一个没有说清，“准确统计”就会成为一个没有确定含义的数字。**精确查询的前提是先定义集合，而不是先得到数字。**

### 为什么确定性过滤要和语义判断分开？

城市、薪资范围、学历、求职者经验等，在字段已被成功标准化时，可以按明确规则过滤。Job-RAG 的 `StructuredFilters` 描述这些条件，`matches()` 执行它们。

但这些字段看似简单，仍存在需要解释的业务口径：

- `salary_mode=lower_bound`：岗位薪资**下限**至少达到指定下限；`overlap`：薪资区间与指定范围存在交集。它们不能混用。
- `experience_years`：表示**求职者具备的工作年限**能否达到岗位最低年限，非“岗位写了几年经验”的精确数值搜索。岗位最低年限缺失时，此筛选不会猜测符合。
- `education`：当前按标准化后的学历文本**完全相等**，没有实现“硕士自动满足本科及以上”等完整学历层级推理。
- `skills=["vLLM"]`：只要求标题或描述中**字面存在**该技能，多个技能是 AND 约束；它**不保证**该技能属于岗位必备要求，也不接受同义表达自动放宽。

这解释了为什么[检索链路](../retrieval/README.md)同样复用这套过滤规则：硬条件不能因为换成向量相似度就变了。相反，用户的弱偏好不宜错误放进 `skills`，否则相关岗位会在检索之前被排除。

## 三、怎样进行一次真正的全库字面查询？

假设用户明确问：“在当前收集的广州岗位中，多少份 JD 的标题或描述出现过 `vLLM` 这个词？”这时已经有了一个**可编程判定的规则**，根本不需要 LLM 判断句子是不是相关。

通用做法是：读取整个目标岗位集合，逐条应用城市和招聘状态等结构条件；再对留下的记录执行**相同的字面匹配规则**，最后按岗位 ID 统计。所有岗位都检查过，才能把结果称为该规则下的完整数量。

Job-RAG 提供 `catalog_query()`，例如：

~~~json
{
  "terms": ["vLLM"],
  "fields": ["title", "description"],
  "operator": "and",
  "case_sensitive": false,
  "match_mode": "token",
  "filters": {"city": "广州"},
  "count_only": true
}
~~~

这个请求会读取当前所有岗位记录，并在 Python 中按规则判断；它不依赖 Embedding、BM25 或 `chunks` 索引是否建好。`eligible_jobs` 是结构与状态过滤后的岗位数，`matched_jobs` 是进一步符合字面规则的岗位数；`count_complete=true` 表示**本次遍历已覆盖定义的全集与字面规则**，不是经过语义核验的招聘需求总量。

这里的“字面”还需要把匹配方式讲清楚。

**`substring` 模式**检查一个字符串是否包含另一个字符串；它可能把更长词里的局部字符串也算作命中。**`token` 模式**要求匹配词两侧不是 Unicode 的单词字符（字母、数字、下划线等），并保留词中标点本身，例如 `C++`；但这并不是专业的中文分词。由于中文汉字本身也属于 Unicode 单词字符，`vLLM开发` 这样的紧邻写法就可能不满足 `token` 的右侧边界。选择 `token` 并不是“语义更准”，而是改变了字面判定口径。

`fields` 只允许标题、描述；每个查询词可以出现在任何一个指定字段中。如果输入多个词，`operator=and` 表示所有词都必须各自在所选字段中找到（可以分散在不同字段），`or` 表示至少一个命中。`terms=[]` 不施加字面词约束，等于**枚举所有通过结构与状态条件的岗位**。

因此用户如果说“广州有多少岗位**必须**掌握 vLLM”，仅用 `terms=["vLLM"]` 得到的 `matched_jobs` 依然不是答案：一个公司介绍中出现 vLLM 的岗位、一个“vLLM 优先”岗位同样可能被包含。**扫描范围完整，不代表语义条件已被完整判断。**

### 为什么现在不用数据库全文索引？

当前语料只有数百条，`catalog_query()` 通过一次有序读取获取所有岗位，再在应用层判定文字和筛选条件。这种实现容易检查、规则统一，且无须等待 Chunk/向量索引同步。

代价是每次查询都要读取、遍历当前语料，数据越大、并发越高，成本越明显。将来可以考虑数据库全文索引或专用检索引擎，但必须保证查询语义与计数口径一致，不能因为换了索引就悄悄改变 `substring` 或 `token` 的含义。

## 四、为什么做了全量查询，还需要快照、分页与版本？

“全量”描述的是**算法要覆盖的范围**，不表示可以把数百份完整 JD 一次塞进 Agent 的上下文。为了可控地阅读或继续处理，结果通常需要分页。

但分页会遇到数据变化。例如第一次读出第 1–20 条，第二次继续从第 21 条读取；中间如果插入一条排序靠前的新岗位，原来的第 20 条可能被重复返回，另一个岗位则可能被跳过。单纯把所有页面拼接起来，未必是同一个数据时刻的结果。

因此 Job-RAG 使用两类不同的内容指纹：

- `corpus_id`：根据当前有序岗位数据的序列化内容计算，表示**数据版本**。
- `snapshot_id`：把当前语料指纹与字面查询条件一起计算，表示**这次查询范围和规则**。

第一次分页获取 `snapshot_id` 与 `next_offset`；后续页带上原查询条件、`snapshot_id` 和返回的偏移继续。如果数据或查询条件已变化，接口会拒绝继续，HTTP 层返回 409，要求从第一页重新统计。

这叫**乐观一致性校验**：系统允许正常修改 JD，只是在下一次请求发现前后条件不一致就停止。它**没有保留一份永久、可重复读取的历史数据库快照**，也不能保证写入十分频繁时一定能顺利读完整个范围。若未来要做长期、可审计的全库统计，可能需要持久化某次冻结的语料范围与判定版本。

`count_only=true` 时可以只拿完整字面计数而不返回名单；要逐条做后续语义判断，则通常要分页枚举。分页大小 `page_size` 最多 100，`offset` 后续必须与 `snapshot_id` 配对。**“可以按页阅读完整范围”与“某一页本身代表完整结果”是两件事。**

## 五、什么时候必须回到完整 JD，而不能依赖关键词或 Chunk？

用户问“哪几个岗位适合我”，先检索候选后按需读全文通常更节省；用户指定两个岗位要比较，则直接拿指定 JD 即可；而用户问“广州有多少岗位真正要求**生产环境模型部署能力**”，需要一种更严谨的过程。

为什么字面匹配不够？因为原文可能写：

~~~text
A：必须独立完成生产推理服务部署。
B：具有模型部署经验者优先。
C：公司已在生产环境部署模型；该岗位负责售前销售。
D：负责模型上线、监控和故障恢复。
~~~

若直接检索“生产部署”，可能遗漏语义上符合的 D，却把 B、C 混进“必备部署能力”的计数。即便使用 Chunking 的 `required/preferred/mixed` 标签，也不能推断 Chunk 里每一项技术都具有相同强制程度。

所以，**全库语义统计**除了定义数据与状态范围，还必须定义业务判断口径。例如：工作职责包含部署是否算“岗位要求能力”，还是必须有任职条件明确写出“独立部署经验”？这是业务定义，不是模型自动能替你决定的真值。

一般可以采用如下流程：

~~~text
明确“符合”的语义口径与统计范围
    ↓
完整枚举范围内所有岗位（必要时 terms=[]）
    ↓
分批读取完整 JD，不只阅读命中的 Chunk
    ↓
按统一口径逐岗判断，保存结论、原文证据与无法判断情况
    ↓
汇总符合 / 不符合 / 无法判断 / 未处理
    ↓
确认范围、覆盖完整性、数据版本及结果可追溯，再报告数量
~~~

Job-RAG 已具备其中的**完整枚举**与**批量取全文**能力。`batch_jobs()` 每次按 `source + job_id` 读取 1–20 个指定岗位，可携带 `version` 和 `corpus_id`；岗位不存在、要求的版本变化时逐项报告错误，语料变动时也能拒绝将新数据混入旧范围。`job_detail()` 可读取指定岗位的当前原文、历史版本与招聘状态事件，`knowledge_base_stats()` 提供规模、状态及索引就绪信息。

**尚未实现**的是自动、可恢复的全库语义判定任务、逐岗位证据/判定持久化及最终汇总引擎。因此目前不能仅凭一轮 Agent 阅读或一个 `matched_jobs` 字面数字宣称“全库真正要求部署能力的岗位有 N 个”。在未完成全部判定时，应该明示已处理数、未处理数、符合数、不符合数及无法判断数；用“未判断”冒充“不符合”，会系统性低估真实数量。

## 六、一次完整的 JD 数据查询应该怎样选择工具？

把前三种任务放在一起，就能知道什么时候使用哪条路径：

| 用户任务 | 合适的起点 | 结果性质 |
|---|---|---|
| 找几个真正负责 RAG 的岗位 | [Retrieval](../retrieval/README.md)：相关性召回，读证据 | Top-K 候选，不承诺找全 |
| 统计 JD 中**字面出现** vLLM 的岗位数 | `query_job_catalog`：完整字面计数 | 定义规则内的完整岗位数 |
| 按指定 ID 比较两份 JD | `get_job` / `get_jobs_batch` | 原文与当前版本，免去无关召回 |
| 统计**真正必须具备** vLLM 部署经验的岗位数 | 完整枚举 + 全文语义判定 + 汇总 | 当前只具备前两项基础能力，不能直接报精确总数 |
| 查看索引是否就绪、岗位状态有多少 | `get_knowledge_base_stats` | 状态与索引计数，不是语义相关岗位数 |

这个分工还有一个容易误用的地方：**字面查询不要求索引就绪，但 Retrieval 要求岗位索引版本匹配**。因此同一时刻，Catalog 可能枚举到某个尚未重新索引的岗位，而搜索结果里没有它。这不是两个工具“互相矛盾”，而是一个面向**当前原始记录**，另一个面向**已经建立、且版本匹配的检索索引**。若要对结果进行比较，应先检查这种范围差异。

对外调用时，`query_job_catalog` 接收一个包含 `terms/fields/operator/match_mode` 和嵌套 `filters` 的请求；`get_jobs_batch` 接收 `jobs` 数组和可选的 `corpus_id`。共享过滤的底层实现位于 `filters.py`；全库遍历与版本守卫在 `catalog.py`；详情及统计在 `jobs.py`。函数名是在上面的方法与边界讲清之后，才需要查找的实现入口。

## 七、怎样验证“精确查询”确实可靠？

“精确”不意味着只要 SQL 能运行就万无一失。需要检验三个层次。

**规则结果是否符合业务定义。** 用 `10–25K` 测试“下限 20K”与“区间覆盖 20K”会不会得到不同结果；用 `vLLM`、`vLLM开发`、`C++`、中文词分别测试子串与单词边界；用“优先”“不要求”“公司介绍”检查是否有人把字面命中误解成必备条件。规则能复现不等于规则就是用户想要的。

**全集是否真的覆盖并且不重算。** 在没有 Embedding 或索引未就绪时，Catalog 仍应能按所有原始岗位计数；空描述的岗位如果标题命中，也应该计入；不同 `job_id` 不应因文本相似被偷偷合并。`matched_jobs` 统计的是岗位，不是词项出现次数。

**分页和全文判断是否属于同一版数据。** 可以在两次分页之间插入岗位、修改状态或内容，确认 `snapshot_id` 失效；在批量取全文前改变岗位版本，确认 `version` 或 `corpus_id` 的防护有效。若业务必须连续完成一份不受写入影响的分析，就需要比当前乐观指纹更强的持久快照机制。

理解 Querying 后，应当能够回答：**要数清楚什么，首先定义什么；为什么“扫描了全部 JD”仍可能无法回答语义数量；以及什么时候应当停止 Top-K 搜索、改用完整枚举与全文核验**。这才是把知识库从“找几段相关文字”推进到“产出可核对的业务结论”的关键。
