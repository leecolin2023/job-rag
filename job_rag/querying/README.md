# 为什么 Job-RAG 不能用搜索结果来回答“总共有多少”？

用户问“广州有哪些 vLLM 岗位”和“广州有多少岗位提到了 vLLM”，看似只差一个字，系统的正确工作方式却不同。前者允许先返回一批值得阅读的候选；后者要求在**事先定义的样本范围内不漏算**。如果用语义检索 Top-20 来回答后一个问题，即使每条都很相关，仍不能证明剩余的几百条里没有匹配岗位。

`querying/` 因此专门处理确定性的数据访问：**先说清范围与匹配规则，再穷尽扫描或按指定 ID 取全文**。它不依赖 Embedding、Chat、BM25 或索引是否就绪。

## 一、“符合条件”本身为什么必须有清楚口径？

举例：招聘写“10–25K”。用户说“20K 以上”，究竟是岗位**薪资下限**不低于 20K，还是招聘区间**包含** 20K？两个口径会得到不同的岗位集合。如果把它交给语义相似度，模型可能每次按不同理解筛选，结果难以复核。

`filters.py` 把城市、区、薪资上下限与周期、求职者年限、学历、招聘状态等约束组织为 `StructuredFilters`，并由 `matches()` 执行相同规则。`salary_mode=lower_bound` 强调岗位下限；`overlap` 用于区间覆盖。无法确定薪资或计薪周期不相符时，不能默认为符合。

这里还有一个重要区别：`skills=["vLLM"]` 只表示标题或正文**字面出现** vLLM，不表示它是任职必备。精确的计算不等于完整的招聘语义理解。

## 二、为什么先完整扫描原文，而不是借助向量？

若问题只是“哪些岗位明确写出 vLLM 这个词”，不需要通过 Embedding 推断“推理框架”是否与 vLLM 同义。加入 SGLang、TensorRT-LLM 等扩展词反而会**改变用户原本要统计的集合**。

`catalog.py::catalog_query()` 在当前语料内读取所有岗位，先做结构字段与招聘状态过滤，再在标题或描述中检查原文词项。用户可以规定大小写、AND/OR、`substring` 或 `token` 边界。例如：

~~~json
{
  "terms": ["vLLM"],
  "fields": ["title", "description"],
  "match_mode": "token",
  "filters": {"city": "广州"},
  "count_only": true
}
~~~

返回的 `eligible_jobs` 说明文字匹配前有多少岗位，`matched_jobs` 说明按约定字面规则最终有多少匹配；`count_complete=true` 代表在**当前数据与规则**下完成了全量字面计数。

注意 `token` 依据 Unicode 单词边界，而不是专业中文分词。这是明确、可重复的匹配规则，并不等于懂“必须掌握 vLLM”的业务含义。

## 三、为什么扫描全部岗位却还要分页和快照？

一次返回几百份 JD 会占用大量上下文，所以目录支持按 `page_size/offset` 分页。假设读完前 100 条后，有人新导入一个岗位；再读第 101 条，排序位置可能改变，同一岗位可能重复或漏掉。

系统并未保存一份永久不变的历史表，而是计算两个指纹：`corpus_id` 代表当前已读取的语料状态；`snapshot_id` 还绑定筛选与字面匹配条件。继续翻页必须带回原条件、`snapshot_id` 和 `next_offset`。数据或条件变化就返回冲突，要求从第一页开始。

这是**乐观一致性保护**：它不能阻止写入，只能识别“不能继续把前后两次的结果当成同一次统计”。

## 四、为什么还需要批量取 JD？

假设用户问“广州有多少岗位真正要求过生产级模型部署？”精确字面扫描可以找到“部署”这个词，却无法区分“有经验优先”“熟悉概念”“公司已经完成部署”。要做语义统计，必须先定义判断标准，再读**所有候选的完整原文**进行逐条判断。

`batch_jobs()` 一次按来源 ID 取 1–20 份 JD，可带岗位版本和 `corpus_id`；发现某岗位版本变了、数据变了，就拒绝把新原文混进旧统计范围。`jobs.py` 则提供指定岗位的原文、状态历史及数据库统计。这些能力为后续语义判断提供完整输入。

**但当前还没有自动化的全库逐条语义判定、判定结果持久化和程序汇总引擎。** 因此不能把 `matched_jobs` 说成“真实要求部署能力的岗位数”，也不能把部分 Agent 阅读结果估算成全库精确数量。

## 五、什么情况下转去检索模块？

问题要找“最值得看的几个岗位”，应该使用[retrieval](../retrieval/README.md)，允许有排名与截断；问题要数“原文中确切出现几次/多少岗位”，应该使用这里的完整字面扫描；问题要统计**招聘语义条件**，必须在完整枚举基础上增加可核验的判断与汇总。

这就是将“字面数据事实”“检索相关性”“招聘语义结论”分开的根本原因。代码入口在 `filters.py`、`catalog.py`、`jobs.py`；对外由[interfaces](../interfaces/README.md)提供 API/MCP。
