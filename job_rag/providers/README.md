# 模型服务为什么要单独成层？——让检索依赖能力，而不是依赖某家 API

Job-RAG 可以在没有大模型密钥时查岗位，也可以在配置 Embedding 后进行混合检索。这并不是“可有可无地加一个模型”，而是把两种不同责任拆开：**数据库和检索规则决定怎样寻找与筛选，外部模型客户端负责把文本变成向量或把证据组织成答案**。

如果业务模块直接拼接百炼 HTTP 地址、在多处解析返回 JSON，将来换模型时就必须同时修改索引、搜索和网页回答逻辑。`providers/client.py` 将具体供应商请求格式集中起来，使上层关注调用输入输出，而不是每个 HTTP 字段。

## 一、Embedding 到底在哪两个阶段被调用？

岗位导入并完成分块后，[索引 Worker](../indexing/README.md)对 `Document.text` 调用 `embed(text_type="document")`，把每个块映射为固定维度的向量。用户检索时，[retrieval](../retrieval/README.md)对提问调用 `embed(text_type="query")`，再计算问题与岗位向量的余弦距离。

两边必须使用兼容的模型、维度及输入表示。若只升级查询模型、不重建文档索引，余弦距离就可能失去预期意义；因此索引签名把模型和分块配置纳入版本。

客户端支持 OpenAI-compatible `/embeddings` 和百炼原生 Embedding 请求。原生格式会区分 query/document；结果会校验条数、序号、维度和数值，避免把返回顺序错位的向量错误关联到别的 JD。未配置模型时 `embed()` 返回等量的空向量标记，系统仍可使用 BM25。

## 二、为什么 Chat 不能代替 Embedding？

Embedding 的输出是数值向量，用于**寻找**与问题接近的候选；Chat 的输出是自然语言，用于**解释**检索出的证据。即使 Chat 模型很强，如果不给它可靠候选和原文，它也可能推荐不存在或不满足条件的岗位。

`chat()` 接收问题及已检索的来源、证据、版本/状态信息，发送到 Chat Completions；它不自行浏览招聘网站，也不从零建立数据库。调用方要核查编号引用，并在生成完成后复核岗位状态。引用编号形式正确，仍不代表每句话都由证据支持。

外部 DeepSeek/OpenCode Agent 又是第三个概念：Agent 通过 MCP **选择工具并阅读数据**，所用 DeepSeek 并非这里的 Embedding 服务。

## 三、为什么同一个模型故障会有不同后果？

假设今天 Embedding API 超时：

- 如果 Worker 正在为新岗位建索引，不能伪装成功，应留下可重试的索引任务；
- 如果用户正查询岗位，检索可以回退为 BM25，并提示语义服务不可用；
- 如果 Chat 生成失败，回答层可以返回原始候选列表而非虚构解释。

这些降级与重试规则属于**各自的调用场景**，不能都塞进模型客户端里统一处理，否则底层 HTTP 类就会被迫承担招聘业务策略。

## 四、在线模型和离线实验为什么分开？

`job_rag/experiments/bailian.py` 使用单独的模型客户端、缓存、请求日志和费用保护，用于控制变量实验，不自动写线上索引。实验里验证了 Rerank API，不等于生产 `client.py` 已经提供在线 Reranker。

配置从顶层 `Settings` 读取，不在源码中写 API Key。远程调用会把招聘 Chunk 或用户问题发送给供应商，应检查数据合规与费用预算。最后记住这层的边界：**它把模型能力包装为稳定调用，而不决定业务事实、检索策略或最终招聘结论**。
