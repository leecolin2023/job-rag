# Job-RAG 为什么需要 MCP？如何把岗位知识库变成 Agent 可使用的工具？

Job-RAG 的目标不是再开发一个聊天窗口，而是让求职者、岗位研究者或课程设计者能够基于**有来源的招聘 JD**，寻找岗位、筛选条件、比较要求，以及分析某类技术在招聘市场中的出现情况。

假设用户提出三个问题：

1. **“广州有哪些真正负责 RAG 系统建设的岗位？”**
2. **“广州有多少个岗位在职责或任职要求中写到了 RAG？”**
3. **“这些 RAG 岗位通常还要求掌握哪些技术？分别有多少个岗位要求？”**

这三句话都在查询同一批 JD，但需要的处理方式不同：第一句是**寻找可能相关的岗位**；第二句是**对明确规则进行完整计数**；第三句则需要**找到完整研究对象，再逐份理解要求并汇总**。

本文从这些问题出发，解释为什么要提供 MCP、它如何运作、Job-RAG 应向 Agent 提供哪些工具，以及每个工具应承担什么责任。

> **文档性质：目标设计与学习说明。** 以下是从 Job-RAG 的长期定位推导出的接口方案，不是当前代码清单或已上线功能声明。本文不讨论 API、CLI、网页等其他对外入口的维护，也不提供与现有代码绑定的启动命令。

## 一、已经有岗位数据库，为什么还需要 MCP？

### 1. 大模型不能直接从“知道有数据库”变成“能够查询数据库”

用户问“有哪些 RAG 岗位”，模型可以理解中文、分析 JD，但它不会因此自动拥有数据库连接，也不知道数据库支持哪些查询、参数应该怎样填写。

如果直接把全部岗位文本贴进对话，又会遇到新的困难：

- 岗位越来越多，全部放入上下文成本高，还可能被截断。
- 用户只要广州岗位，却要模型先读完全国岗位。
- 岗位内容发生更新，聊天窗口中的旧文本不会自动更新。
- 模型读过一部分 JD 后，容易误以为自己已经检查了全部。

因此，Job-RAG 应该**保存和检索数据**，模型则在需要时**按问题取得相关数据**，而不是每次把整个知识库塞给模型。

### 2. 为什么不让 Agent 直接执行 SQL？

技术上可以给 Agent 数据库连接，但这相当于把内部数据结构和广泛的数据库操作能力交给模型。

即使只允许 SELECT，模型仍然需要知道表结构、字段含义、状态规则、岗位去重口径；一条能运行的 SQL 也可能把“岗位记录数”算成“公司数”，或把“已采集”误解为“在招”。

更合适的方式是让 Job-RAG 提供有限、可解释的业务操作，例如“按条件找候选”“按字面规则统计”“读取指定 JD”。这样数据库如何存储可以改变，但工具的业务语义保持稳定。

### 3. 为什么选择 MCP，而不是让每个 Agent 自己集成 Python 函数？

**MCP（Model Context Protocol）是 AI 应用与外部工具和数据交互的开放协议。** 它定义了工具如何被发现、工具接受什么输入，以及如何返回结果。支持 MCP 的 AI 应用可以通过统一协议使用 Job-RAG，而不必分别为每个模型或 Agent 框架重新开发一套调用方式。

这里要区分两个价值：

- **Job-RAG 提供业务能力**：数据过滤、检索、计数、原文读取、证据与版本信息。
- **MCP 提供连接方式**：让 AI 应用发现和调用这些能力。

MCP 不会自动提高检索召回率、增强模型理解能力，也不会使不完整的统计变得完整。它解决的是**Agent 怎样可靠地调用业务能力**，不是替业务能力本身兜底。

## 二、一次 MCP 调用究竟是怎样发生的？

### 1. MCP 里有哪些参与者？

先区分三个对象：

- **Host（宿主应用）**：例如用户正在使用的 Coding Agent 或 AI 助手应用，负责对话、模型调用和工具使用管理。
- **MCP Client**：宿主内负责与 MCP Server 按协议通信的部分。
- **MCP Server**：由 Job-RAG 提供，公开允许使用的岗位查询工具，接收参数并返回结果。

模型不是直接连接数据库。它通过宿主看到工具说明，提出工具调用，再由宿主中的 Client 访问 Job-RAG MCP Server。

### 2. 用户提问以后，调用顺序是什么？

```text
用户：广州有哪些负责 RAG 建设的岗位？
                 │
                 ▼
       AI 宿主应用 / 大模型
       理解问题、决定调用工具
                 │
                 ▼
         MCP Client
       按协议传递工具名和参数
                 │
                 ▼
          Job-RAG MCP Server
       校验输入、执行岗位检索
                 │
                 ▼
       返回岗位 ID、片段、来源、
       状态、版本等结构化结果
                 │
                 ▼
           大模型继续判断
       必要时再取完整 JD
                 │
                 ▼
           向用户解释结果
```

对模型来说，关键不是知道 Job-RAG 用了什么数据库，而是能识别：**我现在需要找候选岗位，应调用哪项工具？结果能证明什么，不能证明什么？**

### 3. 模型怎么知道有哪些工具？

MCP Server 向 Client 提供工具目录。每个工具至少要有清楚的**名称、功能描述和参数结构（input schema）**；也可以定义输出结构（output schema）。

例如工具描述不能只写“搜索岗位”，而应解释：“按相关性寻找候选，返回有限数量的岗位与证据；结果不代表全库精确计数。”

这个说明会影响模型能否选对工具。**工具的名称与描述，本身就是 Agent 的操作指引。**

### 4. MCP 有 Tools、Resources、Prompts，Job-RAG 都要做吗？

不需要一开始全部引入。

MCP 可以提供可调用的 **Tools**、用于读取内容的 **Resources**、可复用的 **Prompts**。但 Job-RAG 当前最核心的问题是：让 Agent 根据用户目标执行有明确参数的岗位查询。因此初期只需要 **Tools**。

等到确实存在“用户希望直接浏览某个固定资源”或“多个宿主需要共享一套专业分析模板”的需求，再考虑 Resources 或 Prompts。不要因为协议支持，就把每种能力都做一遍。

## 三、为什么不能只做一个“向 Job-RAG 提问”的工具？

### 1. 一个通用问答工具看起来不是更简单吗？

如果只提供 `ask_jobrag(question)`，模型只要把用户问题交进去，似乎最省事。

但它会掩盖三种根本不同的操作：

| 用户要做什么 | 真正需要的能力 | 容易发生的错误 |
|---|---|---|
| 找到一些相关岗位 | 有排名的候选检索 | 把关键词接近当成工作内容符合 |
| 数清符合规则的全部岗位 | 完整过滤、枚举、计数 | 把 Top-K 检索数量当成全库数量 |
| 归纳全库的技术要求 | 全量取数、逐份判定、汇总 | 只分析部分 JD，却报告总体百分比 |

如果所有操作被包装成一个黑盒，模型既不知道用了哪种方法，用户也难以核对结果口径。

### 2. 那是不是每一种用户问题都要开发一个 MCP 工具？

也不是。

“找 RAG 岗位”“找模型部署岗位”“找适合三年经验的职位”都属于**候选检索**；没有必要为每个主题开发单独工具。

工具应该围绕**稳定、可复用的业务操作**划分，而不是围绕技术关键词、页面按钮或某一句提问划分。

### 3. 对 Job-RAG，最小的业务能力是什么？

先把复杂请求拆到四个基本动作：

1. **了解数据范围**：知识库里有什么、缺什么、数据有多新？
2. **寻找候选**：哪些岗位可能与意图相关？
3. **完整查询**：按确定的规则，到底有多少岗位符合条件？
4. **阅读原文**：这些岗位的职责和要求究竟写了什么？

初期用四个只读工具，就能把这四个动作清楚地交给 Agent。

## 四、工具一：get_job_dataset_info——先知道自己在查什么

### 1. 用户为什么需要知道数据范围？

用户问“RAG 岗位的技术要求是什么”，如果数据库只收集过部分招聘平台、部分时间、部分城市，结果自然只能代表这份语料，不能代表整个招聘市场。

模型还需要知道某些岗位缺失正文，某些岗位尚未核验招聘状态。否则它可能把“库里没找到”回答成“市场上没有”。

### 2. 这个工具应该提供什么？

建议命名为 `get_job_dataset_info`，返回：

- 数据集标识与语料版本（如 `corpus_id`）。
- 岗位记录数、具有完整 JD 的数量、缺失正文数量。
- 数据来源、采集时间范围、最近更新时间。
- 城市、岗位状态等可用的过滤维度及字段说明。
- 已确认在招、已关闭、待核验等状态的定义与分布。
- 可用于检索的岗位数及必要的索引就绪信息。
- 数据集已知的采集范围与覆盖限制。

### 3. 它和“搜索岗位”有什么不同？

它不是返回匹配岗位，而是回答**这次研究能依赖怎样的数据**。例如用户要做覆盖全库的技术要求统计，Agent 应先确认数据范围，再决定怎样枚举、阅读和汇总。

不必每句闲聊都调用它；当任务涉及总数、占比、时间范围或数据完整性时，它尤其重要。

## 五、工具二：search_jobs——先找到值得阅读的候选岗位

### 1. 为什么不能只查字符串？

用户想找“企业 RAG 系统研发”，但 JD 可能写的是“知识文档接入、索引构建、语义检索、智能问答”。如果只能匹配 `RAG` 这三个字母，就可能漏掉真正相关的岗位。

因此需要检索：用词法检索、可选语义检索和多查询等机制，尽量发现**可能相关**的岗位。

### 2. 它应该接收什么参数？

建议命名为 `search_jobs`。核心输入包括：

- `query`：希望寻找的工作内容。
- `filters`：城市、薪资下限、经验、学历、允许的岗位状态等**明确条件**。
- `query_variants`：可选的其他搜索表达，用于提高召回。
- `limit`：最多返回多少个候选岗位。

例如：

```json
{
  "query": "企业 RAG 知识库研发",
  "query_variants": ["文档检索与智能问答", "检索增强生成系统开发"],
  "filters": {
    "city": "广州",
    "min_monthly_salary": 20000
  },
  "limit": 20
}
```

这是**建议中的业务参数示例**，不是现有接口的可执行请求。

### 3. 返回岗位标题和分数够了吗？

不够。结果至少应该包含岗位唯一标识、公司、地点、薪资、来源链接、采集与核验状态、命中的原文片段及片段所属部分（岗位职责、任职要求等）。

还应说明排名依据与检索是否发生降级，不能把 BM25 或向量相似度分数包装成“满足岗位要求的概率”。

### 4. 为什么搜索结果不能拿来做精确统计？

因为检索通常只返回相关性靠前的前 N 个岗位。

如果查到 20 个提及 RAG 的职位，真实含义是“这次检索返回了 20 个候选”，**不是“全库只有 20 个 RAG 岗位”**。

`search_jobs` 应明确暴露 `count_kind: "bounded_candidates"` 或等价信息，防止 Agent 把候选数误用为总体数。

## 六、工具三：query_jobs——需要数清楚时，不能再靠相关性排名

### 1. 什么问题适合完整查询？

例如：“广州所有 JD 中，有多少份的**岗位职责或任职要求**字面出现 RAG？”

这个问题要求按一个明确规则检查全部符合范围的记录，而不是挑最相似的前 20 条。

### 2. 怎么把这个问题转换成可执行规则？

需要逐步明确：

1. **统计单位**：一条岗位记录，还是去重后的招聘职位？默认应使用稳定的来源 + 岗位 ID，避免同一岗位的多个 Chunk 被重复计数。
2. **地域范围**：广州，还是所有城市？
3. **检查位置**：标题、岗位职责、任职要求，还是整个 JD？
4. **匹配方式**：是否忽略大小写？按子串还是词边界匹配？
5. **状态范围**：是否包含已关闭、未核验的岗位？
6. **缺失数据**：没有完整 JD 的岗位如何披露？

**“原文出现 RAG”是确定性的文字判断；“实际从事 RAG 建设”是语义判断。** 二者不能悄悄混为一谈。

如果数据尚未可靠区分“职责”和“任职要求”，工具必须返回字段覆盖或解析限制，不能假装已经准确检查了这两个部分。

### 3. 这个工具支持哪些操作？

建议命名为 `query_jobs`，将确定性查询集中在一个工具内：

- 结构化过滤：城市、薪资、经验、状态等。
- 指定字段的字面条件：词项、AND/OR、匹配方式。
- **完整计数**：返回规则范围内准确匹配的记录数。
- **完整枚举**：将匹配岗位按稳定顺序分页列出，并返回下一页位置。
- **无关键词枚举**：仅按结构条件列出全部目标岗位，为后续语义分析准备样本。

例如：

```json
{
  "filters": { "city": "广州" },
  "text_match": {
    "terms": ["RAG"],
    "fields": ["responsibilities", "requirements"],
    "mode": "substring",
    "case_sensitive": false
  },
  "operation": "count"
}
```

这里的 `responsibilities` 和 `requirements` 是**拟议的逻辑字段**，需要底层具备可信的章节提取才能启用；它们不应被误解为当前数据已经完成的结构化字段。

### 4. 返回结果必须区分哪些数量？

至少区分：

- `corpus_jobs`：数据集里的全部岗位记录数。
- `eligible_jobs`：满足城市、状态等过滤条件的岗位数。
- `matched_jobs`：进一步满足指定字面规则的岗位数。
- `missing_or_unparsed_jobs`：相关字段缺失或无法可靠解析的数量。
- `count_complete`：是否完成了**这套规则下**的全量检查。

即使 `count_complete=true`，也只表示当前语料和给定规则已完整检查；它不表示全市场完整，也不表示完成了技术能力的语义判断。

### 5. 为什么还需要分页和快照标识？

如果匹配出几百个岗位，一次性把所有 JD 发给模型，会再次耗尽上下文。应分批返回岗位 ID 和少量元信息。

但分页期间数据可能更新：第一页基于旧版，第二页基于新版，可能重复或漏掉记录。因此工具应提供 `snapshot_id`、`next_cursor`（或等价分页标识），并在数据或查询条件变化时明确拒绝继续拼接。

**分页解决单次输出过大；一致性校验解决跨页混入不同数据版本。** 校验指纹不等于永久保存了历史数据库快照。

## 七、工具四：read_jobs——为什么找到岗位以后还要读完整 JD？

### 1. 检索片段能证明“必须具备 RAG 经验”吗？

考虑四条不同的原文：

```text
A：负责 RAG 检索系统的开发和部署。
B：具备 RAG 项目经验者优先。
C：公司产品采用 RAG；本岗位负责商务销售。
D：负责知识检索、上下文构建和问答系统优化。
```

如果只搜 `RAG`，A、B、C 都会命中，D 可能被漏掉。但它们体现的要求并不相同：

- A 描述的是工作职责，不必然等于任职硬门槛。
- B 是加分项，不应被写成必备条件。
- C 提到技术，但不代表这个岗位负责研发。
- D 可能与 RAG 工程高度相关，需要结合完整 JD 判断。

这些区别不能由搜索命中或一个相似度分数替代。

### 2. 这个工具应该读什么？

建议命名为 `read_jobs`，支持按**来源 + 岗位 ID**读取单份或批量 JD；已知 ID 时不必重新搜索。

返回信息应包括：

- 标题、公司、城市、薪资、经验、学历。
- **完整岗位职责与任职要求原文**，保留原句和可定位的章节。
- 来源 URL、采集时间、核验时间、招聘状态。
- 岗位版本、语料版本。
- 对缺失、已变更或读取失败的岗位，逐条返回明确错误，而不是默默跳过。

### 3. 为什么要支持批量读取？

“比较两个岗位”和“分析一百个岗位”的底层动作都是读取完整 JD。批量操作能减少调用次数，但每次应设置数量和响应大小上限，不能一次输出整库。

### 4. 读全文时为什么还要传版本？

某个岗位昨天写“RAG 经验优先”，今天改成“必须有生产部署经验”。如果 Agent 用昨天枚举的列表，却读取今天的部分 JD，最终汇总就混用了不同时间的数据。

因此 `read_jobs` 应能校验预期岗位版本，必要时同时校验 `corpus_id`。发现变化就明确报告，让上层重新取数，而不是伪装成一次一致的分析。

## 八、四个工具怎样配合完成真实问题？

### 场景 A：找三个广州的 RAG 开发岗位

```text
用户描述目标、城市、薪资要求
           ↓
Agent 明确硬条件与工作内容意图
           ↓
search_jobs：召回一批可能相关的岗位
           ↓
read_jobs：阅读有希望的候选 JD
           ↓
Agent 区分真实研发职责、加分项与公司介绍
           ↓
给出三个推荐，附上对应原文和来源
```

这里不需要全库精确计数，也不应该每次都枚举所有 JD。**检索负责尽量找对，读原文负责判断是否真的符合。**

### 场景 B：广州有多少份 JD 在职责或要求中提到 RAG？

```text
get_job_dataset_info：确认语料及字段覆盖
           ↓
query_jobs：广州 + 指定字段 + RAG 字面规则
           ↓
返回完整计数、规则、缺失量和语料版本
           ↓
Agent 解释“字面出现”的确切含义
```

这里不需要先做 Embedding，也不需要让大模型猜一份 JD 是否“算 RAG”。**规则明确时，由确定性的程序完成计数。**

### 场景 C：RAG 岗位同时要求哪些技术？

这比上一个问题多了一层。

第一步，用 `query_jobs` 确定研究对象，例如“岗位职责或任职要求字面出现 RAG 的全部岗位”；若研究对象改成“实际从事 RAG 工程的岗位”，就必须另外进行语义筛选。

第二步，对研究对象完整分页，再用 `read_jobs` 批量取出 JD。

第三步，由分析层按照**事先定义的抽取口径**逐份判断：Python、向量数据库、Embedding、Reranker、LangChain、模型部署等技术是否被提到？是在职责里，还是必备、优先、可选的任职要求里？每个判断都要能指回原文。

第四步，汇总**按岗位去重后的数量**。一份 JD 中 Python 出现五次，也只能算一个要求 Python 的岗位；一条写“Python 或 Java”的要求不能随意改写成“必须同时掌握 Python 和 Java”。

第五步，报告处理覆盖情况。用下面的**假设数据**说明口径：

```text
符合初始 RAG 字面条件：120 条
已取得完整 JD：118 条
已完成语义判定：100 条
未处理：18 条
正文缺失：2 条
```

这时可以汇报“已判定的 100 条岗位中，Python 出现多少次”，却**不能**把这 100 条中的比例直接说成“120 条岗位的精确比例”。如果要求全库统计，就必须继续完成其余岗位、保留无法判断项，并明确分母。

这也说明：**MCP 负责提供可靠的数据操作；Agent 负责理解任务和组织分析，但完整的全库语义统计还需要可恢复、可核查的执行流程。**

## 九、既然四个工具已经齐全，为什么还可能需要第五种能力？

### 1. 让 Agent 自己循环读取几百份 JD，有什么问题？

它可以用四个基础工具尝试完成任务，但长流程会遇到现实限制：上下文变长、调用中断、已处理岗位重复、判定口径漂移、Token 成本增加，以及“处理到一半却写出完成报告”。

这些问题不是增加一个 `search_jobs` 的参数就能解决的。

### 2. 什么时候值得增加“全库语义分析任务”？

当用户经常提出“统计整个岗位库的必备技术”“比较不同城市的技能组合”“分析 RAG 岗位能力变化”等**必须完整处理大量 JD**的问题时，可以在下一阶段引入服务端分析任务能力。

它至少需要：

- 固定分析范围、语料版本和分类口径。
- 分批处理并持久记录每条 JD 的判断与原文证据。
- 支持中断、恢复、重试与失败清单。
- 由程序汇总，而不是要求模型凭记忆相加。
- 返回总任务数、已完成、无法判断、失败、未处理等进度。
- 保留模型与规则版本，允许抽样复核和重新分析。

届时可以再考虑 `submit_job_analysis` 和 `get_job_analysis_result` 之类的工具。它们代表的是**新增一项完整的业务能力**，而不是为了 MCP 而制造更多入口。

初期不应把这项尚未建立的能力写成现成工具，更不能让一个普通搜索工具冒充已完成全库语义统计。

## 十、工具结果怎样设计，Agent 才不容易用错？

### 1. 返回自然语言说明不就够了吗？

不够。只返回“找到 23 个岗位”时，Agent 不知道这是前 23 个候选，还是完整扫描后的 23 个岗位。

工具应优先返回结构化结果，再附必要的人类可读说明。对不同任务，明确区分：

- **bounded_candidates**：有限候选，不可用于全库计数。
- **exact_literal_count**：固定范围内、确定字面规则的完整计数。
- **semantic_assessment**：基于 JD 内容的模型或人工判定，必须提供判定标准与处理覆盖情况。

这些是建议中的**业务语义标记**，不是 MCP 协议规定的固定字段名。

### 2. 一条可核对的证据至少需要什么？

应能定位到**哪一条岗位、哪个版本、哪个原文部分、哪一句话**，同时保留来源链接与状态。模型生成的概括可以附在证据旁，但不能替代原文。

### 3. 没找到、没权限、数据变化，能不能都返回空列表？

不能。

- `no_matches`：在指定规则与范围下没有匹配项。
- `invalid_filters`：输入条件或字段不合法。
- `version_changed`：前后数据版本不一致，需要重新获取。
- `data_incomplete`：缺少必要原文或章节信息。
- `service_unavailable`：依赖的检索或数据服务不可用。

这些状态需要有不同处理方式。静默返回 `[]` 会让模型误以为“业务上没有岗位”。

### 4. 为什么要限制返回大小？

因为上下文是一种有限资源。候选检索应只返回精简证据，全文读取要按批次进行，完整枚举要分页；大规模分析结果应返回**汇总 + 可追溯明细引用**，而不是一次输出上百份完整 JD。

## 十一、Job-RAG 和 Agent 的责任应该怎样分开？

| 工作 | 主要责任方 | 原因 |
|---|---|---|
| 保存 JD 原文、来源、版本和状态 | Job-RAG | 必须有稳定、可复核的数据事实 |
| 城市、薪资、状态等严格过滤 | Job-RAG | 不应让模型凭感觉筛选 |
| 关键词计数、全量枚举、分页去重 | Job-RAG | 需要确定性和覆盖保证 |
| BM25、向量等候选召回 | Job-RAG | 属于检索系统的专门能力 |
| 理解用户想研究什么、何时补查 | Agent | 需要语言理解与任务决策 |
| 阅读 JD，区分职责、必备与优先 | Agent 或受控语义分析服务 | 需要语义判断与原文核验 |
| 批量语义判断结果的持久化、汇总 | 可选的 Job-RAG 分析服务 | 大规模任务必须能恢复、审计和准确计数 |
| 组织最终报告、说明口径和限制 | Agent | 面向用户解释，但不能篡改底层事实 |

关键边界是：**Job-RAG 不需要包办“用户的一切推理”，Agent 也不应该重复实现数据库的精确查询和任务记录。**

## 十二、怎样搭建这一层 MCP，才不会再次变成复杂系统？

### 1. 先实现哪些？

第一阶段只暴露四个只读业务工具：

| 工具 | 一句话职责 | 明确不负责 |
|---|---|---|
| `get_job_dataset_info` | 说明知识库的数据范围和状态 | 分析岗位是否匹配 |
| `search_jobs` | 召回有限数量的相关候选与证据 | 全库精确计数 |
| `query_jobs` | 严格过滤、字面匹配、完整计数与枚举 | 判断语义上的必备能力 |
| `read_jobs` | 按 ID 批量获取完整 JD 与版本信息 | 自动生成全库分析报告 |

工具名是目标设计，未来可以调整；但**业务边界应稳定**。不应因为底层有 BM25、Embedding、数据库查询三个实现，就向 Agent 暴露三个重复的“搜索入口”。

### 2. 连接方式怎么选？

如果 Job-RAG 部署在服务器、不同设备或不同 Agent 都要访问，优先考虑 MCP 的 **Streamable HTTP** 传输；如果只是由本机 AI 应用启动一个本地进程，可以采用 **stdio**。

这是**同一个 MCP 服务能力的不同传输方式**，不是另外两套岗位查询产品。实现时应确认使用的 MCP SDK、宿主和协议版本是否兼容；不要把某个旧版本的初始化和会话流程当成永久不变的协议。

### 3. 哪些能力坚决不向普通查询 Agent 开放？

初期不暴露任意 SQL、导入/删除岗位、修改核验状态、重新索引、读取服务密钥、执行宿主系统命令等能力。数据维护和查询应有不同的权限边界。

即使只有只读工具，远程服务仍需考虑认证授权、HTTPS、限流、超时、请求大小、调用记录和敏感信息保护。**只读不等于可以无保护地公开到互联网。**

JD 是外部文本，其中可能出现类似“忽略之前的指令”的内容。它只能作为**待分析的招聘证据**，不能成为改变 Agent 行为或扩大工具权限的指令。

### 4. 用什么问题检查四个工具是否设计正确？

与其只测 MCP 能不能连接，不如用真实问题检验业务边界：

| 测试问题 | 应发生什么 | 不应发生什么 |
|---|---|---|
| 找三个广州 RAG 研发岗位 | 检索候选、取 JD、核对职责 | 仅看关键词就宣称岗位匹配 |
| 广州多少 JD 字面提到 vLLM | 完整条件计数、披露范围 | 把搜索 Top-20 叫作总数 |
| 比较已经知道 ID 的两个岗位 | 直接读取两份完整 JD | 再执行无关的语义检索 |
| RAG 岗位必备哪些技术 | 明确判定口径、覆盖全部目标 JD 或披露未完成 | 把“优先”当“必备”，把部分样本当全库 |
| 分页过程中有岗位更新 | 拒绝混合不同版本，要求重新查询 | 静默拼接旧页和新页 |
| JD 内出现恶意指令 | 把它当数据处理 | 将 JD 的指令提升为系统命令 |

若模型反复选错工具，应先检查**工具边界、名称、描述、输入参数和返回字段**是否能让它区分操作，再考虑补充宿主侧提示或专门路由；不要第一反应就是再增加一个包装工具。

## 十三、最后怎样理解 Job-RAG 的 MCP 定位？

Job-RAG 最值得保留的不是“可以从多少种入口访问”，而是**它能向 Agent 提供什么独有、可信的岗位数据操作能力**。

从用户问题一步步推下来：

1. 想研究岗位，先要知道**有什么数据、数据覆盖到哪里**。
2. 想找工作，需要**有排名的候选检索**，再读原文。
3. 想知道“有多少”，必须先明确**统计范围和判断规则**，不能使用 Top-K 结果凑数。
4. 想理解岗位技术要求，必须**读取完整 JD、区分职责和条件性质**。
5. 想得到全库语义统计，还要保证**所有目标岗位已处理、判断有证据、过程可恢复、汇总由程序完成**。

所以初期最合理的形态是：

```text
多个支持 MCP 的 AI 应用
           │
           ▼
    一个 Job-RAG MCP Server
           │
   ┌───────┼────────┬────────┐
   ▼       ▼        ▼        ▼
 数据概况  候选检索  精确查询  JD 全文
   │       │        │        │
   └───────┴────────┴────────┘
           │
       Job-RAG 业务层
     原文 / 结构化字段 / 索引
     来源 / 版本 / 状态
```

**MCP 是让 Agent 使用岗位知识库的标准工具边界；Job-RAG 的核心价值，仍然来自可靠的数据、正确的查询机制和可追溯的证据。**
