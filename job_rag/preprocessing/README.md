# 数据预处理：从招聘 CSV 到可以可靠查询的岗位记录

用户会说“广州、20K 以上、三年经验的 RAG 岗位”，而 CSV 写的是“广州·天河区”“20-35K·14薪”“3-5年”。直接在原始字符串上筛选容易混淆地点、金额、年限与计薪周期。因此预处理需要**保留原文，同时生成程序能够比较的字段**。

这里不负责爬虫、不让 LLM 分析岗位含义，也不构建向量。它做三件按顺序发生的工作：先验证整个文件，再推导结构字段，最后事务性保存。

## 一、先校验，再写入：为什么不能边读边导？

`validation.py` 的 `parse_csv()` 使用标准 CSV 解析器读取 UTF-8/BOM 文件，保留正文中的换行，检查必需列、列数、空 ID、同批重复 ID 和空文件。其他字段裁剪首尾空白，`description` 不裁剪。

`importer.py` 在**整份 CSV 校验通过以后**才开启数据库事务。否则第 100 行有问题、前 99 行却已落库，就会出现来源文件未完成更新而数据库却部分更新的情况。事务在中途失败也回滚，避免留下半批数据。原始网页是否准确、职位是否有效不属于这一步的验证范围。

## 二、标准化实际改变了什么？

`normalize.py` 用字符串解析和正则，创建 `normalized`，不覆盖原字段。例如：

~~~text
原文：广州·天河区；20-35K·14薪；3-5年；本科
派生：city=广州，district=天河区
      salary_min=20000，salary_max=35000，salary_period=month，salary_months=14
      experience_min=3，experience_max=5，education_level=本科
~~~

将薪资拆成上下限，是为了区分“岗位**最低工资**达到 20K”与“**区间覆盖** 20K”。前者在 `20-35K` 的岗位上成立；`10-25K` 只满足后者。哪个条件符合用户意图，由[查询层](../querying/README.md)决定，不应在数据清洗时预先替用户做决定。

解析无法覆盖所有招聘写法。对“面议”等不可比较的薪资，系统留下空数值、未知周期和 `salary_not_comparable` 质量标记，而不是编造薪资；对缺失正文、字段未显示或经验栏混入学历文字也有相应标记。可重复的有限规则比“看起来合理”的猜测更适合硬条件过滤，但规则不完整意味着可能产生漏选。

## 三、重复导入时怎样保证版本可追溯？

`importer.py::import_csv()` 将 `source:job_id` 作为唯一键，例如 `boss:某ID`。一份岗位初次出现，建立版本 1；后续原始行改变，版本加一并保存 `revisions`；完全相同则主要更新最近观察时间。

系统计算两种不同指纹：`raw_hash` 覆盖导入后的整行字段，检测记录变化；`content_hash` 仅针对影响检索内容的字段。仅采集日期改变时也可能产生新版本，但如果构建出的检索文本和索引签名完全一致，[索引执行器](../indexing/README.md)可复用已有向量。

导入新版本时会**登记** `index_tasks`，而不是在数据库事务里直接调用网络模型。这使“可靠保存新事实”和“可能失败的外部索引构建”分离。数据库状态首次为 `unknown`；再次导入不会自动把人工确认关闭的岗位恢复为在招，后续 CSV 中缺失某个 ID 也不会自动关闭它。

## 四、如何运行与排查？

~~~bash
# 仅保存数据并登记任务
job-rag import data/jobs.csv --no-index

# 独立处理待完成或失败的索引
job-rag worker
~~~

不加 `--no-index` 的 `job-rag import` 会在导入后执行一次索引处理；如果配置远程模型，请确认费用和权限。导入出错，先检查文件编码、必需列、ID 和标准 CSV 转义；某些岗位筛选不到，先查看 `normalized` 的可比较字段与质量标记，不要直接认定检索模型有问题。

代码路径：`validation.py` 负责 CSV 解析；`normalize.py` 负责派生字段与指纹；`importer.py` 负责事务与增量版本。下一环节是[存储层](../storage/README.md)和[索引构建](../indexing/README.md)。
