# 预处理为什么不能直接让 LLM 来做？——从招聘字符串到可比较的数据

用户想找“广州、薪资下限 20K、工作经验 3 年以内要求的岗位”。CSV 却只会告诉我们“广州·天河”“15–25K·14薪”“3–5年”。这些原始字符串适合阅读，却无法安全地直接用于大小比较。如果让检索相似度决定是否符合薪资硬条件，即使语义排名很高，推荐仍可能违反用户约束。

`preprocessing/` 解决的是**把可确定的招聘属性转成可比较的字段，同时不破坏招聘原文**；它不承担语义招聘能力判断。

## 一、为什么先验整个文件，才开始导入？

一次 CSV 通常有数百行，其中 JD 可能包含换行、逗号或引号。若程序边读边写，第 200 条才发现字段错位，前 199 条可能已经更改；用户随后检索到的就是一次未完成的更新。

`validation.py` 采用标准 CSV 解析与 UTF-8 BOM 兼容，检查必需列、行宽、空 ID、重复 ID 及空文件，整批通过才由 `importer.py` 开启数据库事务。事务中途失败会回滚。这保证了**一次导入要么完整成功，要么不部分生效**。正文 `description` 保留解析后的原样换行及空白，避免为了“清洁数据”改变措辞。

校验只证明输入符合约定，不能证明网页本身真实，也不代表岗位仍在招。

## 二、为什么把地区、薪资和经验解析成独立属性？

例如一条原始记录：

~~~text
location=广州·天河区
salary=20-35K·14薪
experience=3-5年
education=本科
~~~

`normalize.py` 生成 `city=广州`、`district=天河区`、`salary_min=20000`、`salary_max=35000`、`salary_period=month`、`salary_months=14`、`experience_min=3`、`experience_max=5` 及学历字段。

这样系统才能清楚地区分：
“**最低工资达到 20K**”要求 `salary_min >= 20000`；
“**薪资区间覆盖 20K**”则是另一个判断；
“我有三年经验，能否达到岗位最低门槛”检查岗位 `experience_min` 是否不高于三年。

这些判断涉及数值与规则，不应该让语义分数代替。两种薪资筛选口径由[查询条件层](../querying/README.md)决定，而不是清洗时提前替用户选好。

## 三、为什么遇到未知信息不直接猜一个值？

职位写“面议”时，如果自动填 `salary_min=0`，会把“我们不知道”变成“确定工资很低”；填一个估计数字又会造成虚假的硬条件匹配。因此代码保留 `None` 和 `salary_not_comparable` 标记。缺正文、来源字段未显示、经验栏混入学历文字也有相应提示。

这种保守规则的代价是**漏选**：未覆盖的薪资格式、复杂地区写法可能无法成功规范化。但漏选可以通过检查质量标记和扩展解析规则来修复，比无依据猜值造成的错误推荐更可控。

## 四、为什么还需要两种哈希和岗位版本？

同一个来源 ID 重新导入，可能出现三种变化：完全没变；只有采集日期变化；岗位职责或薪资变了。

`importer.py` 使用 `source:job_id` 定位岗位。`raw_hash` 对整行导入字段求指纹，用于判断是否增加 `version`、保存新 `revisions`；`content_hash` 针对参与检索内容的一组字段建立另一指纹。这样能够区分“来源记录发生了变化”和“向量文本需要重新生成”。

即使采集日期改变造成新版本，只要索引生成的文字和签名确实没变，[Worker](../indexing/README.md)也可能复用向量。导入时只登记 `index_tasks`，避免数据库事务因外部模型超时而悬挂。

此外，岗位的 `job_status` 不是从 CSV 采集 `status` 直接拷贝。重新导入不会使人工关闭的岗位自动恢复；未出现在文件里的岗位也不会被自动关闭。

## 五、代码边界与操作

~~~text
CSV → validation.parse_csv() → importer.import_csv() 内事务
                              ├─ normalize() 派生属性
                              ├─ 保存当前岗位及历史版本
                              └─ tasks.enqueue() 登记索引任务
~~~

~~~bash
job-rag import data/jobs.csv --no-index
job-rag worker
~~~

需要记住的不是函数列表，而是三个不同保证：**输入一致、硬条件可计算、历史变化可追溯**。下一步由[存储层](../storage/README.md)承载这些事实，再由[索引层](../indexing/README.md)使 JD 可检索。
