# 检索实验实现：如何知道新的分块或模型真的更好？

某次搜索出现更满意的职位，不一定是 Embedding 比 BM25 强：也可能是查询词不同、岗位分块不同，或评测只标了一条“已知相关”的岗位。`job_rag/experiments/` 的作用是把这些变量拆开，使比较结果能解释，而不是给模型排名贴一串看起来漂亮的分数。

这里是**离线实验的 Python 实现**，不参与普通在线请求，也不自动把实验向量写进线上 PostgreSQL。

## 一、实验先冻结什么？

`runner.py::prepare()` 从标准 CSV 读取有正文的岗位，同时冻结查询、人工标注、分块方案、原始文件哈希与实现指纹。运行时先保证不同方案面对同一数据和问题，避免代码中途变化后把不可比较的结果放在一起。

五种候选表示包括旧固定分块、紧凑固定分块、章节分块、章节加条件标签，以及较小预算的章节分块。它们改变的是检索文档的组织方式；`BM25_reference` 则是标题加完整正文的词法参考，不应被说成完全控制了输入形式的纯算法实验。

## 二、第一轮测“能不能找到”，第二轮测“排得好不好”

`recall()` 使用相同 Embedding 模型对查询和不同方案的 Chunk 生成向量、计算精确余弦相似度。一个岗位可能有多个块，离线实验先取该岗位命中块的**最高相似度**，再输出岗位级候选。线上 `retrieval/search.py` 是先对 Chunk 通道做 RRF 再聚合，两套机制并不等价，不能把离线分数直接解释为线上指标。

`pool()` 将各方案的候选合并成待人工审阅集合；`rescore()` 在补充相关性标签后重新计算指标而不重付 Embedding 费用。`rerank()` 则锁定第一轮某个候选集合，在相同原文表示上比较“不重排、BM25、章节规则、Qwen 默认、Qwen 招聘指令”，这样排名变化才可以归因给重排过程，而不是又偷偷扩大了召回范围。

## 三、如何理解指标，为什么不能急着宣布胜者？

`metrics.py` 计算 Recall@K、HitRate、nDCG、MRR 等岗位排名指标，并通过按主题组聚类的 bootstrap 做配对比较。当前 30 条查询主要是每题一个已知正例的 **seed** 标注：找到预设岗位只能证明命中了它，未标注的其他岗位**不是自动负例**。在未穷尽全部候选相关性判断前，不应把 seed 指标宣传成总体 Precision 或 Recall。

第一轮真实 Qwen Embedding 实验已经完成；Rerank 小探针通过，但完整第二轮尚未运行。具体结果、案例及局限见[首轮报告](../../docs/recall-pilot-2026-10-25.md)。

## 四、模型请求如何做到可复查？

`bailian.py` 提供独立的百炼模型客户端，使用本地 SQLite 缓存、请求哈希、脱敏日志和软件费用/请求次数保护。生成 Embedding 时区分 query 与 document；运行相同文本可以复用缓存。`cli.py` 为 `prepare`、`recall`、`pool`、`rescore`、`rerank`、`report`、`probe` 提供命令入口，真正付费的调用需要显式 `--execute`。

缓存与报告存放在 `runtime/experiments/`，与在线索引相互隔离。修改实现后应按指纹重建实验快照，不能绕过历史实验校验来声称完成复现。完整命令见[实验入口](../../experiments/README.md)，实验设计依据见[实验协议](../../docs/embedding-experiments.md)。
