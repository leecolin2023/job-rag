# 为什么我们不能凭几次搜索结果就宣布“新 Embedding 更好”？

系统用了章节分块后，某个指定 RAG 岗位从第 15 位跃升到第 1 位，看起来像大幅进步。但另一个同样相关的岗位可能因此从前排跌落；更麻烦的是，如果评测只标记一个种子岗位，其他真正合适的岗位会被错误地视为负例。**检索评测的核心问题，是怎样区分算法变化、输入变化和标注缺失造成的排名差异。**

这里实现的是离线受控实验，不是在线搜索接口。

## 一、为什么实验先冻结查询、数据和代码？

若今天换模型，明天改切块，后天又改查询改写，结果变好时无法解释是哪一项造成的。`runner.prepare()` 先把 CSV、30 条评测查询、硬条件、分块方案、源文件和实现指纹写进独立快照。每种方案对同一批岗位和问题运行，实验中间不能悄悄换数据。

第一轮保留旧固定 1100 字符（A）、紧凑固定（B）、章节紧凑（C）、章节加条件提示（D）、小预算章节加提示（E），并另设 BM25 全文参考。A 到 B 主要比较重复头部的影响；C 改变边界；C 与 D 尽量使用相同的正文边界，以观察附加条件提示的作用；E 改小预算。不同方案不是处处只有一个变量变化，解释结论时不能夸大实验控制程度。

## 二、为什么第一轮只测召回，第二轮才测重排？

第一个问题是“相关岗位能否进入候选”。`runner.recall()` 将同一查询、每套分块的 Chunk 用相同 Embedding 转为向量，计算余弦相似度；同一岗位取**最高命中 Chunk**代表该职位，再产生岗位级 Top-50。这样不会让一条长 JD 因为有多个块就占据十几个候选位置。

第二个问题是“候选都已经进来了，谁应该排得更靠前”。`runner.rerank()` 冻结第一轮某个候选池，在**同一批完整岗位表示**上比较原顺序、BM25、章节规则、Qwen 默认 Rerank 和招聘条件指令 Rerank。如果第二轮悄悄增加查询或候选，得到的提升就可能来自召回，而不是重排。

注意：离线实验先按岗位取最大 Chunk 余弦，而线上检索先融合 Chunk 的 RRF 排名再按岗位聚合。两种方法不完全相同，因此离线成绩不能直接冒充线上性能。

## 三、为什么要让人读那些“模型没命中的岗位”？

每个查询最初主要只有一个人工种子正例。一个方案把种子排到第 49 位，不代表前 48 位都不相关。`pool()` 把多个方案候选合并给人审阅并补充 `grade` 与原文证据；`rescore()` 可以在不重调 Embedding 的条件下，按新标注重新计算排名指标。

`metrics.py` 区分 seed/pooled/exhaustive 的判断范围，计算 Recall、HitRate、nDCG、MRR 等指标，并按问题主题组做配对 bootstrap。没有全量相关性标注时，不能把 seed Recall 或未审阅负例当成全库真实准确率。指标可以观察排名变化，但问题设计与标签质量同样影响结论。

## 四、为什么模型请求还要缓存、费用限制和脱敏记录？

离线实验可能对数千块文档重复请求向量。`bailian.py` 用请求内容、模型、维度和 query/document 类型构造缓存键，已算过的相同输入可以复用；请求日志只保留哈希、状态、时延及用量元信息，避免把密钥和全部招聘文本写进日志。`cli.py` 只有在显式 `--execute` 后才触发付费模型请求，并允许设置次数与软件估计费用保护。

缓存节省请求费，但也意味着复核历史结果时应核对模型版本和快照哈希；软件费用保护不是供应商账单的绝对上限。实验产物保存在被 Git 忽略的 `runtime/experiments/`，不会自动替换生产数据库。

## 五、目前究竟验证到了哪里？

第一轮真实 Qwen Embedding 实验已经完成，显示章节分块有些问题提升、有些问题退化；BM25 对明确技术词也有很强的种子表现。Qwen Rerank 的小探针已通过，但**完整第二轮重排尚未运行**，因此没有可以归因给完整 Rerank 的实际收益结论。

代码中 `runner.py` 组织冻结、召回、候选池、重排与报告；`metrics.py` 负责指标，`bailian.py` 负责模型请求，`cli.py` 提供命令。具体实验如何执行见[实验入口](../../experiments/README.md)，首轮的案例与局限见[实际结果](../../docs/recall-pilot-2026-10-25.md)。这套模块最重要的价值不是指标种类，而是**让我们能解释为什么一种检索方法变好了或变差了**。
