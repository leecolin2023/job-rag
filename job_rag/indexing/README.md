# 索引构建：为什么导入成功不等于可以搜索？

一条新岗位进入数据库，只说明系统已经可靠保存了来源文字。要让它参加 BM25 或向量检索，还必须将正文变为查询用的 Chunk，并确保它与**当前版本的岗位**一致。尤其当 Embedding 来自远程服务时，索引生成可能超时、限流或失败。因此项目让数据导入和索引执行成为两个独立步骤。

## 一、索引任务怎样产生？

预处理中的 `import_csv()` 保存岗位和版本时，调用 `tasks.py::enqueue()` 在**同一数据库事务**里登记任务。任务关联三个关键对象：岗位标识、岗位版本、当前配置的索引签名。`enqueue()` 不提交自己的事务，也不请求模型。即使此时外部模型不可用，新岗位仍可正确落库。

任务先为 `pending`，处理完成后改为 `done`；失败为 `failed`，版本/签名过期为 `obsolete`。为什么要有“过期”？因为某条岗位在排队期间可能更新了两次，不能再用第一版任务覆盖第二版内容。

## 二、Worker 实际按什么顺序执行？

`worker.py::run_index_tasks()` 每次运行扫描待处理与失败任务，核对岗位版本及签名，然后调用[分块器](../chunking/README.md)生成 `Document(text, details)`。如果开启 Embedding，就通过[模型客户端](../providers/README.md)批量生成文档向量；未开启则得到等量的空向量标记，关键词索引仍然可用。

完成后，Worker 在数据库事务里再次锁定并核对版本，然后删除该岗位旧 Chunk、插入新 Chunk、更新 `indexed_version` 与 `index_signature`、把任务置为 `done`。这是一组原子更新：不能只写入一半新块，就对外宣称索引已经就绪。

~~~text
导入岗位 → pending 任务 → 核对版本 → 分块 → 可选 Embedding
                                                ↓
              事务内复核 → 替换 Chunk → 标记 indexed_version/done
~~~

如果远程请求失败，只记录错误**类型**和重试次数，不存供应商返回正文或密钥；旧版本不会被当成新版本结果返回，失败任务可以再次运行。

## 三、什么情况下可以复用向量？

重新导入岗位并不总是意味着重新调用模型。比如只改了采集日期，而构建出的 Chunk 文本与之前完全相同，并且模型、维度、分块方法等索引签名没有改变，Worker 可以复用旧向量。

反过来，更换 Embedding 模型、解析规则或分块预算，会改变索引签名。即使岗位文字没改，也应重建与新配置匹配的索引，避免同一检索请求混用不可比较的向量。

## 四、运行与限制

~~~bash
# 导入时不立即跑外部索引
job-rag import data/jobs.csv --no-index
job-rag worker

# 当前配置下重新登记所有岗位并执行索引
job-rag reindex
~~~

`worker` 是一次性的命令，不是常驻消息队列；当前设计按**单写入者**运行，不应并发启动多个导入或 Worker。带 Embedding 配置时，`worker`、`reindex` 和默认的 `import` 都可能发生实际费用。变更已有数据库结构还须先备份并按要求 `job-rag migrate`，目录重组本身不要求迁移。

代码定位：`tasks.py` 管理任务登记，`worker.py` 管理执行与原子替换。到[检索模块](../retrieval/README.md)可以看到系统怎样拒绝旧签名和旧版本索引。
