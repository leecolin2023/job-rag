# JD 为什么不能按固定长度随意切分？——Job-RAG 的分块设计与实现

这个目录解决的不是“把长字符串变短”，而是：**怎样把一份招聘 JD 变成检索单位，同时尽量不改变招聘条件的意思，并让结果能回到原文核对？**

用户说“帮我找必须掌握 vLLM 的岗位”。假设某个 JD 的**公司介绍**写“公司正在推广 vLLM”，**任职要求**写“必须掌握 Python”，**加分项**写“使用过 vLLM 者优先”。如果系统只因为命中“vLLM”就推荐它为“必备 vLLM 的岗位”，错误不在于没找到文本，而在于**命中文本脱离了所属的条件语境**。

分块是检索前对文本进行的组织。它不能替大模型理解所有逻辑，但可以尽量让关键语境留在同一个可检索单位中。

## 一、先看三种会实际发生的错误

假设一份 JD 是这样写的（教学示例，非仓库原始岗位）：

~~~text
岗位：模型服务平台工程师
公司介绍
我们为客户提供 vLLM 推理服务。
岗位职责
1. 部署与维护模型推理服务。
任职要求
1. 必须熟悉 Python。
2. 有 vLLM 部署经验者优先。
3. 熟悉 Python 或 Java，满足其一即可。
加分项
1. 有金融行业经验更佳。
~~~

**错误一：只看到关键词，看不到它是什么条件。** “公司介绍”的 vLLM 是业务背景；“任职要求”第二条虽然也有 vLLM，却写了“优先”。如果检索片段只保留关键词，后续模型可能将“提到”误当“必备”。

**错误二：切断了一条完整的条件。** 如果恰好按第 1100 个字符截断，“熟悉 Python 或 Java，满足其一”可能被切成上下两个片段。单独阅读上半句，会错误地以为 Python 是唯一必备；单独阅读下半句，则失去技术名称。

**错误三：把不相关的内容合成一个表示。** 如果公司福利、公司介绍和任职要求被装进同一个大 Chunk，BM25 或 Embedding 给的是混合文本的相关性；一段与问题很接近，不代表整个 Chunk 所包含的条件都与问题相符。

这三个错误有不同来源：第一个缺少**章节和条件语境**，第二个破坏**条目完整性**，第三个缺少**合理的检索粒度**。代码中的步骤正是围绕这三种损失安排的。

## 二、为什么先找章节，而不是直接对整篇分句？

一行“有 vLLM 经验者优先”的含义部分来自这行文字，另一部分来自所属的标题。例如“熟悉 Python”如果位于“加分项”下，不应仅因为包含“熟悉”就推成必备条件。

因此 `parse_sections()` 先识别“岗位职责”“任职要求”“加分项”“福利”“公司介绍”等标题，再把两段标题之间的正文定义为一个 Section。它主要在**行首标题位置**做规则匹配，兼容部分编号、装饰符和 Markdown 标题，而不是在全文任意位置看到“任职要求”四字就切开。否则“负责维护任职要求字段”也可能被错认成一个章节标题。

每个 Section 保留类型以及原文中的开始、结束位置。标题无法识别，或正文出现在第一个已识别标题之前时，程序保留 `unknown`，而不是强行放进“任职要求”。这样选择牺牲了部分结构化覆盖率，却避免凭格式猜测制造虚假的招聘条件。

此时解决的是“这句话处于什么章节”，**还没有解决**“这个章节内具体哪项条件成立”。

## 三、为什么要在章节里面再识别条目？

一个“任职要求”章节常常写着互相独立的 5～10 项条件。只按章节生成一个块，可能同时包含“必须 Python”和“vLLM 优先”；只按句号分割，又可能把一条含续行或多句说明的要求拆碎。

`item_spans()` 因此优先寻找以数字、序号和项目符号开头的条目，把条目及其后续行视为一个初始单位。没有可识别条目符号时，再按行组织。这是一种利用招聘 JD 常见排版的折中：**尽量保持一项要求的上下文，同时允许在同一章节内把不同要求分开**。

例如上面的“必须熟悉 Python”和“有 vLLM 经验者优先”可以先被识别为两项。这一步只确定*文字边界*，并不判断用户是否符合要求。未按常规格式写出的复杂段落也可能无法完美拆分，不能把行分割当成句法分析。

## 四、为什么还需要一个保守的条件标签？

到这里我们知道每个条目属于哪个章节，却仍然面临一件事：**相近的技术词可能具有不同的招聘约束**。

`condition_level()` 并不是用大模型推理逻辑，而是利用章节类型和明确的提示词，给检索块附一层粗粒度注释。

- “必须熟悉 Python”倾向 `required`。
- “有 vLLM 经验者优先”倾向 `preferred`。
- “不要求算法研发经验”倾向 `not_required`。
- “Python 或 Java 满足其一”涉及替代关系，标为 `mixed`，不强行将两者都判断为必备。
- “公司介绍里谈 vLLM”不应推断候选人要求，标为 `unspecified`。

为什么不把所有“任职要求”下的条目都标成 `required`？因为任职要求章节也经常写“有经验者优先”“优秀者可放宽”。代码先检查否定、优先、明确要求和例外等词；出现互相冲突或替代关系时倾向保守的 `mixed`，避免**一个标签覆盖多个相反条件**。

但保守并不等于正确理解。代码的正则只看有限词项，不能完整分析逻辑作用域。例如“必须优先保障服务稳定”中的“优先”是工作职责描述，不是招聘加分条件；代码因此对“岗位职责、福利、公司介绍”章节直接使用 `unspecified`。即便如此，复杂 JD 依然需要后续模型读完整原句。

这里的标签应理解为**检索提示和待复核注释**，绝不是已经存入业务事实库的准确判断。

## 五、为什么不立即把每条要求都存成独立 Chunk？

条目越小，单个技术词越突出，却也越容易失去必要上下文；条目越大，语境更完整，却可能引入其他条件的噪声。系统不能无限细切，也不该把整篇 JD 做成一个块。

`build_documents()` 在“**同一章节、相同条件性质、完整条目、预算容许**”的约束下，把相邻条目合并。也就是说，`required` 的条目不应无差别地与 `preferred` 的条目打包成同一个块。这样降低了某个块中混杂不同约束的机会，又不至于每个短句都增加一次索引开销。

遇到一个条目本身超过预算时，`_split_long()` 尽量先找到可用的句末边界；如果完整句仍放不下，才按照实际字符/字节/Token 预算硬切。硬切会记录 `hard_split` 和相同的 `continuation_id`，告诉下游：“这几个片段原来来自同一条要求，不能随意独立解释。”

当前默认 `section_typed` 的预算是 **1100 个 Unicode 字符**，不是“模型最多处理 1100 Token”；`utf8_bytes` 是字节数，`tokens` 只有在显式提供本地 tokenizer 文件时才能计算。代码将**用于检索的头部**也纳入结构化策略的预算，避免名义上限制 1100，实际却重复加上很长头部。字符预算并非供应商真实 Token 计费口径。

## 六、为什么要给块额外加标题，同时保留原文偏移？

真正参与相似度计算的是 `Document.text`。它可能长成这样（示意，不是实际运行输出）：

~~~text
岗位：模型服务平台工程师
章节：任职要求
条件性质：优先/加分条件，非明确必备
原文：
2. 有 vLLM 部署经验者优先。
~~~

如果只有 `2. 有 vLLM 部署经验者优先。`，模型对其属于哪个岗位、什么章节的判断可能不够稳定。加入岗位标题和章节提示，是为了让**局部文本在脱离长 JD 后，仍有最基本的语境**。是否提高检索排名属于实验问题，不是代码设计能直接保证的结论。

另一个输出 `Document.details` 存放原文起止位置、章节、条件注释、条目连续性和解析版本。代码保存的偏移是 Python **Unicode 码点下标**：`description[source_start:source_end]` 应当能够还原对应的 `raw_text`。这是因为“检索时看到的文本”和“招聘方原来写的文字”必须能互相定位；若日后发现条件标签错了，系统仍有依据重新判断。

注意：索引正文包含额外头部；不能拿索引正文直接和原始 JD 做字节等同。原文及其版本由[存储层](../storage/README.md)负责保存，分块器只生成可重建的派生结果。

## 七、为什么代码还保留四套分块策略？

因为“设计上更合理”并不等于“在真实查询上更好”。`legacy` 保留旧的段落/字符切分与重复头部；`fixed_compact` 尽量沿用相同边界却减少头部；`section_compact` 改用章节/条目边界；`section_typed` 在结构边界上增加条件性质提示。

这四者能帮助区分几个问题：效果变化是因为减少重复元数据，还是改变边界，还是加入了招聘条件提示？`section_compact` 与 `section_typed` 的构建还特意为预算预留相同的 typed 头部空间，以尽量保持正文边界一致，便于考察**标签文本本身**的影响。

首轮[真实 Embedding 实验](../../docs/recall-pilot-2026-10-25.md)表明，结构分块对一些查询提高了种子岗位排名，对另一些查询却退化；加条件提示也没有稳定带来收益。这说明章节完整性和检索准确率并不是同一件事。工程上保留可比较的策略，才有机会根据实际问题选择，而不是凭直觉永久锁定一个“先进算法”。

## 八、这段代码在整个知识库中起什么作用？

数据进入系统时，[预处理](../preprocessing/README.md)保存 JD 并登记索引任务；[索引 Worker](../indexing/README.md)调用 `build_documents()`，把返回的块交给[模型客户端](../providers/README.md)可选生成向量，再存入 `chunks`；[检索](../retrieval/README.md)找到候选块后，会连同证据元数据返回给调用方，并可进一步读取完整 JD。

具体代码主要在 `core.py`：`parse_sections()` 找章节，`item_spans()` 确定条目，`condition_level()` 附规则标签，`_split_long()` 控制过长内容，`build_documents()` 组装输出；`legacy.py` 保留历史算法；`__init__.py` 提供公共导入入口：

~~~python
from job_rag.chunking import build_documents

documents = build_documents(job_row, strategy="section_typed", size=1100)
for doc in documents:
    assert job_row["description"][doc.details["source_start"]:doc.details["source_end"]] == doc.details["raw_text"]
~~~

**这套设计的最终边界**是：尽量不丢失招聘语境、便于局部检索、允许回查原文；但它不理解所有语义，不会自动得到“用户满足岗位必备要求”的结论。后续必须结合[全文读取与业务判断](../querying/README.md)才能把“检索命中”变成“有证据的招聘判断”。
