# JD 数据应该如何切分？——结合招聘文本特点设计 RAG 分块策略

这个目录解决的不是“把长字符串变短”，而是：**怎样把一份招聘 JD 变成检索单位，同时尽量不改变招聘条件的意思，并让结果能回到原文核对？**

用户说“帮我找必须掌握 vLLM 的岗位”。假设某个 JD 的**公司介绍**写“公司正在推广 vLLM”，**任职要求**写“必须掌握 Python”，**加分项**写“使用过 vLLM 者优先”。如果系统只因为命中“vLLM”就推荐它为“必备 vLLM 的岗位”，错误不在于没找到文本，而在于**命中文本脱离了所属的条件语境**。

分块是检索前对文本进行的组织。它不能替大模型理解所有逻辑，但可以尽量让关键语境留在同一个可检索单位中。

## 一、先看三种会实际发生的错误

假设一份 JD 是这样写的（教学示例，非仓库原始岗位）：

~~~text
岗位：模型服务平台工程师
公司介绍
我们为客户提供 vLLM 推理服务。
岗位职责
1. 部署与维护模型推理服务。
任职要求
1. 必须熟悉 Python。
2. 有 vLLM 部署经验者优先。
3. 熟悉 Python 或 Java，满足其一即可。
加分项
1. 有金融行业经验更佳。
~~~

**错误一：只看到关键词，看不到它是什么条件。** “公司介绍”的 vLLM 是业务背景；“任职要求”第二条虽然也有 vLLM，却写了“优先”。如果检索片段只保留关键词，后续模型可能将“提到”误当“必备”。

**错误二：切断了一条完整的条件。** 如果恰好按第 1100 个字符截断，“熟悉 Python 或 Java，满足其一”可能被切成上下两个片段。单独阅读上半句，会错误地以为 Python 是唯一必备；单独阅读下半句，则失去技术名称。

**错误三：把不相关的内容合成一个表示。** 如果公司福利、公司介绍和任职要求被装进同一个大 Chunk，BM25 或 Embedding 给的是混合文本的相关性；一段与问题很接近，不代表整个 Chunk 所包含的条件都与问题相符。

这三个错误有不同来源：第一个缺少**章节和条件语境**，第二个破坏**条目完整性**，第三个缺少**合理的检索粒度**。代码中的步骤正是围绕这三种损失安排的。

## 二、为什么先找章节，而不是直接对整篇分句？

一行“有 vLLM 经验者优先”的含义部分来自这行文字，另一部分来自所属的标题。例如“熟悉 Python”如果位于“加分项”下，不应仅因为包含“熟悉”就推成必备条件。

因此 `parse_sections()` 先识别“岗位职责”“任职要求”“加分项”“福利”“公司介绍”等标题，再把两段标题之间的正文定义为一个 Section。它主要在**行首标题位置**做规则匹配，兼容部分编号、装饰符和 Markdown 标题，而不是在全文任意位置看到“任职要求”四字就切开。否则“负责维护任职要求字段”也可能被错认成一个章节标题。

每个 Section 保留类型以及原文中的开始、结束位置。标题无法识别，或正文出现在第一个已识别标题之前时，程序保留 `unknown`，而不是强行放进“任职要求”。这样选择牺牲了部分结构化覆盖率，却避免凭格式猜测制造虚假的招聘条件。

此时解决的是“这句话处于什么章节”，**还没有解决**“这个章节内具体哪项条件成立”。

## 三、为什么要在章节里面再识别条目？

一个“任职要求”章节常常写着互相独立的 5～10 项条件。只按章节生成一个块，可能同时包含“必须 Python”和“vLLM 优先”；只按句号分割，又可能把一条含续行或多句说明的要求拆碎。

`item_spans()` 因此优先寻找以数字、序号和项目符号开头的条目，把条目及其后续行视为一个初始单位。没有可识别条目符号时，再按行组织。这是一种利用招聘 JD 常见排版的折中：**尽量保持一项要求的上下文，同时允许在同一章节内把不同要求分开**。

例如上面的“必须熟悉 Python”和“有 vLLM 经验者优先”可以先被识别为两项。这一步只确定*文字边界*，并不判断用户是否符合要求。未按常规格式写出的复杂段落也可能无法完美拆分，不能把行分割当成句法分析。

## 四、为什么会有“必须、优先”这些标签？先从用户要作出的判断推导

在最初的场景里，用户只问：“**哪些岗位提到了 vLLM？**”这时不用给 JD 定义 `required` 或 `preferred`。在正文里找到 vLLM，再展示来源，就可以完成这项**字面检索**任务。

后来用户问：“**哪些岗位必须掌握 vLLM？我不会 vLLM，还能不能投递？**”问题发生了变化：现在不仅要知道技能有没有出现，还要知道**招聘方对它的要求性质**。如果一份 JD 写“必须有 vLLM 部署经验”，另一份写“有 vLLM 经验者优先”，两者都命中关键词，却会影响求职者作出不同决定。

为了保留这种会改变判断的差异，我们才需要提出一个业务属性，例如“**要求强度**（requirement strength）”。最小的概念模型可以先区分“必备”“优先”以及“无法明确判断”。`required` 和 `preferred` 是这种业务区分在现有代码里的简化表达，**不是 RAG 算法自带的分类标准**。

~~~text
用户只要找“出现过 vLLM” → 是否出现这个词 → 字面匹配即可
用户还要找“必须掌握 vLLM” → 需区分必备与优先 → 引入要求强度
用户要找“必须有生产部署经验” → 还需识别工作任务/能力深度 → 仅有要求强度不够
~~~

这个顺序说明了标签的来源：**先有应用问题，发现已有信息不足以支持判断，再增加表达差异的数据属性**。如果某个标签既不影响候选检索，也不帮助核验、筛选、比较或统计，就没有必要为了让标签表看起来全面而提前定义它。

### 为什么当前实现还不等于一个完整的“要求强度”模型？

真实招聘语句比“必须/优先”复杂得多：

| 原句（教学示例） | 希望保留的差异 | 当前 `condition_level()` 可能输出 |
|---|---|---|
| 必须掌握 Python | 一项明确要求 | `required` |
| 有 vLLM 经验者优先 | 不是明确必备 | `preferred` |
| 不要求算法研发经验 | 明确排除某项门槛 | `not_required` |
| 熟悉 Python 或 Java，满足其一 | 两项之间是替代关系 | `mixed` |
| 熟悉 Python，RAG 经验优先 | 同一条里有不同强度的条件 | `mixed` |
| 负责部署生产推理服务（位于岗位职责） | 讲工作内容，非直接的任职门槛 | `unspecified` |

这里要留意：现有五个值**并非同一业务维度下严格互斥且完整的五种强度**。`required/preferred` 较接近要求强度；`not_required` 是明确的非要求/否定；`mixed` 告诉我们句子里存在多种要求或逻辑例外；`unspecified` 则表示当前规则无法得出明确标签。

例如“Python 或 Java 满足其一”，理想的业务表达是**至少满足其中一项**。它不能被解释成“Python 和 Java 都必备”，也不能只留下一个模糊的“mixed”就声称已经完成招聘逻辑抽取。当前 `mixed` 更像一个警示：“这里的条件关系复杂，不能拿单一标签替代原文。”

因此，这五个值在现阶段被放在一个 `requirement_level` 字段里，是为了**给分块提供粗粒度、保守的检索提示**，而不是已经设计成熟的招聘条件数据模型。

## 五、这些标签在现有代码中究竟解决什么？为什么用保守规则而不是强制分类？

上节推导的是业务为什么需要区分条件。这一节才回到 Chunking 的具体责任：**让检索块尽量不混入不同性质的招聘条件，并在检索结果里保留一些解释线索**。

当前 `condition_level(text, section_type)` 读取**一条文本与其章节类型**，用明确词语和上下文作近似判断：

- 处在“岗位职责、公司介绍、福利”章节的文字，不被当作任职门槛，返回 `unspecified`。
- 任职要求章节的内容如果出现“优先”，可以标为 `preferred`；即使不出现“必须”，普通任职要求也可能被规则默认标为 `required`。因此 `required` 并不保证原文写过明确的强制措辞。
- 明确的“不要求”“无需”等提示可产生 `not_required`；“必须”“但需”等提示可以支持 `required`。
- 同一条里出现冲突提示、“满足其一”“可放宽”等例外或替代关系时，倾向 `mixed`，避免把它错误简化成一项无条件硬要求。

为什么现在不用 LLM 对每个条目做精确抽取？因为本阶段的任务只是**准备检索片段**：规则可复现、不需要索引每条 JD 时增加额外模型请求，也能保留不确定性；但它不会可靠理解所有招聘措辞。规则标记不准确时，最终判断仍要靠原句及更完整的上下文。

这些输出有两个真实去处。第一，`build_documents()` 尽量只合并**同章节、同标签**且未超过预算的相邻条目，降低“必备 Python”和“vLLM 优先”被混进同一 Chunk 的机会。第二，在 `section_typed` 策略中，`_header()` 将“条件性质：优先/加分条件”等提示写进检索文本，`details.requirement_level` 保存标签供下游展示与核对。

**当前代码没有把 `requirement_level=required` 直接转换成“这个岗位必须具备某项技能”的 SQL 过滤条件。** 标签作用于一个条目或被合并后的**文本块**，并没有精确绑定到其中每个技能实体。它是辅助召回与证据阅读的注释，不是岗位技能需求的最终事实。

## 六、如果以后还要增加标签，应该怎么决定加什么、加在哪里？

假设新的用户问题是：“哪些岗位只是**调用 vLLM API**，哪些要求**部署、优化推理服务**？”这时 `required` 与 `preferred` 根本不能区分答案：它们只描述**是否必须具备能力**，不描述**能力用到什么程度**。

如果分析真实 JD 后确认这个差异会改变搜索、推荐或统计结果，就可能需要另一个独立属性，例如 `competency_depth`（能力深度），候选值可以是 `awareness`（了解）、`usage`（使用）、`deployment`（部署）、`optimization`（优化）等。它们是**未来可能采用的业务分类示例，不是现有项目已实现的代码，也不是行业统一标准**。

例如“有 vLLM 生产部署经验者优先”，可能同时需要表达：

~~~json
{
  "skill": "vLLM",
  "requirement_strength": "preferred",
  "competency_depth": "deployment",
  "evidence": "有 vLLM 生产部署经验者优先"
}
~~~

这里“优先”和“部署”并不冲突，因为它们回答的是两个不同问题。如果把 `deployment` 直接加进当前 `requirement_level` 的取值列表，系统反而必须在“优先”和“部署”之间二选一，丢掉重要信息。

再如“Python 或 Java 满足其一”，问题不是能力深度，而是条件间的**逻辑关系**。未来如果需要程序严格判断候选人能否达到资格条件，可能要将技能实体与 `OR` 关系作为一个整体约束表示，而不能把两个词都打上“必备”标签。这比给 Chunk 增加一个新的单值枚举复杂得多。

一个实用的设计顺序是：

1. **明确用户要作出的判断。** 是筛选“必备技能”、识别“生产部署岗位”，还是统计某技术的需求强度？不要先罗列一套自认为全面的标签。
2. **找出会改变结果的原文差异。** 用实际 JD 比较“必须/优先”“调用 API/部署”“Python 和 Java/Python 或 Java”等表达；若不区分会产生错误结论，才有建模必要。
3. **判断这是新取值还是新维度。** 仍在描述要求强度，可以讨论扩展这个维度；若描述能力深度、逻辑关系或工作任务，则应建立独立属性。无法确定时要保留未知，而不是强行归类。
4. **决定属性附着在哪个对象上。** 章节标签回答“这段文字属于哪里”，Chunk 标签帮助检索，而“vLLM 是否必备、要求部署到何种程度”往往需要附着在**某条具体技能要求**上。
5. **用实际问题验证收益。** 标签若不能帮助目标问题减少误判或提升可解释性，就不应因其名称漂亮而扩大体系。

这一点也划出了 **Chunking 和业务知识建模的分界**：Chunking 负责把原文组织为便于召回和核对的文本单位；要准确统计“多少岗位**必须**具备 vLLM 生产部署经验”，更合理的方向是另建逐要求的结构化事实抽取与证据核验机制，而不是无限加宽 `condition_level()` 这一个枚举。

**在当前代码里不要直接把上述未来属性当作已存在字段。** 如果今后真的改变现有 Chunk 标签或结构，除了修改识别规则，还必须考虑 `_header()`、`Document.details`、下游读取方式、解析/分块版本、索引签名与重建，并为典型正例、否定、例外和未知情况增加测试。能否改善检索，应通过相同查询和数据的实验验证，而不是仅凭新标签更细就判断有效。

## 七、为什么不立即把每条要求都存成独立 Chunk？

条目越小，单个技术词越突出，却也越容易失去必要上下文；条目越大，语境更完整，却可能引入其他条件的噪声。系统不能无限细切，也不该把整篇 JD 做成一个块。

`build_documents()` 在“**同一章节、相同条件性质、完整条目、预算容许**”的约束下，把相邻条目合并。也就是说，`required` 的条目不应无差别地与 `preferred` 的条目打包成同一个块。这样降低了某个块中混杂不同约束的机会，又不至于每个短句都增加一次索引开销。

遇到一个条目本身超过预算时，`_split_long()` 尽量先找到可用的句末边界；如果完整句仍放不下，才按照实际字符/字节/Token 预算硬切。硬切会记录 `hard_split` 和相同的 `continuation_id`，告诉下游：“这几个片段原来来自同一条要求，不能随意独立解释。”

当前默认 `section_typed` 的预算是 **1100 个 Unicode 字符**，不是“模型最多处理 1100 Token”；`utf8_bytes` 是字节数，`tokens` 只有在显式提供本地 tokenizer 文件时才能计算。代码将**用于检索的头部**也纳入结构化策略的预算，避免名义上限制 1100，实际却重复加上很长头部。字符预算并非供应商真实 Token 计费口径。

## 八、为什么要给块额外加标题，同时保留原文偏移？

真正参与相似度计算的是 `Document.text`。它可能长成这样（示意，不是实际运行输出）：

~~~text
岗位：模型服务平台工程师
章节：任职要求
条件性质：优先/加分条件，非明确必备
原文：
2. 有 vLLM 部署经验者优先。
~~~

如果只有 `2. 有 vLLM 部署经验者优先。`，模型对其属于哪个岗位、什么章节的判断可能不够稳定。加入岗位标题和章节提示，是为了让**局部文本在脱离长 JD 后，仍有最基本的语境**。是否提高检索排名属于实验问题，不是代码设计能直接保证的结论。

另一个输出 `Document.details` 存放原文起止位置、章节、条件注释、条目连续性和解析版本。代码保存的偏移是 Python **Unicode 码点下标**：`description[source_start:source_end]` 应当能够还原对应的 `raw_text`。这是因为“检索时看到的文本”和“招聘方原来写的文字”必须能互相定位；若日后发现条件标签错了，系统仍有依据重新判断。

注意：索引正文包含额外头部；不能拿索引正文直接和原始 JD 做字节等同。原文及其版本由[存储层](../storage/README.md)负责保存，分块器只生成可重建的派生结果。

## 九、为什么代码还保留四套分块策略？

因为“设计上更合理”并不等于“在真实查询上更好”。`legacy` 保留旧的段落/字符切分与重复头部；`fixed_compact` 尽量沿用相同边界却减少头部；`section_compact` 改用章节/条目边界；`section_typed` 在结构边界上增加条件性质提示。

这四者能帮助区分几个问题：效果变化是因为减少重复元数据，还是改变边界，还是加入了招聘条件提示？`section_compact` 与 `section_typed` 的构建还特意为预算预留相同的 typed 头部空间，以尽量保持正文边界一致，便于考察**标签文本本身**的影响。

首轮[真实 Embedding 实验](../../docs/recall-pilot-2026-10-25.md)表明，结构分块对一些查询提高了种子岗位排名，对另一些查询却退化；加条件提示也没有稳定带来收益。这说明章节完整性和检索准确率并不是同一件事。工程上保留可比较的策略，才有机会根据实际问题选择，而不是凭直觉永久锁定一个“先进算法”。

## 十、这段代码在整个知识库中起什么作用？

数据进入系统时，[预处理](../preprocessing/README.md)保存 JD 并登记索引任务；[索引 Worker](../indexing/README.md)调用 `build_documents()`，把返回的块交给[模型客户端](../providers/README.md)可选生成向量，再存入 `chunks`；[检索](../retrieval/README.md)找到候选块后，会连同证据元数据返回给调用方，并可进一步读取完整 JD。

具体代码主要在 `core.py`：`parse_sections()` 找章节，`item_spans()` 确定条目，`condition_level()` 附规则标签，`_split_long()` 控制过长内容，`build_documents()` 组装输出；`legacy.py` 保留历史算法；`__init__.py` 提供公共导入入口：

~~~python
from job_rag.chunking import build_documents

documents = build_documents(job_row, strategy="section_typed", size=1100)
for doc in documents:
    assert job_row["description"][doc.details["source_start"]:doc.details["source_end"]] == doc.details["raw_text"]
~~~

**这套设计的最终边界**是：尽量不丢失招聘语境、便于局部检索、允许回查原文；但它不理解所有语义，不会自动得到“用户满足岗位必备要求”的结论。后续必须结合[全文读取与业务判断](../querying/README.md)才能把“检索命中”变成“有证据的招聘判断”。
