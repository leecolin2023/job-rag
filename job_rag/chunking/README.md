# JD 数据应该如何切分？——从检索单位设计到招聘文本的分块策略

构建招聘岗位知识库时，原始数据通常是一条岗位记录对应一份完整 JD（Job Description，职位描述）。用户却可能只问：“哪些岗位负责 RAG 知识库的建设？”“哪些岗位将 vLLM 部署列为必备条件？”如果系统要根据这些问题找出岗位，就必须决定：**应该拿整份 JD 去匹配问题，还是拿 JD 中更小的片段去匹配？匹配到片段之后，又如何恢复这份岗位的完整含义？**

这不是一个单纯的字符串切割问题。要设计切分方式，首先需要理解检索系统如何利用文本，然后才能根据 JD 的结构和业务要求确定切分边界。以下先讲通用方法，再解释 Job-RAG 为什么这样实现。

## 一、什么是检索单位？为什么 RAG 需要考虑文本切分？

假设知识库里有一百份文档。用户提出问题后，检索系统需要比较问题与知识库内容的相关性，找出值得交给后续模型阅读的候选文本。

这个过程中，**检索单位（retrieval unit）就是系统实际拿来建立检索索引、计算匹配程度并参与候选排序的基本内容单位**。它可以是一整份文档、一段话、一个章节，也可以是切分后生成的 Chunk。检索单位的大小和边界，是系统设计的选择，不存在所有 RAG 都必须采用的固定长度。

例如一本技术手册包含“模型部署”“故障排查”“监控告警”三个章节。若整本手册只建立一条向量，检索“为什么推理延迟升高”时，检索模型只能用整本手册的混合内容来计算相关性；它无法通过这一个向量直接知道相关证据集中在哪一节。

如果把手册划成多个检索单位，系统就能分别比较“模型部署”“故障排查”“监控告警”，让与问题最接近的片段获得更好的排序机会，再把命中的文本交给后续模型。

但反过来，如果将“延迟升高可能由 KV Cache 占用增加导致”切成“延迟升高可能由”“KV Cache 占用增加导致”两个单位，单个片段又不再保留完整的因果关系。**切分可以减少无关内容的干扰，也可能破坏原本完整的表达。**

因此分块（Chunking）的目的，不是将长文本切得尽可能短，而是**组织出既容易被找到，又保留足够含义、可以核对来源的检索单位**。

并不是所有文档都必须切分。若文档本身很短且主题单一，整篇作为一个检索单位可能更简单；若问题需要跨多个章节才能回答，仅检索一个小片段也可能不够，需要扩大上下文或回读全文。切分解决的是检索粒度的问题，而不是自动解决全部理解问题。

### 检索单位、业务对象与证据单位不是同一回事

理解这个区分，对 Job-RAG 尤其重要：

| 层次 | 在招聘知识库里是什么 | 它负责什么 |
|---|---|---|
| **业务对象** | 一条完整岗位及其 JD | 用户最终要比较、筛选、投递的对象 |
| **检索单位** | 一份 JD 中的某个 Chunk | 在 BM25 / Embedding 中与问题匹配、参与排序 |
| **证据来源** | JD 中可以回查的原始句子或条目 | 支撑“这份岗位究竟要求什么”的判断 |

比如用户想找“有生产环境 vLLM 部署经验要求”的职位，系统可能首先命中某个 Chunk，但最后应该向用户展示**岗位**，而不是把一段招聘要求当成一个独立职位；如果要认定 vLLM 是必备项，还需要核对这个 Chunk 对应的**原文条款**。

当前 Job-RAG 正是以 Chunk 为检索和初步排序单位，随后按岗位 ID 聚合命中结果，并允许读取完整 JD。一个岗位可以对应多个 Chunk，而不是每个 Chunk 都是一条岗位。

## 二、设计检索单位的一般思路是什么？

知道要切分，并不等于知道应该在哪里切。相比先设定“每块 500 或 1000 字”，更合理的起点是：**用户会问什么？为了正确理解与回答这些问题，一个检索片段需要保留多少上下文？**

### 1. 如何确定检索单位的切分边界和大小？

如果用户问“某种技术是什么”，可能需要完整定义和相邻解释；如果问“某个流程由谁审批”，可能需要步骤及所属角色；如果问“某合同是否允许提前还款”，仅有“允许”两个字不够，还要保留限制条件与例外。

因此，首先要寻找**语义相对完整的基本片段**：它不必独立回答所有问题，但脱离整篇原文后，仍能表达清楚主要意思，不至于把条件、否定、因果或替代关系切断。

但完整并不意味着越长越好。检索单位太大，相关内容可能被无关文字淹没，后续也要阅读更多上下文；太小，则可能丢失标题、条件、前后指代，且需要建立更多索引。**切分粒度需要同时兼顾定位精度与语义完整性。**

一种通用做法是：**先结合用户任务和文档结构，找出相对完整的基本片段；再根据片段间的关联程度与长度预算，决定是否合并或进一步拆分。** 技术手册可能以小节为候选边界，合同可能以条款为单位，会议纪要可能以议题和决议为单位；这些结构是帮助判断边界的线索，不是必须机械遵守的格式。

这里要区分**基本片段与最终 Chunk**。一条完整要求可以是基本片段，但若它很短，可以与语境相容的相邻要求合并；如果一条要求过长，又可能必须分成多个 Chunk，并保留它们原本属于同一条要求的关联。由此得到的不是“固定切多少字”的公式，而是一种从**任务需求、语义边界到实际检索粒度**的设计方法。

### 2. 切开以后，如何保留原来的上下文？

完整句子仍可能依赖它的章节标题。例如一个孤立条目写“熟悉 Python”，如果不知道其属于“任职要求”还是“加分项”，系统就无法仅凭这句话判断招聘条件。

常见做法是把必要的**父级上下文**随检索单位保留，例如文档标题、章节标题或范围提示。但不能无限重复整篇文档的元信息，否则每个 Chunk 都会出现大量与当前问题无关的词，反而影响排名。

同时，索引里为了检索而添加的标题或提示不等于原作者写的正文。应分别保留**检索表示**与**原始内容及位置**，这样检索命中后能检查上下文是否正确，必要时回读全文。

### 3. 如何让方案满足模型与系统的实际约束？

当基本片段和上下文确定之后，才应该考虑字符数、字节数或 Token 数的预算。预算限制的是一次索引或输入能够容纳多少文字，**不应该反过来成为主要的语义边界**。

固定长度切分的优点是实现容易、成本可控、适合作为对照基线；沿自然边界切分能更好利用文档结构，却有解析失败、块长不均和额外复杂度。是否使用重叠窗口、何时强制截断，也应服务于特定资料中的跨边界风险，而不是把“重叠越多”视为通用最优解。

最终检索单位不是只由分块器决定的。检索方式、候选聚合、回读全文、评测查询和成本约束共同决定什么粒度有效。**所谓“合理切分”，必须通过真实任务检验，而不只是看切出来的文字整不整齐。**

## 三、把通用方法用于 JD，先要理解招聘文本有哪些特点

一份 JD 看起来只是一个长字符串，实际却承载不同层次的信息。考虑下面的教学示例（非仓库的真实招聘记录）：

~~~text
岗位：模型服务平台工程师

公司介绍
我们为客户提供 vLLM 推理服务。

岗位职责
1. 负责生产推理服务部署、监控与性能优化。

任职要求
1. 必须熟悉 Python。
2. 具有 vLLM 部署经验者优先。
3. 熟悉 Python 或 Java，满足其一即可。

加分项
1. 有金融行业项目经验更佳。
~~~

假设问题是“**哪些岗位必须掌握 vLLM？**”这份 JD 中出现了两次 vLLM，但公司介绍只是背景，任职要求又写着“优先”，都不能直接证明 vLLM 是必备条件。

如果问题换成“**哪些岗位的工作涉及模型推理服务的部署和优化？**”，真正重要的证据是“岗位职责”里的一项，而不是技能表里是否有一个标着“必备”的 vLLM 标签。

由此可见，JD 至少有四个值得影响切分方式的特点：

**首先，全文并不是同一种语义。** 公司介绍讲业务，岗位职责讲入职后要做什么，任职要求讲候选人应该具备什么，加分项讲优势，福利讲待遇。相同技术词在不同章节中的招聘含义可能不同。将它们混在一个 Chunk，容易把背景、工作任务和候选人门槛混为一谈。

**其次，同一个章节内部包含多条不同要求。** “必须 Python”“vLLM 优先”“Python 或 Java 满足其一”不能直接当作同一个不可分的条件；但第三条中的“或”“满足其一”也不能被任意切开。

**再次，排版规则并不稳定。** JD 可能用“1.”“①”“•”表示条目，也可能用自然段、连续行、加粗标题，甚至没有明确标题。只依靠固定字符位置会无视这些线索；只靠标题正则又无法覆盖所有形式。

**最后，用户要得到的是可核对的岗位结论。** 每个命中片段应当能返回到完整 JD 的对应位置；否则“vLLM 必备还是优先”一旦判断有争议，便缺少查证依据。

因此，对 Job-RAG 来说，一个自然的设计方向是：**以完整 JD 作为业务对象，以岗位中的主题或条件相对完整的片段作为检索单位，保留章节语境与来源位置，命中后再按岗位汇总和核验。**

## 四、根据这些特点，JD 的切分策略应该怎样推导？

我们不是先决定必须用章节、条目和标签，然后再把 JD 塞进这套框架，而是逐项解决上节提出的需求。

### 先保证不同用途的内容不被无差别混合

既然“公司介绍提到 vLLM”与“任职要求必须掌握 vLLM”的含义不同，就需要让 Chunk 至少知道自己来自 JD 的哪个区域。因此，识别“公司介绍、岗位职责、任职要求、加分项”等结构，是一种成本较低的上下文保留办法。

这意味着章节边界适合作为**避免误合并的约束**。但章节本身不一定就是最终 Chunk：一个任职要求章节可能有许多独立条件，把所有要求放在同一块依旧可能造成混淆。

### 再找到能够相对独立理解的基本内容

JD 经常逐条描述工作职责和任职门槛，因此**一条完整要求及其续行**是比任意字符数更合适的候选基本片段。

例如“Python 或 Java 满足其一即可”应该整体保留；而“必须熟悉 Python”和“vLLM 经验优先”通常应先作为两条独立内容处理。这不表示每条都必须独占一个索引块：如果两条内容很短、来自同一章节且语境相容，仍可在长度预算内合并。

这样的推导得到的是“**先识别有意义的边界，再按上下文和预算组合**”，而不是“看到一个编号就强制生成一个 Chunk”。

### 如果用户需要区分必备与优先，才考虑条件信息

对于“有哪些 JD 提到 vLLM”这种查询，章节加原文可能已经足够；但如果用户要筛选“vLLM 是必备项的岗位”，只保存技术词就会遗漏一个影响求职决策的差异：**招聘方究竟要求必须具备，还是只是优先考虑？**

因此可以考虑引入“要求强度”这一业务属性。概念上先区分必备、优先及未知即可。不过真实 JD 还会写“不要求”“可放宽”“Python 或 Java 满足其一”，它们涉及否定、例外和逻辑关系，不是同一个强度维度。

这一步的设计原则是：**标签来自业务需要回答的判断，不是 RAG 规定的固定分类。** 如果目标变成比较“调用 API”与“生产部署”，需要考虑的是“能力深度”这个独立维度，而不能将 `deployment` 直接塞进“必备/优先”枚举里。

更重要的是，不应该把一个整块的粗标签误当成“块中每个技能都有同样的要求性质”。对严格的必备条件统计，最终要按具体技能和条件关系建立可核验事实，而不只是给 Chunk 加提示。

### 最后才把基本片段组合成有预算的检索单位

现在我们有了“章节范围”“完整条目”和可选的“条件语境”，才可以决定实际生成多少 Chunk。

设计上的目标是：相邻且相容的短条目可合并，避免索引过碎；章节或条件明显不同的条目尽量不混合；单条太长时优先沿完整句子切，仍超预算则记录被迫截断的事实。检索文本可重复必要的岗位及章节信息，元数据则记录它来自原文的哪里。

**决定 Chunk 的不是某一个步骤，而是它能否同时满足可定位、可理解、可控制成本三项约束。**

## 五、把一份 JD 按这个方案切分，会得到什么？

沿用第三节的示例，如果我们采用结构化方式，可以从概念上形成以下候选检索单位（**示意边界，不表示当前代码一定严格生成这六块**）：

| 片段所处语境 | 内容 | 检索时应避免的误解 |
|---|---|---|
| 公司介绍 | 我们为客户提供 vLLM 推理服务 | 不能推成候选人必备 vLLM |
| 岗位职责 | 负责生产推理服务部署、监控与性能优化 | 说明工作任务，不等于已写明入职门槛 |
| 任职要求 | 必须熟悉 Python | 需要保留“必须” |
| 任职要求 | 具有 vLLM 部署经验者优先 | 需要保留“优先” |
| 任职要求 | Python 或 Java，满足其一 | 不能误判成两项都必备 |
| 加分项 | 有金融行业项目经验更佳 | 需要保留加分语境 |

从这些片段能看到，切分不是为了让每段字数相同，而是为了让不同问题有机会找到**恰当的证据**：问生产部署工作，优先关注岗位职责；问 vLLM 是否必备，不能只看技术词出现，而要读完整条件；问金融行业经验是否需要，不能丢掉“加分项”的背景。

如果原文很短，多个同类型条目可能合并；如果一条要求很长，可能拆成几个延续片段；如果没有明确章节标题，只能保留未知语境。**正确的策略允许这些差异存在，而不是强迫每份 JD 生成固定数量的 Chunk。**

在索引时，某个候选片段可表示为（示意）：

~~~text
岗位：模型服务平台工程师
章节：任职要求
条件性质：优先/加分条件，非明确必备
原文：
2. 具有 vLLM 部署经验者优先。
~~~

其中“岗位、章节、条件性质”是为了检索增加的上下文；“原文”来自招聘文字。二者应分别对待：提示可能帮助检索理解片段，但也可能干扰相似度，因此效果需要实验验证。真正做结论时，仍应返回原文。

## 六、Job-RAG 目前是怎样把这个设计落到代码中的？

理解了通用方法与 JD 特点，再来看[分块源码](core.py)，就不需要把函数名当成一组必须背诵的步骤。

项目目前提供四种分块策略：`legacy` 按旧方式保留段落/字符分块及较长头部；`fixed_compact` 沿用旧边界但缩减头部；`section_compact` 以章节和条目为基础、使用紧凑上下文；默认的 `section_typed` 额外把条件性质写入索引文本。

结构化方案中的各个函数分别落实前面的设计选择：

| 设计上必须完成什么 | 当前实现 | 取舍与边界 |
|---|---|---|
| 从 JD 识别有意义的大范围 | `parse_sections()` 匹配已知章节标题 | 识别不了时保存 `unknown`，不强行猜测 |
| 找到相对完整的基本片段 | `item_spans()` 按常见编号、项目符号和续行组织条目 | 非标准排版可能被错误合并或拆散 |
| 对检索保留必要的条件语境 | `condition_level()` 为条目给出粗粒度标签 | 不是逐技能、逐条件的完整语义抽取 |
| 在长度限制内生成 Chunk | `_split_long()` 与 `build_documents()` 处理合并和超长切分 | 长句仍可能被迫硬切 |
| 让命中内容能回到原文 | `Document.details` 记录原文偏移、章节、条目及版本 | 偏移是 Python Unicode 码点下标 |

目前 `condition_level()` 的取值为 `required`、`preferred`、`not_required`、`mixed` 和 `unspecified`。它们不全是同一“要求强度”维度：`mixed` 还承载了复杂或替代条件，`unspecified` 代表规则没有充分信息。处在公司介绍、岗位职责或福利中的内容直接视为非明确任职门槛；在“任职要求”章节中，普通条目即使没有出现“必须”也可能被规则标为 `required`。因此这里的 `required` **不是人工核实过的硬性招聘事实**。

同一章节内，代码尽量只合并标签相同、能完整放入预算的相邻条目。过长时尽量沿句子切分，否则标记 `hard_split`，并用同一个 `continuation_id` 保留片段原本属于哪条要求。`section_compact` 和 `section_typed` 还为条件头部预留一致的预算空间，以便比较标签文本带来的变化。

默认预算是 **1100 个 Unicode 字符**，并非 1100 个模型 Token；可选 UTF-8 字节预算或显式指定本地 tokenizer 的 Token 预算。`Document.text` 是供 BM25/Embedding 使用的带上下文文本，`Document.details` 保存 `raw_text`、`source_start`、`source_end`、`section_type`、`requirement_level` 等信息。原始正文可以通过 `description[source_start:source_end]` 回查，不应将这些偏移当 UTF-8 字节下标。

~~~python
from job_rag.chunking import build_documents

chunks = build_documents(job_row, strategy="section_typed", size=1100)
for chunk in chunks:
    detail = chunk.details
    assert job_row["description"][detail["source_start"]:detail["source_end"]] == detail["raw_text"]
~~~

[索引 Worker](../indexing/README.md)调用 `build_documents()` 并按需生成 Embedding、写入数据库；[检索模块](../retrieval/README.md)对 Chunk 排名并聚合为岗位，在返回结果时提供 `evidence_details` 及有限的任职要求/加分项上下文，必要时通过[查询模块](../querying/README.md)读取完整 JD。

这意味着当前项目**不是**“先准确抽取每个技能事实，再用结构化条件过滤岗位”的系统；它仍是“分块召回候选 → 保留证据 → 进一步阅读判断”的系统。是否需要额外的逐技能事实抽取层，要由未来的业务问题决定。

## 七、怎样判断一种 JD 切分策略是否真的更好？

仅检查“有没有识别标题”“块长是否合规”，只能说明分块程序按规则运行，不能说明用户更容易找到合适的岗位。

评估至少应当覆盖三个层次：

**先检查文本有没有被错误破坏。** 从 Chunk 能否定位回原 JD？是否遗漏了“必须”“优先”“无需”“满足其一”等限制词？超长条目拆分后能否知道它们本属同一项？标题格式异常、没有标题、正文为空时会如何处理？这些是分块质量的基础。

**再检查检索能否找到相关证据。** 对“负责模型部署”“vLLM 经验优先”“有金融行业经验”分别准备真实问题，在相同语料和模型条件下比较 Top-K 里能否找到支持判断的片段，以及是否将公司介绍中的关键词误排成重要岗位要求。一个 JD 可能有多个相关片段，评估需要同时观察 Chunk 命中和**岗位级召回**。

**最后检查对求职判断是否有帮助。** 检索到技术词不等于找到适合的岗位。应让评审者结合完整 JD 判断，是否存在工作任务相关但未用同一个技术名词表达的职位，是否误把“优先”说成“必备”，以及为这一改进付出了多少索引、查询和模型调用成本。

Job-RAG 保留 `legacy`、`fixed_compact`、`section_compact`、`section_typed` 正是为了做控制变量对照，而不是默认结构化程度越高效果越好。[2026-10-25 的实际召回实验](../../docs/recall-pilot-2026-10-25.md)显示，章节分块在部分查询上改善了指定种子岗位的排名，在另一些查询上退化；增加条件提示也没有带来稳定增益。由于当时的正例标注不完整，还不能据此裁决哪种策略在真实用户问题上普遍最好。

## 八、这套方法可以迁移到其他资料吗？

可以迁移的是**思考顺序**，而不是 JD 的章节名或“必备/优先”标签。

面对合同，先考虑用户要查询条款权利、义务还是例外，再判断应以条款和附属条件为基本片段；面对操作手册，先考虑用户要找操作步骤、前提还是故障处理，再沿任务和步骤组织内容。只有当某种业务差异确实会改变检索或判断结果时，才有必要设计额外的上下文属性。

回到 JD，推导路径是：

**明确用户要找什么岗位 → 确定岗位与检索片段的区别 → 寻找有足够语境的最小内容 → 观察 JD 的章节、条目和复杂条件 → 形成有边界、有预算、可溯源的 Chunk → 用真实查询检验检索与判断效果。**

这里的第一原则不是“优先用章节分块”，而是：**检索单位应当根据用户任务与数据的表达结构共同设计；切分要为正确找到和解释证据服务。**
