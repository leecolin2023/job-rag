# JD 数据应该如何切分？——从一份招聘信息理解检索单位与分块设计

在[Retrieval：招聘 JD 应该如何检索](../retrieval/README.md)中，我们讨论了怎样从大量岗位中找到相关内容。但检索之前，还有一个更早的决定：**要把一整份 JD 交给检索系统，还是把它拆成几段？如果要拆，应该在哪里切开？**

这篇文章沿用同一份**虚构的招聘 JD**，逐步回答这些问题。先讲通用的切分思路，再解释 JD 为什么适合采用章节、条目与条件信息，最后看 Job-RAG 的实现和真实实验。文中的示意分块只是为了帮助理解，不代表代码一定生成完全相同的 Chunk。

## 一、为什么招聘 JD 要考虑切分？

### 1. 什么是检索单位？

假设你有 600 份招聘 JD。用户问：“哪些岗位负责推理服务部署？”检索系统要拿这句话与已保存的内容进行比较，找出可能相关的文本。

**检索单位（retrieval unit）**，就是系统实际拿来与问题计算匹配程度、参加检索排序的基本内容单位。

它可以是一整份 JD，也可以是其中一个章节或一个更小的 **Chunk（分块）**。检索单位并不是一个固定大小的“文本盒子”，而是我们为了方便找到相关证据，选择如何组织原文的结果。

在 Job-RAG 中要区分三个对象：

| 对象 | 具体是什么 | 用来做什么 |
|---|---|---|
| **岗位** | 一条完整的招聘记录及 JD | 用户最终要了解、比较和投递的职位 |
| **Chunk** | 从这份 JD 产生的某个检索片段 | 参加 BM25 / Embedding 的匹配和排序 |
| **原文证据** | JD 中具体的职责或条件表述 | 最后核对“这份岗位到底要求什么” |

一个岗位可以有多个 Chunk。**搜索先找到 Chunk，最终仍然要回到岗位和 JD 原文**，而不是把每个 Chunk 都当成一条独立岗位。

### 2. 整份 JD 不切，直接搜索不行吗？

可以，尤其是 JD 很短、只谈一个主题时。但一份典型 JD 可能同时包含：

- 公司在做什么产品；
- 员工入职后要负责什么；
- 应聘者必须具备什么；
- 哪些能力只是加分项；
- 福利、工作地点等其他说明。

例如同一份 JD 写着“公司为客户提供 vLLM 推理服务”，又写着“岗位负责模型部署”，还写着“vLLM 经验优先”。

如果整份 JD 只对应**一个**检索向量，Embedding 得到的是整份混合内容的表示；它不能通过这个向量直接告诉我们，命中的 vLLM 来自公司介绍还是任职要求。

把 JD 分成若干检索单位后，系统就有机会分别匹配“公司介绍”“岗位职责”“任职要求”，更容易定位相关的内容。注意：**切分改善的是定位的机会，不会自动理解招聘语义**。

### 3. 是不是切得越小越好？

也不是。假设原文写：

> 熟悉 Python 或 Java，满足其一即可。

如果恰好切成“熟悉 Python”和“或 Java，满足其一即可”，第一段看起来像单独要求 Python，原来的**二选一**关系却被破坏了。

所以存在一个基本取舍：

**块太大，容易把无关内容混在一起；块太小，容易丢掉理解条件所需的上下文。**

后面全部设计，都在解决怎样同时避免这两种问题。

## 二、准备切分时，应该先看什么？

### 1. 先想用户会问什么，而不是先规定每块多少字

不同问题需要的证据并不一样：

| 用户的问题 | 至少需要保留的内容 |
|---|---|
| “哪些岗位负责模型部署？” | 与部署有关的完整职责 |
| “vLLM 是不是必备技能？” | 技能名称、**必须/优先**等限制词及其所在章节 |
| “有 Python 或 Java 就可以吗？” | 原句中“或”“满足其一”等逻辑关系 |

这说明，设计切分时要先找到**足以表达完整意思的基本片段**。它不一定能独立回答所有求职问题，但至少不应该把决定原意的限制词切走。

例如技术手册可以优先观察小节，合同可以优先观察条款。对 JD 来说，值得优先观察的是**章节、逐条列出的职责和任职条件**。

### 2. 什么叫“基本片段”？它等于最终 Chunk 吗？

不一定。

“必须熟悉 Linux”是一条完整的基本片段，但单独占用一个 Chunk 可能过短。可以考虑与相邻、含义相容的短要求合并。

反过来，“负责模型部署、灰度发布、故障定位……（后面还有一大段）”虽然本来是一条职责，却可能太长，必须进一步拆成多个 Chunk。

因此更容易理解的顺序是：

~~~text
先根据原文结构，找出不该随便切断的基本片段
                  ↓
短且相容的片段，可以合并
                  ↓
单个片段过长，才进一步切分
                  ↓
形成最终参加检索的 Chunk
~~~

**基本片段帮助我们找边界；最终 Chunk 还要兼顾长度和检索成本。** 后文的章节识别、条目识别、条件标签与 1100 字符预算，都是为这件事服务的。

## 三、先看一份 JD，哪些地方最值得作为边界？

以下是全文使用的**教学示例**：

~~~text
岗位：模型服务平台工程师

公司介绍
我们为客户提供 vLLM 推理服务。

岗位职责
1. 负责模型推理服务部署、监控和性能优化。
2. 处理线上推理延迟异常。

任职要求
1. 必须熟悉 Linux。
2. 有 vLLM 部署经验者优先。
3. 熟悉 Python 或 Java，满足其一即可。

加分项
1. 有金融行业项目经验更佳。
~~~

用户问：“**这个岗位必须掌握 vLLM 吗？**”

这份 JD 两次提到 vLLM。但公司介绍中的出现，只证明公司涉及这种技术；任职要求则明确写着“**优先**”，并不是“必须”。

再换个问题：“**这个岗位实际做不做模型部署？**”重要证据就变成“岗位职责”中的第一条。

一个简单的观察就出现了：**相同技术词在 JD 不同位置，可能代表完全不同的含义。**

所以我们不能只决定“分成几百字”，还要决定**哪些内容不应该跨在一起**。

## 四、为什么要先识别 JD 的章节？

### 1. 章节到底解决了什么问题？

如果用户只看到：

> 有 vLLM 部署经验者优先。

这句话能说明“优先”，却还不知道它来自岗位的哪一部分。

如果附上：

> 章节：任职要求

就更容易理解它是在描述候选人的资格，而不是公司产品功能。

因此，**章节标题是一种重要的父级上下文**。它让切出来的片段仍带有原文的用途信息。

对 JD 而言，常见章节的作用不同：

| 章节 | 主要描述什么 |
|---|---|
| 公司介绍 | 企业业务、产品或背景 |
| 岗位职责 | 员工入职后要做的工作 |
| 任职要求 | 候选人需要具备的条件 |
| 加分项 | 有则更有优势的条件 |
| 福利待遇 | 薪资福利和其他待遇 |

### 2. 是不是每个章节直接切成一个 Chunk 就够了？

还不够。

假设“任职要求”有二十条，既包含开发语言，又包含算法经验、沟通要求和学历。整章作为一个 Chunk 仍然太大，用户问“是否要求 vLLM”时，容易混入许多无关要求。

所以章节通常只是**第一层边界**：先避免把“公司背景”和“任职要求”无差别合在一起，再考虑同一章节内部如何切。

### 3. 如果 JD 没有标准章节标题怎么办？

招聘网站中的 JD 排版不统一：有人用“岗位职责”，有人写“工作内容”，有人只列编号；也可能全文没有明确标题。

Job-RAG 的 `parse_sections()` 使用一组已知标题及正则规则来识别章节，不是让大模型猜。匹配不到时保留 `unknown`（未知）语境。

这意味着系统在不确定的时候**不强行把一段文字解释成任职要求**。代价是特殊格式的 JD 可能分节不准确，需要靠样本检查不断改进规则。

## 五、同一章节内部，应该按什么继续切？

### 1. 为什么 JD 里的编号很有用？

看“任职要求”的三条：

~~~text
1. 必须熟悉 Linux。
2. 有 vLLM 部署经验者优先。
3. 熟悉 Python 或 Java，满足其一即可。
~~~

每条通常描述一个相对完整的招聘条件，因此“1.”、“2.”、“3.”都是很有价值的**候选边界**。

与直接数 100、200 个字符相比，沿条目边界切，更有机会保留“必须”“优先”“或”等重要词和它们对应的技能。

### 2. 一条要求换行了，是不是就成了两条？

不一定。招聘网站排版可能写成：

~~~text
2. 有 vLLM 部署经验者优先，
   能处理生产环境推理服务问题更佳。
~~~

这是带续行的同一条要求，不应该因为中间出现换行符就直接拆开。

Job-RAG 的 `item_spans()` 会识别常见数字编号、圈号和项目符号，并将一个条目后续的内容尽量保留在该条目范围内；如果没有识别出列表标记，则主要退回按行划分。

这种方法适合格式比较规整的 JD，但不是“懂了所有招聘排版”的语义解析器。特殊缩进、嵌套列表仍有识别错误的可能。

### 3. 一条内部有“或”“但”“优先”，可以继续拆吗？

要格外小心。比如：

> 熟悉 Python 或 Java，满足其一即可。

它并不是两条独立的必备条件。如果为了缩小块数而在“或”附近截断，就可能把“任选其一”误读成“必须同时满足”。

因此**先尽量保留完整条目**，只有当它长到超出预算时，才考虑在更细的自然边界拆分。这是后面处理超长条目的出发点。

## 六、为什么还要区分“必须、优先”等条件？

### 1. 这些标签是谁规定的？

不是 RAG，也不是 Chunking 算法规定的，而是**用户需要回答的问题**决定的。

如果用户只问“哪些岗位出现 vLLM”，保留原文和章节通常就够了。

但用户问“哪些岗位**必须**掌握 vLLM”，就必须区分：

> 必须具备 vLLM 部署经验。

和

> 有 vLLM 部署经验者优先。

两句话的技能名称相同，但招聘含义不同。为了让分块过程尽量不要将不同性质的条件混在一起，就可以设计**要求强度**这样的属性。

这里的思路是：**先明确用户想做什么判断，再识别哪些文本差异会改变判断，最后决定是否需要标签。**

### 2. Job-RAG 目前用了哪些条件标签？

当前 `condition_level()` 对条目给出一个粗粒度值：

| 标签 | 大致含义 | 需要注意 |
|---|---|---|
| `required` | 必备要求 | “任职要求”章节里没有明确强制词的普通条目也可能被标为此值 |
| `preferred` | 优先、加分 | 不是明确必备 |
| `not_required` | 明确不要求 | 不是一种更弱的“必备程度”，而是否定条件 |
| `mixed` | 混合、例外或替代条件 | 不能直接推出每项技能的具体逻辑 |
| `unspecified` | 没有明确判定 | 职责、公司介绍等章节通常会得到此值 |

例如“Python 或 Java，满足其一即可”容易归入 `mixed`。这只是提示**条件逻辑复杂，需要读原句**，并没有完整抽取出“Python OR Java”的结构化逻辑。

同样，`required` 也不意味着系统已经人工核实了“该段里每一项技能都是硬门槛”。**当前标签是在组织检索片段，而不是生成可直接用于精确统计的技能事实表。**

### 3. 如果以后想区分“会调用 API”和“能部署模型”，怎么办？

这属于另一个问题：不仅关心“必备还是优先”，还关心**能力用到什么程度**。

例如：

> 有 vLLM 生产部署经验者优先。

这句话可以同时包含两个信息：

~~~json
{
  "skill": "vLLM",
  "requirement_strength": "preferred",
  "competency_depth": "deployment"
}
~~~

这是**未来业务建模的教学示例，不是现有 Job-RAG 已实现的数据字段**。“优先”与“部署”回答不同的问题，不应把 `deployment` 塞进 `required/preferred` 枚举中。

如果进一步要统计“全库有多少岗位将生产部署列为必备能力”，就需要把技能、条件、逻辑关系及原文证据关联到**具体要求**，而不能只靠一个 Chunk 标签。

## 七、已经划好章节和条目，为什么还要合并短片段？

### 1. 每条招聘要求单独建立一个 Chunk，不是最准确吗？

不一定。假设一个章节有十几条很短的要求，每条几十个字。全部独立索引，就会产生很多小 Chunk，每块还可能重复岗位、章节等提示信息。

独立小块容易定位到具体要求，却可能增加索引数量、重复内容和检索候选的碎片化。

因此可以把**相邻、语境相容的短条目**合并，在不破坏主要条件差异的前提下减少碎片。

### 2. 哪些内容可以合并，哪些不宜合并？

从一般设计看，至少要观察三件事：

**第一，是不是同一类内容？** 公司介绍与任职要求通常不应合并；同一章节内的两条相近职责则可能合并。

**第二，重要条件是否相容？** “必须具备”与“经验优先”混在一个 Chunk，容易让读者误解；如果系统已经识别出这种差异，就不宜无差别合并。

**第三，合并以后是否仍符合长度预算？** 即使两条条件相容，加在一起过长也不能无限追加。

Job-RAG 当前采用一个比较简单的实现：**同章节内，只有相邻且条件标签相同的片段，才尝试在预算内合并。** 它不是对两段文本做深度语义相似度判断，所以“标签相同”不保证两条要求真的属于同一主题。

### 3. 一条要求和一个 Chunk 究竟是什么关系？

现在可以把几个对象区分清楚：

~~~text
完整 JD
 ├─ 公司介绍（章节）
 │   └─ 一条或多条基本片段
 ├─ 岗位职责（章节）
 │   ├─ 条目 1
 │   └─ 条目 2       ──可能合并──→ 一个 Chunk
 └─ 任职要求（章节）
     ├─ 条目 1       ──可能独立──→ 一个 Chunk
     ├─ 条目 2
     └─ 超长条目 3   ──可能拆分──→ 多个 Chunk
~~~

**章节是理解来源的范围，条目是相对完整的基本片段，Chunk 才是最终参加检索的单位。** 三者不是一一对应的关系。

## 八、如果单条内容太长，必须切开怎么办？

### 1. 为什么不能到第 1100 个字符就直接截断？

因为预算边界可能刚好落在一句话中间。

例如：

> 熟悉模型部署流程；能够在生产环境完成灰度发布；出现推理延迟异常时，能够结合监控指标与日志定位……

如果在“出现推理延迟异常时”后面硬切，后一块可能丢掉条件前提。因此，超长条目更合理的处理顺序是**先找句子、分句等自然边界，再考虑强制按预算截断**。

### 2. Job-RAG 实际怎样处理超长条目？

`_split_long()` 首先检查整个条目能否装下。装不下时，在预算内寻找合适的句末位置，当前重点识别“。！？；”等标记；找不到可用自然边界才按可容纳的字符长度切。

一旦发生非自然边界的截断，元数据会记录 `hard_split`。同一个原始条目产生的片段还带有共同的 `continuation_id`，用于表明它们来自同一条目。

这并不保证模型每次检索时都会自动把全部续片取回。它的意义是：**不要丢掉片段之间的来源关系，必要时可以依据原文位置回查。**

当前策略也没有默认给每两个相邻 Chunk 增加一段固定重叠文本。重叠不是越多越好，它可能增加重复索引和费用，是否需要应由跨边界误检情况决定。

## 九、长度预算是什么？为什么当前是 1100 字符？

### 1. 1100 指的是每个 Chunk 至少要有 1100 字吗？

恰恰相反，**1100 是长度上限，不是需要填满的目标值**。

即使整份 JD 不到 1100 字，因为章节或条件标签不同，也可能形成多个 Chunk；如果某条内容很长，超过这个预算，则需要进一步拆分。

对当前默认 `section_typed` 策略而言，预算还包括为了检索而加的岗位名称、章节和条件性质提示，不只是 JD 正文。例如：

~~~text
岗位：模型服务平台工程师
章节：任职要求
条件性质：优先/加分条件，非明确必备
原文：
2. 有 vLLM 部署经验者优先。
~~~

这些内容**合计**不得超过预算；因此原文实际可用的字符数会比 1100 少一些。

### 2. 这里的“字符”是不是 Embedding 的 Token？

不是。

当前默认单位 `chars` 使用 Python 字符串长度计算，即 Unicode 码点数量。一个汉字通常算一个码点，一个英文字母也算一个码点；这既不是 UTF-8 字节数，也不能直接等同于模型 Token 数量。

项目还支持 `utf8_bytes` 和使用指定本地 tokenizer 的 `tokens` 预算。但即使选择本地 tokenizer，也不能未经验证就假设其 Token 数量与云端 Embedding 模型的实际计费 Token 完全一致。

### 3. 为什么偏偏选择 1100？

查看[2026-10-25 初版源码](https://github.com/leecolin2023/job-rag/blob/2a31c65e15f09cc719ad4580e5cd441d6aef96fa/job_rag/normalize.py)，当时的旧 `documents(row, size=1100)` 就已经采用这个值。后续结构化分块延续了它，并拿 600 字符做对照。

仓库目前没有提供“通过 JD 长度分布、模型 Token 上限或参数优化得出 1100 最优”的证据。因此要准确理解为：**1100 是当前保留的工程基线，不是经过验证的最佳长度。**

### 4. 1100 在真实 JD 上产生了什么影响？

[2026-10-25 的离线实验协议](../../docs/embedding-experiments.md)记录了 592 份有正文的 JD 在不同策略下生成的 Chunk 数：

| 分块方式 | 字符预算 | Chunk 总数 | 平均每份 JD |
|---|---:|---:|---:|
| 原段落/字符分块 `legacy` | 1100 | 790 | 1.33 |
| 章节/条目/条件分块 `section_typed` | 1100 | 2,443 | 4.13 |
| 同样的 `section_typed` | 600 | 2,657 | 4.49 |

为什么两种 1100 策略差别这么大？因为结构化分块更重视章节、条目和条件边界，**不是只根据字符上限决定分块数量**。因此第一行与第二行不属于“只改变预算”的实验。

再比较后两行：将预算从 1100 缩到 600，Chunk 只多了 214 个，约 **8.8%**。这与不少边界早已由 JD 结构决定的设计相符，但仅靠总数不能确定具体的 Chunk 长度分布和强制截断率。

### 5. 既然 600 更短，检索效果是不是更好？

没有观察到稳定的汇总优势。[第一轮真实 Embedding 实验](../../docs/recall-pilot-2026-10-25.md)在相同模型和语料下比较了 `section_typed_1100` 与 `section_typed_600`：

| 种子指标 | 1100 | 600 |
|---|---:|---:|
| Dev Recall@5 | 78.57% | 78.57% |
| Dev nDCG@5 | 0.6973 | 0.6973 |
| Test Recall@5 | 93.75% | 93.75% |
| Test nDCG@5 | 0.8683 | 0.8683 |

这些**汇总指标相同**，不代表两套方案每个查询的排序都完全一致。实验仅有 30 条查询，主要标注有限的已知相关岗位，不能据此断言 1100 最优。

更小预算增加了 Chunk 数和重复头部，但实际是否显著增加 Embedding 费用，需要结合服务返回的 Token 使用量判断，不能直接按 Chunk 数量估算。

因此，现阶段保留 1100 的理由是**尚未有充分证据支持换成另一个值**，而不是“1100 已被证明最好”。

## 十、把前面的规则用到示例 JD，会切成什么样？

回到第三节的模型服务平台岗位。先忽略具体代码，从设计思路看可以这样处理：

**第一步：确定章节。** 公司介绍、岗位职责、任职要求、加分项描述不同的事情，先作为不同范围。

**第二步：找到基本条目。** 两条岗位职责分别保留；三条任职条件也先分开，不把“Python 或 Java 满足其一”截成两条。

**第三步：观察条件性质。** “必须熟悉 Linux”与“vLLM 经验优先”不应仅因为相邻就合成一个含义不清的要求；“Python 或 Java”要保留“或”的关系。

**第四步：按预算形成 Chunk。** 同章节、条件相容的短条目可以合并；超过预算的再沿自然句子拆。

由此**可能**形成以下检索片段（教学示意，不是对该示例真实调用 `build_documents()` 的输出）：

| 检索片段 | 主要内容 | 为什么这样组织 |
|---|---|---|
| 公司介绍 Chunk | 公司提供 vLLM 推理服务 | 不与应聘门槛混合 |
| 职责 Chunk | 推理服务部署、监控、优化；线上延迟排查 | 相近、短小的职责可能合并 |
| 要求 Chunk A | 必须熟悉 Linux | 保留必备条件 |
| 要求 Chunk B | vLLM 部署经验优先 | 不误当成必备 |
| 要求 Chunk C | Python 或 Java，满足其一即可 | 保留替代关系 |
| 加分 Chunk | 金融行业经验更佳 | 保留加分语境 |

这样用户问“这个岗位必须掌握 vLLM 吗”，系统可以找到“vLLM 经验优先”这个片段，再回到 JD 原文确认。

但不能因为我们切得漂亮，就认为已经自动回答了这道题。**Chunking 负责提供便于检索和核对的片段；是否推荐岗位，仍需 Retrieval 和后续阅读判断。**

## 十一、切完以后，为什么还要给 Chunk 添加标题和原文位置？

### 1. 检索时只保存“有 vLLM 经验者优先”不行吗？

原句本身可以理解，但缺少岗位名称和章节时，检索系统及后续读者不容易判断它属于哪个职位、哪个招聘语境。

因此 Job-RAG 的 `_header()` 会为索引文本添加必要提示，例如“岗位：模型服务平台工程师”“章节：任职要求”，`section_typed` 还加上“条件性质：优先/加分条件”。

这样做是为了**把拆分前的重要上下文带到检索单位里**。但添加提示也可能影响 BM25 或 Embedding 的排序，不能预先认定越多越好。

### 2. 这些标题和标签是招聘方原文吗？

不是全部都是。

Job-RAG 区分：

- `Document.text`：供检索使用的文本，可能包含系统添加的岗位、章节、条件提示。
- `Document.details`：保存原文 `raw_text`、`source_start`、`source_end`、章节、标签、切分方式等信息。

来源偏移使用 Python Unicode 码点下标。通过 `description[source_start:source_end]` 可以拿回对应原文，避免误把检索用的提示词当成招聘方亲自写下的条件。

这一点很重要：用户若质疑“岗位是否真的必须掌握某项技术”，应当能回查原文，而不是只引用系统自己加的 `required` 标签。

## 十二、这些设计在 Job-RAG 代码中怎样实现？

前面的文章没有要求先认识源码。但理解完机制以后，代码职责就容易对应了：

~~~text
完整 JD
  ↓
识别章节范围
  ↓
在章节内识别编号条目及续行
  ↓
为条目生成粗粒度条件标签
  ↓
过长条目尽量按句子切
  ↓
相邻且同章节、同标签、未超预算的片段尝试合并
  ↓
添加检索上下文，并保留原文偏移
  ↓
产生多个 Document(text, details)
~~~

当前实现集中在 [`core.py`](core.py)：

| 函数 | 对应的设计问题 |
|---|---|
| `parse_sections()` | 如何找到 JD 中不同用途的章节？ |
| `item_spans()` | 怎样保留编号条目和续行？ |
| `condition_level()` | 怎样粗略区分招聘条件，避免错误合并？ |
| `_split_long()` | 超过预算的单条内容怎样尽量沿句子切开？ |
| `build_documents()` | 怎样组合相邻片段并产生最终 Chunk？ |
| `_header()` | 怎样在检索文本中保留必要的父级语境？ |

项目保留四套策略，主要用于观察不同分块设计的效果：

| 策略 | 核心区别 |
|---|---|
| `legacy` | 早期按段落及字符预算组织，重复较完整的岗位头部 |
| `fixed_compact` | 使用旧正文边界，缩减重复头部 |
| `section_compact` | 根据章节、条目和条件边界组织，使用紧凑头部 |
| `section_typed` | 与上一方案保留相同分块边界，并将条件性质提示写进检索文本 |

当前默认是 `section_typed`。在结构化方案里，为了让 `section_compact` 与 `section_typed` 可以比较“是否写入条件提示”的影响，两者计算合并边界时都会**预留带条件提示的头部预算**；但 `section_compact` 真正写入的头部更短。

旧 `legacy` 的 1100 主要限制正文，拼上完整岗位头部后，最终检索文本可能超过 1100；因此不能把四套策略都说成“1100 字符完全等长”的实验。

想查看一次分块的原文对应关系，可以沿用这个检查：

~~~python
from job_rag.chunking import build_documents

chunks = build_documents(job_row, strategy="section_typed", size=1100)

for chunk in chunks:
    detail = chunk.details
    assert (
        job_row["description"][detail["source_start"]:detail["source_end"]]
        == detail["raw_text"]
    )
~~~

这里验证的是**片段能定位到原文**，不等于验证了章节识别、条件标签与最终检索质量全部正确。

[索引 Worker](../indexing/README.md)负责将 Chunk 与可选 Embedding 写入索引；[Retrieval](../retrieval/README.md)根据查询找到相关 Chunk，再聚合为岗位并提供证据；[Querying](../querying/README.md)负责完整 JD 读取以及需要明确统计范围的查询。

## 十三、怎么判断 JD 切分到底有没有做好？

### 1. 先检查：有没有把原文切坏？

从具体 JD 抽样检查：

- “必须”“优先”“无需”“满足其一”是否被分到容易误解的片段？
- 没有章节标题、格式混乱或超长的 JD 怎么处理？
- `hard_split` 是否过多？同一条超长要求能否定位回原文？

这类检查回答的是**分块程序是否尽量保留原来的意思**。

### 2. 再检查：切出来的 Chunk 是否更容易被找到？

准备真实求职问题，例如“负责模型生产部署”“vLLM 是必备还是加分”“有金融行业经验要求”。保持相同模型、语料和查询，比较不同分块方案是否能更好地召回正确岗位，以及命中证据是否来自合适的章节。

这里需要同时看 **Chunk 级证据**和**岗位级排名**。Chunk 数变多、长度更整齐，都不自动等于检索更好。

### 3. 最后检查：它是否减少了招聘判断错误？

如果系统仍把“vLLM 优先”说成“必须”，或把公司介绍里的技术当成岗位职责，即使召回指标不错，业务结果也存在问题。

[2026-10-25 的离线实验](../../docs/recall-pilot-2026-10-25.md)显示：结构化分块在部分查询上让已知岗位排名提前，也在另一些查询上退化；增加条件提示并没有稳定改进。由于正例标注不完整，现有结果只足以指导后续实验，不能宣布某个策略普遍最好。

如果未来要重新确定 1100 字符预算，还应统计 JD **基本条目的长度分布、P90/P95、超预算比例、强制切分比例**，并结合召回、人工核验和真实 Token 成本做对照，而不是仅凭块数选择参数。

---

这套方法也能迁移到合同、操作手册或会议纪要：**先从用户要找什么信息出发，识别文档里能够保留完整意思的基本片段；再决定哪些内容不能混、哪些相邻内容可以合并、太长时怎样拆、切开后怎样回查原文。**

对 JD 而言，章节、条目、条件性质和长度预算，都是从这套通用思路推导出来的具体设计选择，而不是必须照搬的固定分块算法。
