# 候选检索：怎样从几百份 JD 中找到值得阅读的证据？

当用户问“找负责企业 RAG 全链路建设的工程岗位”，他需要的并不是出现“RAG”三个字的全部招聘广告，而是与工作任务接近、同时符合城市和薪资条件的岗位。`retrieval/` 负责产生**有排名、可截断的候选集合**；它不保证穷举，也不能将相似度直接当作招聘要求已经成立。

## 一、检索前为什么先过滤？

`search.py::resolve_filters()` 只保守地从问题里识别已知城市、明确的“20K以上”及候选人年限；用户显式传入的条件优先。`querying/filters.py::matches()` 用标准化字段检查薪资、城市、年限、状态等硬条件，避免相关性很高但工资或地区不符合的岗位混进来。

例如“做大模型部署、广州、20K以上”，先把“广州”和薪资约束落实到结构化字段，再用剩余描述表示检索目标。`skills` 为字面 AND 硬条件，不宜把“希望接触 vLLM”随意转成必须出现该字符串。

只有当前 `version`、`indexed_version` 与 `index_signature` 一致的 Chunk 才参加检索，防止职位已更新但证据还停留在上一版本。

## 二、BM25、Embedding、RRF 分别做什么？

`search.py::tokens()` 把英文技术词识别为词项，把连续中文切成字符二元组；`bm25()` 根据词频、文档长度和词项稀有程度计算词法相关性。它在“vLLM”“SGLang”等明确术语上比较直接，但“模型上线”和“推理服务化交付”可能字面不相同。

若启用 Embedding，查询也会生成向量；PostgreSQL 用 pgvector 精确余弦距离，SQLite 在 Python 中计算。它提供另一种语义候选信号，不负责断言岗位是否真的具备某项必备要求。Embedding 请求失败时回退为关键词模式。

两个通道各取前 100 个 Chunk，然后用 RRF 依据**排名**融合：某 Chunk 在两路都靠前，获得更大的累计排名贡献；不直接把不同量纲的 BM25 分数和余弦分数相加。融合后按 `source:job_id` 归并为岗位，返回每岗最多两个证据块，并附任职要求和加分章节的有限上下文以便复核。

## 三、为什么还要有多查询？

`candidates.py` 接收原问题和最多 4 条可选改写。比如用户说“公司知识问答”，可补“RAG”“知识库检索增强”等不同表达，在每条查询**保持同样硬条件**的前提下分别召回最多 30 个岗位，再对各查询的岗位排名做一层 RRF，去重并返回至多 60 个候选。

这就是两个不同层次的融合：`search()` 对词法/向量 **Chunk 排名**融合；`candidates()` 对不同**查询返回的岗位排名**融合。两者都只能提高候选排序与覆盖机会，不能证明结果涵盖全库。

## 四、候选怎样变成回答？

`answer.py` 默认生成可核对的来源列表；仅当请求 `generate=true` 并配置 Chat 模型时才调用 `providers.chat()`。回答必须包含可用的 `[1]` 等来源编号，并在生成后再次检查岗位版本与状态。如果模型失败或未配置，就退回来源列表。

另一路是外部 DeepSeek/OpenCode Agent：它通过 MCP 获取候选、读 `evidence` 与 `qualification_context`，必要时读取整个 JD 并自行作语义判断。它不等同于网页的 Chat 分支，也不意味着生产环境已经启用了专用 Qwen Reranker。

`total_matched` / `total_candidates` 代表受排名截断影响的检索结果数（响应有 `count_complete=false`），不是全库精确满足数；`fusion_score` 不是岗位适合度概率。

## 五、如何选择另外一条查询路径？

如果任务是“哪些职位**字面提到** vLLM，有多少个”，应该去[确定性查询](../querying/README.md)完成全库扫描，而不是用这个模块的 Top-K 推总数。如果任务要对多个候选进行技能要求比较，应读完整原文，区分“必备、优先、否定、例外”。离线实验使用的同岗位最高向量块聚合与这里的线上融合流程不同，详见[实验说明](../experiments/README.md)。
