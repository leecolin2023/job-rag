# 为什么搜索一个岗位，需要过滤、召回、融合和再核对？

求职者提出“广州、月薪下限 20K，找负责企业知识库全链路的工程岗位”。一个正确结果必须同时满足两种约束：**硬条件不能违反，工作内容又要与意图相关**。

纯关键词可能漏掉“知识接入—解析—索引—检索—服务化”的职位，因为它不一定写出“知识库全链路”；纯 Embedding 虽可能识别相关概念，却不能保证月薪下限符合要求。项目因此把查询先拆成确定性过滤和相关性排序，最后再核对 JD 原文。

## 一、为什么先过滤，再评价相关性？

`search.py` 收到 `SearchRequest` 后，仅保守识别已知城市、“20K以上”这样的明确薪资门槛及求职者年限。用户在表单或 Agent 中显式给出的条件优先。随后复用[querying/filters.py](../querying/README.md)的 `matches()`，将不满足城市、薪资、经验、状态等硬条件的岗位排除。

这避免了“语义分数高，所以可以放松用户的城市要求”。`skills` 更需要谨慎：它是文字出现的 AND 条件，不是“模型懂得用户偏好”的语义判断；用户只是希望接触 vLLM，强行要求 JD 必须出现 vLLM 会漏掉用“推理引擎部署”表达的岗位。

检索还会检查岗位 `version`、`indexed_version` 与 `index_signature` 是否一致；否则旧 Chunk 可能代表已被修改的 JD。

## 二、为什么 BM25 仍然有价值？

岗位招聘常出现 Python、vLLM、SGLang、FastAPI 等明确技术名称。`tokens()` 将英文技术名称作为词项，中文连续文字拆为二元字符片段；`bm25()` 根据词项稀有度、频率和文档长度给每个 Chunk 排名。

这样即使完全没有模型密钥，也能找到明确提到相关词的原文。它的局限是**同义表达**：问“让模型查资料后回答”，JD 却写“检索增强生成”，二者并不必然有较高的文字交集。BM25 好用，不等于它能理解需求的全部语义。

## 三、为什么同时支持 Embedding，却不把两种分数直接相加？

配置外部 Embedding 后，查询会被转换成向量，与索引中的 Chunk 向量计算余弦相似度。它能引入字面不同但语义相近的候选，然而向量距离和 BM25 的原始分数不在同一个量纲：比如 BM25 的 8.2 与余弦相似度 0.82，直接相加没有可靠意义。

因此 `search()` 把两种通道各自的**名次**转换成 RRF 排名贡献，再融合前 100 个 Chunk。一个块同时在两个通道靠前会受益，但这不是“岗位满足业务要求的概率”。没有 Embedding 时仅使用 BM25；向量请求失败也可降级为词法检索。

当前 PostgreSQL 通过 pgvector 做精确余弦排序，SQLite 在 Python 中计算；还没有 ANN 向量索引。小语料这样足够直接，但规模增长后需重新考虑效率。

## 四、为什么 Chunk 命中后，还要回到岗位？

同一条长 JD 可能有多个命中 Chunk。如果原样返回片段列表，某个长岗位可能占满前几名，用户却真正想比较的是**不同岗位**。因此 `search()` 融合 Chunk 排名后按 `source:job_id` 聚合，每岗保留最多两个命中块。

单个块仍可能丢失语境，代码会进一步带上任职要求和加分项的有限 `qualification_context`；必要时通过详情接口拿完整 JD。用户问“vLLM 是否必备”时，不能仅凭块中出现 vLLM 就判定成立。

## 五、为什么允许 Agent 发起多次查询？

用户的自然语言表达可能与 JD 不完全一致。`candidates.py` 可保留原问题，再附最多四个同义或相关技术改写；每条查询先独立召回最多 30 个岗位，再按**岗位排名**进行第二层 RRF 融合并去重。

例如“企业知识问答”与“RAG”“文档检索增强”可能各自召回一些不同岗位。多查询提高覆盖机会，但所有改写必须继承原始城市、薪资等硬约束；不应为了找得更多而悄悄放宽条件。它不是一个能证明全库已穷尽的过程。

## 六、生成回答为什么仍要复核？

`answer.py` 默认返回附状态和采集日期的来源列表；请求明确设置 `generate=true` 且配置 Chat 后才生成说明。生成结果至少检查引用编号，再复核岗位版本和状态；如果生成期间 JD 改了，不能继续返回原来的推荐作为当前事实。

外部 OpenCode/DeepSeek Agent 通过 MCP 阅读证据、再取完整 JD 进行判断，这是与网页 Chat 不同的一条路径，也不代表线上已经接入专用 Reranker。当前 `total_matched/total_candidates` 都受 Top-K 限制，`count_complete=false`，不应用于全库数量统计；要回答“总共多少”应转去[querying](../querying/README.md)。

代码最后才值得查：`search.py` 是条件过滤与单查询候选，`candidates.py` 组合多个查询，`answer.py` 做可核对输出。理解它们的关键在于：**过滤确保必要约束，检索提高候选可发现性，原文核验才能支撑招聘判断**。
