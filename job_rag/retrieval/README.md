# 招聘 JD 应该如何检索？——从一次岗位搜索理解召回、排序与证据核验

前面[《JD 数据应该如何切分？》](../chunking/README.md)已经解决了一件事：把一份很长的 JD（职位描述）整理成适合检索的 Chunk。接下来还有一个更直接的问题：

**用户提出求职要求后，系统怎样从这些 Chunk 中找到值得看的岗位？**

这篇文章用同一次岗位搜索贯穿讲解。先弄清每一步在做什么、为什么需要它，再看 Job-RAG 的实际代码。文中 A、B、C、D 四份 JD 是**教学示例**，不是对线上数据或排名的实测。

## 一、用户说“帮我找岗位”，系统究竟要完成什么？

假设用户输入：

> 帮我找**广州、月薪下限 20K 以上**，**负责企业 RAG 知识库建设**的工程岗位。

知识库里有下面四条岗位：

| 岗位 | 地点与月薪 | JD 关键信息 |
|---|---|---|
| A | 广州，25–35K | 岗位职责：建设文档接入、索引、语义检索和智能问答服务 |
| B | 广州，10–25K | 岗位职责：研发 RAG 知识库系统 |
| C | 广州，30–40K | 公司介绍：公司使用 RAG；岗位职责：负责销售客户关系管理软件 |
| D | 深圳，30–40K | 岗位职责：负责 RAG 系统部署、维护与优化 |

把四条 JD 里的 “RAG” 搜出来，会发生什么？

B、C、D 都提到了 RAG，但 B 的薪资下限不够，D 不在广州；C 的 “RAG” 只是公司背景，并不能说明销售岗位负责 RAG 建设。**真正值得继续看的反而可能是 A**：它没写 RAG 三个字，却描述了 RAG 系统相关的具体工作。

因此，完成这次搜索至少包含三个不同的问题：

**第一，哪些岗位满足不能妥协的条件？** 例如地点与薪资。这是**过滤**。

**第二，在剩下的岗位中，哪些工作内容接近用户的意思？** 例如 A 的“文档接入、索引、智能问答”与 RAG 建设是否相关。这是**召回与排序**。

**第三，找到候选以后，原文到底证明了什么？** 是公司业务、岗位职责，还是任职要求？招聘状态有没有核实？这是**证据核验**。

这里先认识两个词：

- **召回（Recall）**：尽可能把可能相关的岗位找进候选名单，重点担心**漏掉**好岗位。
- **排序（Ranking）**：候选已经找到了，决定**先让用户看谁**，重点担心不相关的岗位排在前面。

它们会相互影响，但目标不同。假如 A 根本没有进入候选名单，再好的排序也不可能把 A 排到第一。

## 二、为什么先处理城市和薪资，而不是直接搜索 RAG？

### 1. 什么叫“硬条件”？

用户明确规定“只看广州、月薪下限至少 20K”，即使某个深圳岗位的 RAG 技术很先进，也不应为了相似度高而混进结果。

这里的**硬条件**，就是有清楚判断规则、而且用户要求必须满足的约束。例如：

- 城市是否等于广州？
- 岗位**月薪下限**是否不低于 20,000 元？
- 岗位是否处于允许展示的招聘状态？

按例子筛选，B 因下限为 10K 被排除，D 因城市为深圳被排除。之后的检索只需要在 A、C 之间继续判断工作内容。

这叫**先限定候选范围，再计算相关性**。注意它是逻辑顺序，不一定要求数据库在物理执行时分成两次查询。

### 2. 为什么“我想做 RAG”不一定是硬条件？

因为用户想找的是一类**工作内容**，而不是要求 JD 必须出现某个字符串。

如果把 `RAG` 放进“所有岗位必须包含的关键词”过滤条件，就会直接排除 A。这样一来，后面即使使用再强的 Embedding 模型，也找不回它。

所以要区分：

- “岗位必须位于广州”——适合确定性过滤。
- “岗位必须**字面出现** vLLM”——只有用户明确要求按字面查找时，才适合做文字硬过滤。
- “希望从事 RAG 建设”——应先作为**相关性搜索意图**，保留不同表述进入候选的机会。

在 Job-RAG 中，`StructuredFilters` 和 `matches()` 负责明确条件。薪资默认采用 `lower_bound` 口径，即**岗位区间下限**达到要求；`10–25K` 并不满足“下限 20K”。`skills=["RAG"]` 当前也是**字面必须出现**，不等于“工作职责语义上属于 RAG”。

### 3. 城市和薪资怎么从一句话里识别出来？

有两种输入方式：用户直接在界面或 Agent 工具参数中填城市、薪资；或者系统从“广州”“20K 以上”等明确写法里提取。显式指定的条件优先。

这个提取是**有限规则解析**，不是任意自然语言都能理解。识别不了就需要调用方明确传参，不能悄悄把自己猜测的含义当成用户要求。

## 三、通过过滤以后，系统拿什么与问题匹配？

这里连接上一篇 Chunking 文章的结论。

一份 JD 可能同时包含公司介绍、岗位职责、任职要求和加分项。如果将整份 JD 当成一个检索文本，“公司使用 RAG”和“负责开发 RAG”可能混在一起。

Job-RAG 在索引阶段已经为一份 JD 生成多个 **Chunk**。检索阶段先拿**问题与 Chunk 比较**，而不是每次直接让模型阅读所有完整 JD。

例如 C 岗位可能有：

~~~text
Chunk C-1｜公司介绍：公司使用 RAG。
Chunk C-2｜岗位职责：负责销售客户关系管理软件。
~~~

A 岗位可能有：

~~~text
Chunk A-1｜岗位职责：建设文档接入、索引、语义检索和智能问答服务。
~~~

**Chunk 是参加匹配的单位，岗位是用户最终要看的单位。** 先找到 A-1、C-1 这样的片段，后面还要判断它们属于哪条岗位、能证明什么。

接下来就遇到一个技术问题：**到底怎样判断一个 Chunk 与问题接近？**

## 四、最容易实现的搜索：文本里有哪些相同的词？

### 1. 直接查字符串为什么还不够？

如果用户输入“vLLM”，直接查 JD 是否出现 `vLLM` 就能找到**字面命中**。

但用户输入“模型部署工程师”，一个 Chunk 可能写“模型部署、推理优化”，另一个只写了一次“部署”，还有一段很长的公司介绍反复出现“模型”。三者不应该只因为“命中/没命中”被当成同等相关。

检索需要的不只是找到了哪些文字，还需要**给候选排优先级**。

### 2. BM25 是什么？它为什么能够排序？

**BM25** 是常见的关键词相关性排序方法。它会查看：用户问题里的词项，在每个 Chunk 中是否出现、出现多少次、在全部参与比较的 Chunk 中有多常见，以及当前 Chunk 有多长。

可以用三个直觉理解：

| 观察 | 对排序的作用 |
|---|---|
| “vLLM”只在少数 Chunk 出现，“岗位”几乎处处出现 | 少见、能区分内容的词通常更有参考价值 |
| 某个 Chunk 提到相关词两次，另一个提到一次 | 频率可以提供信号，但增加次数不会无限等比例加分 |
| 两段文字命中相似，第二段夹杂大量其他内容 | 文档长度需要纳入比较，避免长文本仅因词多占优势 |

BM25 把这几个因素合在一起，给每个 Chunk 一个**词法相关性分数**。分数更高意味着按这套词法规则更值得先看，**不意味着招聘语义已经判断正确**。

不需要先背完整公式，但可以把它理解为：

~~~text
问题中的词项
    ↓
看每个词项在多少 Chunk 里出现（区分度）
    ↓
看它在当前 Chunk 出现几次（词频）
    ↓
结合 Chunk 的长度修正
    ↓
得到每个 Chunk 的词法排序分数
~~~

### 3. 中文句子怎么变成可以比较的词项？

BM25 不会自动知道“模型部署”应该分成哪些中文词。它必须先进行**分词或词项提取（tokenization）**。

Job-RAG 用了一种轻量做法：

- 英文技术名称尽量整体保留，例如 `vllm`、`python`、`sglang`。
- 连续中文按相邻两个字生成片段，例如“模型部署”可以形成“模型”“型部”“部署”。
- 去掉部分常见搜索词，并做少量固定别名替换。

这样不需要中文分词模型，也能找到具有局部字面重叠的文本。

但它不知道“知识库构建”和“文档索引与智能问答”一定属于同一类工作。**BM25 找的是词项线索，而不是对工作内容的完整理解。**

这就是它的价值和局限：遇到明确技术名称非常直接；遇到没有相同字词的表达，可能漏掉真正相关的 A 岗位。

## 五、两段文字没有相同关键词，还有机会搜到吗？

### 1. Embedding 解决的是哪类问题？

看两句话：

> 用户问：负责企业 RAG 知识库建设。

> JD 写：建设文档接入、索引、语义检索和智能问答服务。

字面词并不完全相同，但它们有可能指向相近的工作。

**Embedding（文本向量）** 是把一段文字转换为一组数字的模型表示方式。模型通过训练，使某些语义或用法相近的文本在向量空间中具有更接近的表示。检索时，系统分别保存 JD Chunk 的向量，并给用户问题生成向量，再比较它们的相似程度。

可以将它理解为：

~~~text
JD Chunk → Embedding 模型 → 文档向量（建索引时保存）
用户问题 → Embedding 模型 → 查询向量（查询时生成）
                                     ↓
                         计算两种向量的相似度
                                     ↓
                            按相似度排列 Chunk
~~~

最常见的比较方式之一是**余弦相似度**：看两组向量在方向上有多接近，而非简单比较字符。它提供的是相关性信号，不是“模型已经证明这个岗位满足条件”。

### 2. 为什么 Embedding 也不能单独解决所有问题？

因为“语义接近”与“招聘要求完全符合”不同。

> 必须有 vLLM 部署经验。

> 有 vLLM 部署经验者优先。

两句话的主题和用词都非常接近，但对候选人的门槛不同。如果向量分数很高就直接断定“必须掌握 vLLM”，仍然可能出错。

所以 Embedding **扩大不同表述被找到的机会**，但判断“必须、优先、不要求、二选一”等条件，仍要读原始 JD。

### 3. 当前 Job-RAG 什么时候真的使用 Embedding？

并不是每次检索都有向量。

只有配置了可用的 Embedding 服务、索引中保存了对应向量、查询也能成功生成向量时，系统才会同时使用向量通道。当前 PostgreSQL 使用 pgvector 做精确余弦排序，SQLite 则在 Python 中计算相似度；没有启用 ANN 近似向量索引。

如果没有配置或查询时调用失败，系统仍能走 BM25 词法检索，并对失败降级给出提示。**“能搜索”不等于“向量检索已经生效”。**

还有一个当前代码细节：用于 BM25 的查询文本会尝试去掉已识别的城市、薪资和经验表达；用于 Embedding 的请求仍使用原始问题。两条通道因此不仅模型不同，查询文本也不完全一样。以后做严格对照时需要记住这一点。

## 六、已经有 BM25 和 Embedding 两个排名，为什么还要融合？

### 1. 两套分数为什么不能直接相加？

假设某个 Chunk 的 BM25 分数为 7.5、余弦相似度为 0.83。直接相加成 8.33，看似简单，却没有合理依据认为“1 分 BM25”等价于“1 分余弦相似度”。

不同通道的分数尺度本来就不同，还可能随着语料变化。**所以 Job-RAG 不是直接相加原始分数，而是先利用各自的排名。**

### 2. RRF 是什么？怎么计算？

**RRF（Reciprocal Rank Fusion，倒数排名融合）** 的做法是：在每一份排名表里，越靠前贡献越高；一个 Chunk 如果在多张排名表中都靠前，就把这些贡献累加。

例如某个 Chunk：

- 在 BM25 中排第 2。
- 在 Embedding 中排第 5。

使用项目的 `k=60`，它得到的融合分约为：

~~~text
BM25 贡献：     1 / (60 + 2) ≈ 0.0161
Embedding 贡献：1 / (60 + 5) ≈ 0.0154
融合分：        0.0161 + 0.0154 ≈ 0.0315
~~~

另一个 Chunk 即使在 BM25 中排第一，但在 Embedding 前列没有出现，也只会拿到一次贡献：

~~~text
1 / (60 + 1) ≈ 0.0164
~~~

在这个**示意例子**中，两个通道都较靠前的 Chunk 会超过只在一个通道排第一的 Chunk。RRF 的作用是**综合不同检索方法提供的排序线索**，而不是判定谁语义正确。

`60` 是当前算法的融合常数，不是概率阈值；`0.0315` 也绝不是“3.15% 的岗位匹配概率”。

### 3. Job-RAG 每个通道融合多少个结果？

当前单查询检索先从词法和语义通道各取**最多前 100 个 Chunk**参与 RRF，然后在这些 Chunk 中继续排序。

这说明一个重要边界：**没进入某个通道前 100 的 Chunk，就不会因为“它也许相关”自动被这一通道贡献分数。** 检索不是证明所有 JD 都已经检查并判定合格的过程。

## 七、为什么排好 Chunk 以后，还要合并成岗位？

现在设想融合结果是：

| Chunk 排名 | 命中内容 | 属于哪个岗位 |
|---|---|---|
| 第 1 | 负责文档接入和语义检索 | A |
| 第 2 | 负责智能问答服务建设 | A |
| 第 3 | 公司使用 RAG | C |

如果原样展示三个 Chunk，用户看到的是 A、A、C，好像有三个岗位，实际上只有两个。

因此，Job-RAG 会把同一 `source:job_id` 下的 Chunk 归为同一个岗位，**按照该岗位首次出现在 Chunk 排名中的位置确定岗位顺序**。每个岗位最多附带两个命中的 Chunk 作为证据。这也意味着它并不是把该岗位所有 Chunk 的分数相加。

为什么还保留 Chunk 证据？因为你需要知道**系统究竟为什么找到了这个岗位**。C 被找到可能只是由于公司介绍写了 RAG。如果只显示一个“岗位匹配分数”，读者就看不到这个关键区别。

项目还会补充从原 JD 中提取的任职要求、加分项上下文 `qualification_context`，上限约 3600 字符，可能发生截断。必要时还应取回整份 JD。

因此，**找到相关片段 → 合并成岗位 → 阅读证据** 是三个不同动作：

- 找到片段，解决“可能相关的内容在哪里”。
- 合并岗位，解决“用户实际要比较哪些招聘职位”。
- 阅读证据，解决“这个职位是否真的符合要求”。

## 八、一次搜索没找到理想岗位，能换个问法再找吗？

可以。这叫**查询改写或多查询召回**。

例如“企业知识库建设”还可以尝试“RAG 系统研发”“文档索引与检索服务”“检索增强问答”。不同问法可能找到不同候选，尤其在 BM25 对字面表达敏感时更有价值。

但这里应分清两个问题。

### 1. 多查询怎样避免把同一个岗位返回好几次？

Job-RAG 的 `candidates()` 接受原问题和**最多四条额外改写**。每个问法各自检索最多 30 个岗位，然后**在岗位层面再次使用 RRF**，将重复岗位合并。

它与第六节的 RRF 不是一回事：

| 融合发生在哪里 | 融合对象 | 解决的问题 |
|---|---|---|
| **第一次** | 同一个问法下，BM25 和 Embedding 给出的 **Chunk 排名** | 不同匹配方法怎样合用 |
| **第二次** | 不同问法分别得到的 **岗位排名** | 多个问法找到的岗位怎样去重并排序 |

所以，**两次 RRF 的原理相同，但作用的对象和阶段不同**。

### 2. 多查询会不会改变用户真正的要求？

可能。所以系统应当固定原问题中已明确的广州、薪资等硬条件，只改变用于寻找相近工作内容的表达。

例如把“广州、月薪下限 20K 的 RAG 岗位”改成“全国不限薪资的 AI 岗位”，即使结果更多，也不是有效的同义改写。

当前改写由调用方 Agent 提出；Job-RAG 服务负责接收并执行，而不是自动生成同义词。多查询可以提高发现相关岗位的机会，但不能保证找全所有岗位。

## 九、找到候选以后，为什么还不能直接回答“这些岗位适合你”？

因为检索得到的是**值得阅读的候选**，还不是最终的招聘判断。

至少还有三类需要看原文的问题：

**第一，工作职责是否真相关？** “公司使用 RAG”与“岗位负责研发 RAG”不同。阅读命中的章节、必要时取全文，才能区分。

**第二，任职要求是否理解正确？** “必须掌握”“经验优先”“无需经验”“Python 或 Java 满足其一”可能影响是否值得投递。上一环节的相似度与 Chunk 标签都不能直接代替理解这些条件。

**第三，岗位信息是否仍可信？** 数据库最近采集到岗位，不代表企业此刻仍在招聘。`active` 才是已确认在招；`unknown` 只是尚未核验。最终还要以招聘页面和实际沟通为准。

Job-RAG 的 `answer()` 默认返回含岗位来源、采集日期、状态的列表；只有显式要求生成且配置 Chat 模型时才调用模型组织文字，并进行基础引用编号检查。**引用编号有效不代表对 JD 的解释就一定正确**。

还有一种更新问题：在生成回答或多查询进行期间，某个 JD 可能改版。代码会检查版本和状态，阻止把已经变化的旧结果当作当前推荐。但这不是对外部招聘网站的实时核验。

当前在线 Retrieval 也没有默认接入专用 Reranker。**Reranker 是对已经找到的一批候选重新评分排序**；它不能找回召回阶段漏掉的岗位，不能仅因使用了 Embedding 或 Agent 就认为已经完成重排。

## 十、Job-RAG 实际执行的是哪几步？与哪些代码对应？

现在已经解释完每个动作的目的，再对应代码会更直观：

~~~text
输入：广州、月薪下限20K，找企业RAG知识库建设岗位
    │
    ├─ 识别明确条件：广州、月薪下限20K
    │    └─ 排除不符合条件或索引版本未就绪的岗位
    │
    ├─ 在剩余岗位的 Chunk 中做 BM25 词法匹配
    │
    ├─ 若 Embedding 可用，同时计算 Chunk 语义排名
    │
    ├─ 词法/语义各取前100个 Chunk → 第一次 RRF
    │
    ├─ 将 Chunk 合并为不同岗位，保留证据
    │
    ├─ 若 Agent 提供额外问法，重复上面步骤
    │    └─ 多份岗位排名 → 第二次 RRF
    │
    └─ 回读 JD、核对要求和状态 → 展示候选或生成回答
~~~

对应源码：

| 文件 | 在这一流程中负责什么 |
|---|---|
| [`search.py`](search.py) | 解析部分明确条件、BM25、可选 Embedding、第一次 RRF、按岗位合并 |
| [`candidates.py`](candidates.py) | 接收额外问法、逐个搜索、第二次 RRF、去重与状态复核 |
| [`answer.py`](answer.py) | 将候选整理为来源列表、可选生成、引用编号检查及输出前复核 |
| [`querying/filters.py`](../querying/filters.py) | Retrieval 和全库查询共用的城市、薪资、经验等明确过滤规则 |

默认单查询展示最多 8 个岗位，可调整但不超过 30；多查询入口默认返回最多 20 个候选，可调整到 60。它们都是**有上限的候选**。`total_matched`、`total_candidates` 也只是当前有界召回得到的数量，**不是“知识库里总共有多少符合条件的岗位”**。后者应按问题口径使用[Querying 的完整枚举和计数能力](../querying/README.md)。

## 十一、怎么知道这套检索方法有没有帮用户找到更合适的岗位？

先别只看系统“返回了几个结果”，而要对照真实 JD 问三个简单问题。

### 1. 本来应该找到的岗位，找到了吗？

例如 A 虽然没写 RAG，却描述了知识接入、索引与问答服务。BM25 有没有遗漏它？增加 Embedding 或改写是否帮助 A 进入前 10？这是**召回覆盖**问题，可用岗位级 Recall@K 等指标观察。

### 2. 找到以后，排在前面的真的更值得看吗？

如果 C 只是在公司介绍提到 RAG，却排在 A 前面，系统可能需要更好的排序或后续语义判断。固定同一批候选，比较 Top-5 的人工相关性、nDCG 等指标，才更容易判断排序方法的贡献。

### 3. 最终有没有误解 JD？

是否把“有经验优先”说成“必须”？是否把“未核验”说成“正在招聘”？这种错误不一定能从相似度发现，需要按具体原文证据核对。

[2026-10-25 的离线实验](../../docs/recall-pilot-2026-10-25.md)比较过多种分块方案和 Embedding 召回。它只覆盖 30 条查询及其有限种子正例，尚不能证明当前在线 Hybrid、多查询与最终 JD 判断整条链路已达到最佳效果。

到这里，就可以把 Retrieval 总结为一句话：

**先用明确条件限定范围，再用 BM25、可选 Embedding 和查询改写尽量找到可能相关的 Chunk；把它们汇总成岗位并附上证据，最后阅读 JD 才能作出求职判断。**
