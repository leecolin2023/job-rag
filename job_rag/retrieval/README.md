# 如何从大量 JD 中找到真正相关的岗位？——候选召回、融合与证据核验

用户提出：“帮我找广州、月薪下限 20K 以上，真正负责企业 RAG 知识库建设的工程岗位。”数据库里可能有几百份 JD，其中有的写“RAG”，有的写“知识接入、解析、索引、检索与服务化”，还有的只是公司介绍中提到知识库产品。

这个任务不能简化成“搜索 RAG，然后把分数最高的几条列出来”。系统必须同时判断**哪些岗位具备资格进入候选范围**，以及**哪些岗位的工作内容与求职意图接近**。最后还要回到原 JD，确认它到底是工作职责、任职门槛还是加分项。

本文先解释信息检索的一般方法，再根据招聘 JD 的特点推导 Job-RAG 的召回链路，最后对照真实代码与现有实验。它与[Chunking：JD 数据应该如何切分](../chunking/README.md)相衔接：Chunking 决定*用什么文本参与匹配*，Retrieval 研究*如何根据问题找到值得阅读的内容*。

## 一、先明确检索在 RAG 中解决什么问题

假设一份知识库有 10,000 条记录，用户的问题只与其中几十条有关。让 LLM 一次读完全部记录成本高，也可能超出输入容量；但只让模型凭自身记忆回答，又无法利用新收集的 JD。检索（Retrieval）的任务，就是根据问题从知识库中**挑选并排序一批值得进一步阅读的候选内容**。

因此“检索正确”与“最终回答正确”不是一回事。检索可以把某个很相关的岗位排在前面，却不能仅凭这个排名确认用户符合入职要求，也不能确认招聘目前有效。一个合理的链路至少要区分：

| 环节 | 解决的问题 | 不能据此宣称 |
|---|---|---|
| 过滤范围 | 哪些记录不违反明确的城市、薪资等条件？ | 剩余岗位都符合工作偏好 |
| 候选召回 | 哪些文本可能谈到了目标工作？ | 没进入 Top-K 的岗位都不相关 |
| 相关性排序 | 有限阅读预算内应优先看哪些？ | 相似度就是满足条件的概率 |
| 证据核验 | JD 原文到底描述了什么，状态是否可靠？ | 搜到了关键词就证明它是必备技能 |

这里还有一个对象区别：**Job-RAG 的检索单位是 Chunk，用户要比较的业务对象却是岗位**。一份 JD 可以产生多个 Chunk；因此先找到片段，再合并到岗位，并保留片段作为解释依据。否则一份很长的 JD 可能凭多个片段占满结果页。

## 二、一般应该怎样设计一条检索链路？

设计起点不是先选择“BM25 还是 Embedding”，而是观察用户问题中哪些部分需要**确定性判断**，哪些需要**相关性判断**。

### 先把硬约束与开放式意图区分开

“广州”“月薪下限至少 20K”“必须是实习”通常可以转成明确的数据库条件：满足就是满足，不满足就不应为了语义分数高而入选。

“真正负责企业知识库建设”却不那么容易转成固定词表。某份 JD 可能写“构建文档接入与语义检索链路”，虽然没有“RAG”三字，仍很符合这个目标。这部分需要检索多个可能的表达，再阅读职责内容判断。

因此通常可以先**限定合格的记录范围**，再在该范围内做相关性排序。这个顺序是一个逻辑约束，而不强制要求数据库内部一定先执行哪条 SQL。

但“硬约束”必须来自明确口径，而不能由检索程序自行猜测。例如“希望接触 vLLM”是偏好；如果把它当作 JD 必须字面包含 `vLLM` 的硬条件，就会排除那些实际负责“推理服务部署”、却使用其他术语的岗位。正确的过滤可以防止误推荐，**错误的过滤也可能在召回开始前永久排除正例**。

### 对候选文本进行匹配：词法与语义提供不同信号

一种基本方案是**词法检索**：将问题与文档拆成词项，看是否具有可区分的词项重合。BM25 是经典的词法排序方法之一；它不只是数词出现次数，还综合考虑词在多少文档里出现、在当前文档出现多少次以及文本长度。

直觉上，“vLLM”出现在很少的 JD 中时，可能比“招聘”“负责”更能定位目标岗位；但同一个词在一个 Chunk 中出现 20 次，不应该简单当成出现一次的 20 倍证据。BM25 用词频饱和等机制缓和这种偏差。它对 Python、SGLang、FastAPI 等拼写明确的技术词很有用，但对“从文档查资料再回答”与“检索增强生成”这样的不同表述，可能无法产生足够的字面联系。

另一种方案是**语义向量检索**：用 Embedding 模型把问题与文本映射到向量空间，再依据余弦相似度等方法排序。它能在训练和数据适配允许的范围内识别部分表达差异，但向量相近并不意味着它理解了所有招聘条件。例如“必须具备部署经验”和“有部署经验者优先”高度相似，却对求职者有不同意义。

词法与语义不是谁替代谁：**词法偏向可核对的明确词项，语义有机会发现另一种表达；两者都只是候选匹配信号。**

### 为什么融合排名，而不是直接把两个分数相加？

如果 BM25 给某个 Chunk 的分数是 7.5，Embedding 余弦相似度是 0.83，这两个数没有共同量纲。直接相加等于擅自规定“1 分 BM25 与 1 分余弦相似度同样重要”。

一种简单做法是 RRF（Reciprocal Rank Fusion，倒数排名融合）：**先让各检索通道分别排出名次，再根据名次累加贡献**，不要求原始分数可比。

以当前代码的常数 `60` 为例，某个 Chunk 在词法排序第 2、向量排序第 5，那么贡献约为：

~~~text
RRF = 1 / (60 + 2) + 1 / (60 + 5)
    ≈ 0.0315
~~~

这里的 0.0315 只是排名融合分，**不是它有 3.15% 的概率满足用户需求**。融合也有代价：一个精确匹配专业术语的片段，可能被两个通道都较靠前的泛化片段超过。是否融合、怎样融合，都需要用真实问题检验。

### 找到片段后，还需要把答案交还给业务对象

匹配单位越小，检索越容易定位到局部证据，却越可能丢失 JD 其他条件。检索完成后应当把同一岗位的多个命中片段关联起来，避免重复展示；同时保留它们在原文中的位置，以便必要时取完整 JD。

最后是否推荐该岗位，还要判断语义、薪资口径、招聘状态与用户能力是否匹配。**召回阶段的职责是减少遗漏可能性，而不是宣称已经完成全部招聘判断。**

## 三、招聘 JD 的特点如何改变检索策略？

考虑三个教学示例：

~~~text
岗位 A｜广州｜25–35K
岗位职责：负责检索增强生成系统的知识接入、索引与问答服务。
任职要求：必须具备 Python 开发经验。

岗位 B｜广州｜10–25K
岗位职责：负责 RAG 知识库研发和线上部署。
任职要求：有 vLLM 经验者优先。

岗位 C｜深圳｜30–40K
公司介绍：公司已部署 vLLM 和 RAG 产品。
岗位职责：负责销售客户关系管理软件。
~~~

如果用户要求“广州，薪资**下限** 20K，建设企业知识库”，A 是有希望的候选：它虽然没直接写“RAG”，职责可能高度相关；B 的职责也相关，但薪资下限只有 10K，不符合当前硬条件；C 同时存在地区不符和“只在公司介绍提到关键词”的问题。

这里能看清两种容易混淆的错误：

- **召回不足**：只检索“RAG”可能漏掉 A，因为它用了另一套专业表达。
- **判断错误**：只看“RAG/vLLM”的匹配程度可能误推 B 或 C，忽略了薪资、地区或文本所在章节。

另外，JD 往往混用英文技术词、中文缩写、职责动词和招聘门槛。查询“模型部署”时，“推理服务上线”“模型托管”“vLLM 运维”可能分别对应不同岗位任务。适度的同义查询扩展可以提高覆盖机会；但查询改写**不能把硬性限制或用户真正关心的工作内容悄悄改掉**。

因此本项目选择了：明确条件过滤 + Chunk 级词法/可选语义召回 + 融合排序 + 岗位聚合 + 原文证据阅读。这个组合是针对当前语料与工具能力的实现选择，不是所有 RAG 项目必须照搬的固定流水线。

## 四、Job-RAG 的单次检索实际上怎样运行？

先看一条问题如何在项目中流动，而不是先记住三个源文件的名字：

~~~text
用户问题 + 显式条件
    ↓
解析少量明确条件，限定岗位范围及索引版本
    ↓
从合格岗位的 Chunk 中提取词项并计算 BM25
    ├── 配有 Embedding：计算查询向量和 Chunk 相似度
    └── 未配置/调用失败：仅使用词法通道
    ↓
各通道取前 100 个 Chunk，按 RRF 融合
    ↓
按 source:job_id 合并，保留最多两个命中证据块
    ↓
补充任职要求/加分项上下文，返回有限岗位候选
~~~

这个过程中有几项值得理解的实际取舍。

**其一，检索不能使用过期索引代替最新 JD。** 项目检查岗位当前版本、已经索引的版本及 `index_signature`。例如原文从“vLLM 经验优先”变成“必须掌握 vLLM”，旧 Chunk 不应再为新岗位提供证据。代价是尚未完成重建索引的岗位暂时不参与检索，返回结果会提示索引未就绪。

**其二，词法匹配采用轻量实现。** `tokens()` 保留英文技术名称，中文连续文字按二字片段组织，并对少量别名作替换；`bm25()` 计算各 Chunk 的词法分数。它不是完整的中文分词系统，也没有行业词典或训练出的招聘同义词库；优点是逻辑透明、无模型调用费用，缺点是可能遗漏不同表述。现在的 BM25 分数由当前符合硬过滤条件的 Chunk 集合计算，不应与另一次查询的分数直接作业务比例比较。

**其三，语义检索不是必然发生。** 只有配置有效 Embedding 服务时，才会对查询生成向量。PostgreSQL 使用 pgvector 进行精确余弦排序，SQLite 在 Python 中计算；当前未采用 ANN 近似索引。若向量服务失败，系统会提示并降级至词法通道，所以看到“检索成功”不能据此判断 Embedding 一定参与了搜索。

**其四，RRF 之后仍需要按岗位汇总。** `search()` 对融合后的 Chunk 依次排序，按岗位第一次出现的 Chunk 建立结果，并尽量保留该岗位前两个命中块作为 `evidence`。这里**不是把该岗位所有 Chunk 的 RRF 分数求和**；用于返回的 `score` 来自该岗位最高排序的命中 Chunk。每个岗位随后附加最多约 3600 字符的任职要求和加分项上下文（`qualification_context`，可能截断），便于判断原文到底是必备、优先还是例外。

**其五，返回数量存在人为截断。** 单查询 `limit` 最大 30、默认 8；每个通道的 RRF 只取前 100 个 Chunk。`total_matched` 是参与这次有界召回后得到的岗位数，`count_complete=false`，绝不是全库“符合用户需求的岗位总数”。

这几个实现细节共同决定了一个边界：**用户没在候选列表看到某份岗位，不足以证明这份 JD 不相关**。

## 五、什么时候需要多查询？扩展范围如何避免变成偏离需求？

假设首次查询“负责企业知识问答的工程岗位”，词法结果较少。Agent 可以另外尝试“RAG 系统建设”“文档索引与检索服务”等表述：它们从不同角度覆盖同一种工作任务，而不是随意增加不相关岗位种类。

Job-RAG 的 `candidates()` 接受原始查询以及**最多四条**额外改写。每条查询独立检索最多 30 个岗位，再在**岗位层**使用第二轮 RRF 聚合、去重，最终默认返回 20 个候选（`candidate_limit` 最大 60）。为什么融合两次？第一次是在**同一问法下融合词法和语义 Chunk 排名**；第二次是在**不同问法下融合岗位排名**。两层处理的对象和目的并不相同。

更重要的是，城市、薪资等硬条件从**原问题**提取并冻结，不能随着改写被扩大。否则“广州、月薪下限 20K 的 RAG 岗位”可能因为“知识平台”这个扩展查询变成全国不限薪资的职位，虽然召回数更多，却违背了需求。

查询改写目前由调用方 Agent 提出，不是搜索服务自动生成。MCP 的建议“普通查找最多三轮、补检索前说明缺口”是提示层策略，**并非后端强制执行的跨调用状态机**。多查几次可能扩大候选，但不会自动证明已经找全。

## 六、从候选到回答，还缺少哪些判断？

这时假设系统召回一份写着“有 vLLM 实践经验者优先”的 JD。它满足了“文本涉及 vLLM”，并不能推出“vLLM 必须具备”。Chunking 的 `required/preferred/mixed` 标签只是规则产生的提示；最终判断要阅读原句，必要时取完整 JD。

项目 `answer()` 默认输出带岗位、薪资、来源状态和采集日期的列表；只有显式设置 `generate=true` 且配置 Chat 模型时才尝试生成回答，并检查引用编号是否来自返回的候选。这里的引用校验**只验证编号存在，不保证模型对原文的解释一定准确**。

JD 也可能在生成回答的几秒钟内更新。代码在输出前重新检查岗位版本与招聘状态，发现变化时拦截过期结果并提示重新查询；多查询入口也会复核结果版本和状态。这不是外部招聘网站的实时核验：`unknown` 仅表示尚未核实在招，采集过的网页也不能自动视为当前仍在招聘。

调用方 Agent 如需给出“这个岗位适合你”的判断，还需阅读完整岗位职责与任职要求、核对硬条件，必要时再读取最新岗位详情。专用 Reranker 是另一种候选重排序方法，**当前在线检索链路并没有因为支持 Embedding 或调用 Agent 而自动具备专用 Reranker**。

## 七、怎样判断检索设计真正改善了求职结果？

从一般信息检索的机制看，至少应分别验证三类不同的损失。

**遗漏了该找到的岗位。** 用多个已核实相关岗位构成的查询集，衡量候选阶段的岗位级 Recall@K、HitRate@K。因为 Chunk 最后会按岗位合并，评估时不能只数召回了多少 Chunk。多查询是否增加正例覆盖，应与没有改写的方案比较，同时检查是否违反硬条件。

**找到了却排得不合理。** 同一批候选可以交给词法排名、向量排名、融合或专用 Reranker，比较 nDCG@K、Precision@K 和人工复核的 Top-K 质量。必须控制候选集不变，才能将变化归因于重排；Reranker 不可能找回从未进入候选集的岗位。

**检索相关，却解释错了招聘要求。** 例如将“有经验优先”解释为“必须具备”、将公司介绍误判为岗位职责，或把未核验岗位说成确认在招。这类问题需要阅读 JD 的证据判断，不能只靠向量相似度高低评分。

项目的[首轮真实 Embedding/分块实验](../../docs/recall-pilot-2026-10-25.md)只覆盖 30 条查询的种子标注：在部分场景中结构化分块使已知岗位名次提前，也有退化，BM25 在该批含明确术语的查询上表现很强。但它**没有测试当前线上多查询 Hybrid 整条链路的最终求职正确率**，也未完成全量的专用 Rerank 评测。不能把一次离线种子对照直接当作“线上检索已经最优”。

理解这套链路后，应能解释：为什么硬约束不应交给相似度、BM25 与 Embedding 各自改变什么、为什么 RRF 不是概率、为什么片段还要合并为岗位，以及**为什么 Top-K 检索天生无法承担精确全库计数**。后一个任务需要[Querying：精确查询与完整枚举](../querying/README.md)提供另一种访问方式。
